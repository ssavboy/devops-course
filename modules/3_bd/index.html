    Реляционные базы данных: SQL и администрирование СУБД для DevOps

    Для DevOps-инженера база данных — это самый ответственный компонент любой архитектуры, потому что в отличие от stateless-приложений (которые можно убить и пересоздать за секунду), база данных хранит состояние (Stateful). Потеря контейнера с бэкендом — это минутная заминка; потеря базы данных без рабочего бэкапа — это катастрофа для бизнеса.

    В этом модуле мы разберем как язык запросов SQL (в полном соответствии с программой), так и критически важные аспекты администрирования PostgreSQL: конфигурацию, права доступа, резервное копирование, индексы и миграции схемы БД в CI/CD.

    Блок 1. Архитектура PostgreSQL, терминал psql и конфигурация

    1.1. Как устроен PostgreSQL под капотом

    PostgreSQL работает по процессной модели клиент-сервер:

    • postmaster (Главный процесс): Слушает TCP-порт 5432 и принимает входящие подключения. На каждое новое клиентское соединение он порождает отдельный рабочий процесс (backend process).
    • Shared Buffers (Общий буфер в RAM): Область оперативной памяти, куда PostgreSQL загружает страницы таблиц и индексов с диска для быстрого чтения и изменения.
    • WAL (Write-Ahead Log — Журнал предзаписи): Сердце надежности СУБД. Перед тем как изменить данные на диске, PostgreSQL сначала последовательно записывает операцию в журнал WAL (pg_wal/). Если сервер внезапно обесточится, при старте база просто воспроизведет записи из WAL и восстановит целостность данных без единой потери.
    • PGDATA (Директория данных, обычно /var/lib/postgresql/data): Папка на диске, где физически лежат таблицы, индексы, WAL и конфигурационные файлы.

    1.2. Два главных конфигурационных файла PostgreSQL

    Внутри директории PGDATA (или /etc/postgresql/<версия>/main/) лежат два файла, с которыми работает каждый DevOps-инженер:

    1. postgresql.conf — основные настройки движка и ресурсов:
    2. listen_addresses = '*' (по умолчанию 'localhost' — база принимает коннекты только внутри хоста; для работы по сети ставят '*' или IP интерфейса).
    3. max_connections = 100 — лимит одновременных подключений.
    4. shared_buffers = 256MB — объем RAM, выделенный под кэш данных (обычно ставят 25% от всей оперативной памяти сервера).

    5. log_min_duration_statement = 500 — логировать все медленные SQL-запросы, которые выполняются дольше 500 мс (главный инструмент поиска тормозов!).

    6. pg_hba.conf (Host-Based Authentication) — встроенный фаервол и правила входа: Определяет, кто, к какой базе, с какого IP-адреса и каким методом может подключаться. 

      # TYPE   DATABASE   USER       ADDRESS          METHOD
local    all        postgres                    peer
host     all        app_user   172.18.0.0/16    scram-sha-256
host     all        all        0.0.0.0/0        reject

    Важно для безопасности: Всегда используйте современный метод шифрования паролей scram-sha-256 (не устаревший md5 и тем более не trust, который пускает вообще без пароля!).

    1.3. Инструменты работы: терминал psql и GUI (pgAdmin / DBeaver)

    В графических клиентах (pgAdmin 4, DBeaver) удобно визуально строить диаграммы связей (ER-диаграммы) и просматривать таблицы. Но на боевых серверах и внутри контейнеров графики нет — там используется штатный терминальный клиент psql.

    Шпаргалка по мета-командам psql (начинаются с обратного слэша \):

    Команда в psql Что делает
    \l Показать список всех баз данных на сервере (и их размеры с \l+).
    \c dbname Переключиться (Connect) на базу данных dbname.
    \dt / \dt+ Показать список всех таблиц в текущей схеме (с + — включая размер каждой таблицы на диске!).
    \d table_name Показать структуру конкретной таблицы (колонки, типы данных, ключи, индексы).

    | | \du | Показать список всех пользователей (ролей) и их привилегии. | | \timing | Включить секундомер выполнения каждого SQL-запроса в миллисекундах. | | \q | Выйти из psql (или нажать Ctrl+D). |

    Блок 2. Проектирование схемы данных (DDL): таблицы, типы и связи

    Язык SQL делится на подмножества:

    • DDL (Data Definition Language): Создание, изменение и удаление структуры таблиц (CREATE, ALTER, DROP, TRUNCATE).

    • DML (Data Manipulation Language): Работа с самими строками данных (SELECT, INSERT, UPDATE, DELETE).

    • DCL (Data Control Language): Управление правами доступа (GRANT, REVOKE).

    2.1. Ключевые типы данных и ограничения (Constraints)

    Основные типы данных в PostgreSQL

    :

    • Числа: INTEGER (INT), BIGINT (для больших ID), NUMERIC(10, 2) (точные дробные числа для денег без ошибок округления).
    • Автоинкремент: SERIAL / BIGSERIAL или современный стандарт SQL GENERATED ALWAYS AS IDENTITY.

    • Строки: VARCHAR(n) (строка с лимитом длины $n$), TEXT (строка произвольной длины — в PostgreSQL работает так же быстро, как VARCHAR).

    • Дата и время: DATE, TIMESTAMP (без часового пояса), TIMESTAMPTZ (TIMESTAMP WITH TIME ZONE — золотой стандарт для серверов, всегда хранит время в UTC).

    • Логический тип: BOOLEAN (true / false).

    • Специальные типы (суперсила Postgres): UUID, JSONB (бинарный индексируемый JSON для хранения полуструктурированных данных и конфигов), INET (для хранения IP-адресов и подсетей!).

    Ограничения целостности (Constraints)

    :

    • PRIMARY KEY (Первичный ключ): Уникальный идентификатор строки в таблице (не может быть пустым NULL и не может повторяться).

    • FOREIGN KEY (Внешний ключ): Ссылка на PRIMARY KEY другой таблицы — создает связь между таблицами и не позволяет записать «висячую» ссылку на несуществующий объект.

    • NOT NULL: Запрещает оставлять поле пустым.

    • UNIQUE: Гарантирует уникальность значения во всей колонке (например, hostname или email).

    • CHECK: Проверяет значение по условию (например, CHECK (cpu_cores > 0)).

    • DEFAULT: Задает значение по умолчанию (например, DEFAULT NOW()).

    2.2. Создание таблиц, связей и каскадное удаление (ON DELETE CASCADE)

    Представим схему данных для учета инфраструктуры:

    1. Таблица environments (Окружения: production, staging, dev).

    2. Таблица servers (Серверы, каждый привязан к своему окружению: связь Один-ко-Многим — 1:N).

    3. Таблица deployments (История выкаток сервисов на эти серверы).

    Как работает каскадное удаление (ON DELETE)

    :

    Что должно произойти с записями в таблице deployments, если мы удалим сервер из таблицы servers?

    • ON DELETE RESTRICT (по умолчанию) — база выдаст ошибку и запретит удалять сервер, пока на него ссылаются деплои.

    • ON DELETE CASCADE — при удалении сервера PostgreSQL автоматически каскадно удалит все связанные с ним записи в deployments.

    • ON DELETE SET NULL — сервер удалится, а в таблице deployments в колонке server_id проставится NULL (история деплоев сохранится).

    -- 1. Создаем таблицу окружений
CREATE TABLE environments (
    id SERIAL PRIMARY KEY,
    env_name VARCHAR(50) NOT NULL UNIQUE,
    is_critical BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. Создаем таблицу серверов со связью на environments (FOREIGN KEY)
CREATE TABLE servers (
    id SERIAL PRIMARY KEY,
    hostname VARCHAR(100) NOT NULL UNIQUE,
    ip_address INET NOT NULL,
    cpu_cores INT NOT NULL CHECK (cpu_cores > 0),
    ram_gb INT NOT NULL CHECK (ram_gb > 0),
    env_id INT REFERENCES environments(id) ON DELETE RESTRICT,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 3. Создаем таблицу деплоев с КАСКАДНЫМ удалением при удалении сервера
CREATE TABLE deployments (
    id SERIAL PRIMARY KEY,
    service_name VARCHAR(100) NOT NULL,
    version VARCHAR(30) NOT NULL,
    status VARCHAR(20) NOT NULL CHECK (status IN ('SUCCESS', 'FAILED', 'ROLLED_BACK')),
    duration_sec NUMERIC(6, 2) NOT NULL,
    server_id INT NOT NULL REFERENCES servers(id) ON DELETE CASCADE,
    deployed_at TIMESTAMPTZ DEFAULT NOW()
);

    Изменение и удаление таблиц (ALTER, DROP)

    :

    -- Добавить новую колонку в существующую таблицу
ALTER TABLE servers ADD COLUMN os_version VARCHAR(50) DEFAULT 'Ubuntu 24.04';

-- Переименовать колонку
ALTER TABLE servers RENAME COLUMN ram_gb TO memory_gb;

-- Удалить колонку
ALTER TABLE servers DROP COLUMN os_version;

-- Полностью удалить таблицу (и зависимые связи через CASCADE)
-- DROP TABLE deployments CASCADE;

    Блок 3. Манипуляция данными (DML), фильтрация, функции и JOIN

    3.1. Добавление, изменение и удаление данных (INSERT, UPDATE, DELETE)

    -- 1. Вставка данных (INSERT)
INSERT INTO environments (env_name, is_critical) VALUES
    ('production', true),
    ('staging', false),
    ('development', false);

-- 2. Обновление записей с фильтрацией (UPDATE ... WHERE)
-- ВНИМАНИЕ: Никогда не запускайте UPDATE или DELETE без секции WHERE,
-- иначе вы перезапишете или сотрете ВСЮ таблицу!
UPDATE servers
SET memory_gb = 32
WHERE hostname = 'prod-api-01' AND cpu_cores >= 8;

-- 3. Удаление записей по фильтру (DELETE ... WHERE)
DELETE FROM deployments
WHERE status = 'FAILED' AND deployed_at < NOW() - INTERVAL '30 days';

    3.2. Выборки, операторы сравнения, сортировка и преобразование типов (CAST)

    -- Фильтрация (WHERE), операторы сравнения (=, !=, >, <, >=, IN, BETWEEN, LIKE, IS NOT NULL)
-- и сортировка (ORDER BY ... ASC / DESC) с лимитом строк (LIMIT)
SELECT hostname, ip_address, cpu_cores, memory_gb
FROM servers
WHERE cpu_cores >= 4
  AND hostname LIKE 'prod-%'
  AND env_id IS NOT NULL
ORDER BY memory_gb DESC, hostname ASC
LIMIT 10;

-- Преобразование типов данных в SQL-запросах: функция CAST(val AS type) или оператор Postgres ::
SELECT 
    hostname,
    ip_address::TEXT AS ip_string,
    CAST(memory_gb AS NUMERIC) / cpu_cores AS ram_per_core_ratio,
    '2026-10-18'::DATE AS report_date
FROM servers;

    3.3. Функции для работы со строками, датой и временем

    SELECT
    -- Функции работы со строками:
    UPPER(service_name) AS service_upper,                 -- В верхний регистр
    LOWER(status) AS status_lower,                        -- В нижний регистр
    CONCAT(service_name, ':', version) AS image_tag,      -- Склейка строк (или оператор ||)
    SUBSTRING(version FROM 1 FOR 4) AS major_minor,       -- Вырезка подстроки
    REPLACE(service_name, '-service', '') AS short_name,  -- Замена подстроки
    LENGTH(service_name) AS name_len,                     -- Длина строки

    -- Функции работы с датой и временем:
    NOW() AS current_time,                                -- Текущее время с таймзоной
    DATE_TRUNC('day', deployed_at) AS deploy_day,         -- Округление даты до дня/часа/месяца
    EXTRACT(HOUR FROM deployed_at) AS deploy_hour,        -- Извлечь конкретный час (или YEAR, MONTH)
    NOW() - deployed_at AS age_interval                   -- Сколько времени прошло с момента деплоя
FROM deployments;

    3.4. Группировка данных (GROUP BY) и агрегирующие функции

    Агрегирующие функции сворачивают множество строк в один итоговый показатель:

    • COUNT(*) — количество строк.

    • SUM(col) — сумма значений.

    • AVG(col) — среднее арифметическое.

    • **MIN(col) / MAX(col)** — минимум и максимум.

    Разница между WHERE и HAVING (любимый вопрос на собеседованиях): * WHERE фильтрует исходные строки ДО группировки. * HAVING фильтрует **уже сгруппированные результаты ПОСЛЕ GROUP BY** (по агрегатным функциям).

    -- Посчитать статистику деплоев по каждому сервису и вывести только те сервисы,
-- которые деплоились больше 1 раза
SELECT 
    service_name,
    COUNT(*) AS total_deploys,
    ROUND(AVG(duration_sec), 2) AS avg_duration_sec,
    MAX(duration_sec) AS max_duration_sec,
    SUM(CASE WHEN status = 'FAILED' THEN 1 ELSE 0 END) AS failed_count
FROM deployments
WHERE deployed_at >= NOW() - INTERVAL '7 days'
GROUP BY service_name
HAVING COUNT(*) > 1
ORDER BY total_deploys DESC;

    3.5. Виды соединений таблиц (JOIN) и извлечение связанных данных

    Чтобы собрать полную картину из нескольких связанных таблиц, используют операторы соединения JOIN:

    Вид JOIN
    		 Как работает Когда использовать
    INNER JOIN (или просто JOIN) Возвращает только те строки, для которых нашлось совпадение в обеих таблицах. Показать все серверы и названия их окружений (серверы без окружения не попадут).
    LEFT JOIN Возвращает ВСЕ строки из левой таблицы, а из правой подтягивает совпадения (если совпадения нет — ставит NULL). Найти все серверы, включая те, на которые еще ни разу ничего не деплоили (WHERE d.id IS NULL)!
    RIGHT JOIN Возвращает все строки из правой таблицы и совпадения из левой. Например, вывести все окружения из справочника, даже если в них пока нет ни одного сервера.
    FULL OUTER JOIN Объединяет LEFT и RIGHT — возвращает все строки из обеих таблиц, заполняя пропуски через NULL. Сверка расхождений между двумя таблицами. 
    -- Извлечение связанных данных сразу из 3 таблиц (INNER JOIN):
-- Какой сервис, на какой сервер и в какое окружение был выкачен?
SELECT 
    e.env_name,
    s.hostname,
    s.ip_address,
    d.service_name,
    d.version,
    d.status,
    d.deployed_at
FROM deployments d
INNER JOIN servers s ON d.server_id = s.id
INNER JOIN environments e ON s.env_id = e.id
ORDER BY d.deployed_at DESC;

-- Поиск "простаивающих" серверов без единого деплоя через LEFT JOIN:
SELECT s.hostname, s.ip_address
FROM servers s
LEFT JOIN deployments d ON s.id = d.server_id
WHERE d.id IS NULL;

    Блок 4. Администрирование СУБД для DevOps: Индексы, Бэкапы и Миграции

    4.1. Индексы (B-Tree) и анализ производительности (EXPLAIN ANALYZE)

    Если в таблице deployments 10 миллионов строк и вы делаете запрос SELECT * FROM deployments WHERE service_name = 'auth-api', без индекса PostgreSQL вынужден читать с диска все 10 миллионов строк подряд (Seq Scan — Sequential Scan). Это кладет диск сервера на лопатки.

    Создав индекс (CREATE INDEX), мы строим сбалансированное дерево поиска (B-Tree), по которому база находит нужные строки за 1 миллисекунду (Index Scan):

    -- Создать индекс по колонке service_name и времени деплоя
CREATE INDEX idx_deployments_service_date ON deployments (service_name, deployed_at DESC);

-- В продакшене на живых таблицах ВСЕГДА используйте флаг CONCURRENTLY!
-- Обычный CREATE INDEX блокирует таблицу на запись, а CONCURRENTLY строит индекс в фоне без простоя:
CREATE INDEX CONCURRENTLY idx_servers_ip ON servers (ip_address);

-- Посмотреть реальный план выполнения запроса и затраченное время:
EXPLAIN ANALYZE SELECT * FROM deployments WHERE service_name = 'auth-api';

    4.2. Транзакции (ACID) и блокировки

    Любая серия изменений должна быть атомарной (либо выполнились все шаги, либо ни одного). В SQL это оборачивается в блок BEGIN ... COMMIT (или ROLLBACK при ошибке):

    BEGIN;
UPDATE servers SET env_id = 1 WHERE hostname = 'stage-node-01';
INSERT INTO deployments (service_name, version, status, duration_sec, server_id)
VALUES ('billing-api', '2.1.0', 'SUCCESS', 14.5, 2);
COMMIT; -- Если что-то пошло не так до COMMIT, команда ROLLBACK отменит всё!

    Главный запрос DevOps-инженера при «зависании» базы в продакшене: Посмотреть текущие активные запросы и убить зависший запрос, который заблокировал таблицу:

    -- 1. Найти долгие или зависшие запросы (системное представление pg_stat_activity)
SELECT pid, now() - query_start AS duration, usename, state, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC;

-- 2. Мягко отменить запрос по его PID (аналог SIGTERM для запроса)
SELECT pg_cancel_backend(12345);

-- 3. Жестко разорвать соединение с базой, если мягкая отмена не помогла
SELECT pg_terminate_backend(12345);

    4.3. Резервное копирование и восстановление (pg_dump и pg_restore)

    Логический бэкап с помощью pg_dump не блокирует работу базы — он читает согласованный снимок данных (snapshot) прямо во время работы пользователей.

    Два главных формата pg_dump:

    1. Plain SQL (.sql / .sql.gz) — обычный текстовый файл с командами CREATE TABLE и COPY. Удобно читать глазами, восстанавливается через psql.
    2. Custom Format (-Fc, файл .dump) — стандарт для продакшена: Сжат по умолчанию, позволяет восстанавливать данные в несколько потоков (-j 4) или вытащить из бэкапа только одну случайно удаленную таблицу, не трогая всю остальную базу!
    # 1. Снять бэкап в сжатом профессиональном формате Custom (-Fc)
pg_dump -U postgres -d infra_db -Fc -f /backups/infra_db_$(date +%F).dump

# 2. Восстановить базу целиком из Custom-бэкапа в 4 потока (-j 4) с очисткой старых объектов (--clean)
pg_restore -U postgres -d infra_db --clean --if-exists -j 4 /backups/infra_db_2026-10-18.dump

# 3. Восстановить из огромного бэкапа ТОЛЬКО ОДНУ случайно удаленную таблицу (-t deployments)
pg_restore -U postgres -d infra_db -t deployments /backups/infra_db_2026-10-18.dump

    4.4. Миграции схемы БД в CI/CD (Flyway / Liquibase / Alembic)

    В реальных проектах никто не заходит в базу руками, чтобы выполнить ALTER TABLE. Изменения структуры таблиц хранятся в Git в виде версионированных файлов миграций:

    • V1__init_schema.sql
    • V2__add_os_version_to_servers.sql

    Инструмент миграций (например, Flyway, Liquibase или Alembic для Python) создает в базе служебную таблицу schema_version, сверяет, какие файлы уже были применены, и при деплое новой версии в CI/CD автоматически накатывает только недостающие скрипты.

    Золотое правило Zero-Downtime миграций (Backward Compatibility): Никогда не переименовывайте и не удаляйте колонку одним шагом в один релиз! Пока обновляются контейнеры, старая версия кода еще работает и упадет с ошибкой Column not found. Паттерн Expand and Contract (В 3 шага):

    1. Релиз 1: Добавить новую колонку (без NOT NULL или с DEFAULT), начать писать данные в обе колонки.
    2. Релиз 2: Переключить чтение в коде на новую колонку.
    3. Релиз 3: Удалить старую ненужную колонку.

    🛠 Практический проект Модуля 3: Создание БД, аналитика, каскадное удаление и бэкап

    Этап 2. Создание схемы данных, связей и наполнение таблиц

    Скопируй и выполни этот блок — он передаст SQL-скрипт напрямую в psql, создаст 3 связанные таблицы (environments, servers, deployments) и заполнит их реалистичными данными:

    docker exec -i pg-server psql -U admin -d devops_inventory << 'EOF'
-- 1. Очистка на случай повторного запуска
DROP TABLE IF EXISTS deployments CASCADE;
DROP TABLE IF EXISTS servers CASCADE;
DROP TABLE IF EXISTS environments CASCADE;

-- 2. Создание таблиц со связями и ограничениями
CREATE TABLE environments (
    id SERIAL PRIMARY KEY,
    env_name VARCHAR(50) NOT NULL UNIQUE,
    is_critical BOOLEAN DEFAULT FALSE
);

CREATE TABLE servers (
    id SERIAL PRIMARY KEY,
    hostname VARCHAR(100) NOT NULL UNIQUE,
    ip_address INET NOT NULL,
    cpu_cores INT NOT NULL CHECK (cpu_cores > 0),
    memory_gb INT NOT NULL CHECK (memory_gb > 0),
    env_id INT NOT NULL REFERENCES environments(id) ON DELETE RESTRICT,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE deployments (
    id SERIAL PRIMARY KEY,
    service_name VARCHAR(100) NOT NULL,
    version VARCHAR(30) NOT NULL,
    status VARCHAR(20) NOT NULL CHECK (status IN ('SUCCESS', 'FAILED', 'ROLLED_BACK')),
    duration_sec NUMERIC(6, 2) NOT NULL,
    server_id INT NOT NULL REFERENCES servers(id) ON DELETE CASCADE,
    deployed_at TIMESTAMPTZ DEFAULT NOW()
);

-- 3. Добавление данных в таблицы

    ('auth-api',    '1.1.1', 'SUCCESS',     14.20, 2, NOW() - INTERVAL '1 day'),
    ('payment-svc', '2.0.1', 'SUCCESS',     22.80, 1, NOW() - INTERVAL '3 days'),
    ('payment-svc', '2.0.2', 'ROLLED_BACK', 65.00, 2, NOW() - INTERVAL '12 hours'),
    ('frontend-ui', '3.4.0', 'SUCCESS',      8.50, 4, NOW() - INTERVAL '4 hours'),

    Этап 3. Отработка аналитических запросов, JOIN, группировки и обновлений

    Выполни этот аналитический блок и изучи результаты в терминале:

    docker exec -i pg-server psql -U admin -d devops_inventory << 'EOF'
\echo '=== 1. Сводный отчет по деплоям с объединением 3 таблиц (INNER JOIN) и функциями строк/дат ==='
SELECT 
    UPPER(e.env_name) AS env,
    s.hostname,
    CONCAT(d.service_name, ':', d.version) AS release_artifact,
    d.status,
    d.duration_sec::INT AS sec_rounded,
    TO_CHAR(d.deployed_at, 'YYYY-MM-DD HH24:MI') AS deploy_time
FROM deployments d
JOIN servers s ON d.server_id = s.id
JOIN environments e ON s.env_id = e.id
ORDER BY d.deployed_at DESC;

\echo '=== 2. Поиск серверов, на которые еще не было ни одного деплоя (LEFT JOIN) ==='
SELECT s.hostname, s.ip_address::TEXT, s.cpu_cores, s.memory_gb
FROM servers s
LEFT JOIN deployments d ON s.id = d.server_id
WHERE d.id IS NULL;

\echo '=== 3. Группировка (GROUP BY) и агрегатные функции по окружениям ==='
SELECT 
    e.env_name,
    COUNT(s.id) AS server_count,
    SUM(s.cpu_cores) AS total_cpu,
    SUM(s.memory_gb) AS total_ram_gb,
    ROUND(AVG(s.memory_gb), 1) AS avg_ram_gb
FROM environments e
LEFT JOIN servers s ON e.id = s.env_id
GROUP BY e.env_name
ORDER BY total_ram_gb DESC;

\echo '=== 4. Обновление записей с фильтрацией (апгрейд RAM для всех staging и dev серверов) ==='
UPDATE servers
SET memory_gb = memory_gb * 2
WHERE env_id IN (SELECT id FROM environments WHERE is_critical = false)
RETURNING hostname, memory_gb AS new_memory_gb;
EOF

    Этап 4. Снятие бэкапа, проверка каскадного удаления и восстановление

    Теперь проверим, как работает ON DELETE CASCADE, а затем восстановим удаленные данные из бэкапа pg_dump:

    1. Протестируй каскадное удаление связанных объектов: У нас на сервер stage-app-01 (id = 4) было выкачено 2 релиза сервиса frontend-ui. Удалим сам сервер stage-app-01 из таблицы servers и убедимся, что все связанные с ним деплои из таблицы deployments автоматически удалились каскадом:
    docker exec -i pg-server psql -U admin -d devops_inventory << 'EOF'

\echo '--- Количество деплоев ПОСЛЕ удаления сервера (2 связанных деплоя удалились каскадно!) ---'
SELECT COUNT(*) AS deployments_after FROM deployments;
EOF
    1. Восстанови базу из бэкапа с помощью pg_restore: Представим, что удаление сервера было ошибочным. Восстановим базу за 1 секунду из нашего дампа /tmp/inventory_backup.dump:
