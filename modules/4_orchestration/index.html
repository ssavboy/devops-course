    Оркестрация многоконтейнерных приложений Docker Compose & Nginx

    Когда проект вырастает из одного контейнера и превращается в систему (Фронтенд + Бэкенд API + База данных PostgreSQL + Кэш Redis + Веб-сервер Nginx), запускать каждый контейнер вручную через длинные простыни docker run становится невозможно.

    Docker Compose решает эту задачу с помощью декларативного подхода: мы описываем всю архитектуру, сети, тома и зависимости в одном файле compose.yaml и поднимаем весь стек одной командой docker compose up -d.

    Блок 1. Принципы микросервисной архитектуры и 12-Factor App

    1.1. Монолит против Микросервисов

    • Монолит (Monolith): Вся бизнес-логика (авторизация, каталог, оплата, уведомления) живет в одном большом процессе и использует одну общую базу данных. Если модуль генерации отчетов вызовет утечку памяти — упадет весь сайт целиком.
    • Микросервисы (Microservices): Приложение разбито на независимые, слабосвязанные (loosely coupled) сервисы, общающиеся по сети (HTTP/REST, gRPC или через очереди сообщений RabbitMQ/Kafka).

    Ключевые правила проектирования микросервисов для DevOps: 1. Stateless (Отсутствие состояния в контейнерах приложений): Контейнер с кодом (Python/Go/Node.js) не должен хранить сессии пользователей или загруженные картинки на своем локальном диске. Любой инстанс бэкенда может быть убит или клонирован в 10 копиях за секунду. Всё состояние выносится во внешние Stateful-сервисы: PostgreSQL (данные), Redis (сессии и кэш), S3 (файлы). 2. Конфигурация через окружение (III фактор из 12-Factor App): Никаких зашитых в код адресов БД или паролей. Окружение (dev, stage, prod) настраивается исключительно через переменные окружения (ENV) и примонтированные секреты. 3. Изоляция сетей (Least Privilege Networking): Внешний мир видит только входные ворота — Reverse Proxy (Nginx). Сам бэкенд-сервис находится во внутренней сети, а база данных — в глубокой внутренней сети, куда нет доступа даже у Nginx.

    [Интернет :80/:443] 
        │
   (frontend-net)
        ▼
   [ Nginx Proxy ]
        │
   (backend-net)
   ┌────┴────┐
   ▼         ▼
[App-1]   [App-2]  (Горизонтальное масштабирование)
   └────┬────┘
    (db-net)
   ┌────┴────┐
   ▼         ▼
[Postgres] [Redis] (Изолированный слой данных)

    Блок 2. Анатомия современного compose.yaml

    Важное примечание по версиям: Старая утилита на Python docker-compose (через дефис) и строка version: "3.8" в начале файла официально устарели (deprecated). Современный стандарт — встроенный плагин docker compose (через пробел) и спецификация Compose Specification без указания version.

    2.1. Сети, порты, переменные окружения и тома данных

    • ports vs expose:
    • ports: ["8080:80"] — пробрасывает порт на хостовую машину (доступен снаружи сервера).
    • expose: ["8000"] — порт открыт только для других контейнеров внутри общей Docker-сети, снаружи хоста к нему подключиться нельзя (идеально для бэкендов и БД).
    • networks: Позволяет разделить сервисы на изолированные сегменты (frontend-net, backend-net). Флаг internal: true полностью запрещает сети выход во внешний интернет.
    • volumes: Управляет постоянными данными (pg_data:/var/lib/postgresql/data) и пробросом конфигураций (./nginx.conf:/etc/nginx/nginx.conf:ro).

    2.2. Переиспользование конфигураций (YAML Anchors & Extensions)

    В соответствии с принципом DRY (Don't Repeat Yourself), чтобы не копировать одинаковые блоки (логирование, лимиты ресурсов, политики перезапуска) в каждый из 10 сервисов, в Compose используют расширение x- и YAML-якоря (& и *):

    # Объявляем шаблон в секции x- (Docker Compose игнорирует секции, начинающиеся с x-)
x-common-defaults: &common-defaults
  restart: unless-stopped
  security_opt:
    - no-new-privileges:true
  logging:
    driver: "json-file"
    options:
      max-size: "10m"
      max-file: "3"

services:
  api:
    # Встраиваем все настройки из шаблона одной строчкой!
    <<: *common-defaults
    image: my-api:1.0.0

  worker:
    <<: *common-defaults
    image: my-worker:1.0.0

    2.3. Управление секретами и порядком запуска контейнеров (depends_on + healthcheck)

    Ловушка простого depends_on

    Многие новички пишут просто: 

    depends_on:
  - db
    В чем проблема? Обычный depends_on ждет только того момента, когда процесс контейнера db стартовал (это занимает 0.2 секунды). Но самой СУБД PostgreSQL внутри контейнера нужно еще 3–5 секунд, чтобы инициализировать таблицы и открыть порт 5432. В итоге бэкенд стартует мгновенно, пытается подключиться к еще не готовой БД и падает с ошибкой Connection refused!

    Правильное решение: condition: service_healthy

    Мы добавляем к базе данных проверку готовности (healthcheck через штатную утилиту pg_isready), а бэкенду приказываем ждать статуса healthy:

    services:
  db:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    build: .
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy

    Безопасная работа с secrets в Docker Compose

    Вместо того чтобы передавать пароль от БД через обычную переменную окружения (которую видно через docker inspect), в Compose используется блок secrets:. Docker монтирует файл с паролем в оперативную память (tmpfs) контейнера по пути /run/secrets/<имя_секрета>:

    secrets:
  db_password:
    file: ./secrets/db_password.txt

    Блок 3. Масштабирование сервисов и настройка L4/L7-балансировки через Nginx

    3.1. Разница между L4 и L7 балансировкой

    Nginx может работать как балансировщик на двух уровнях модели OSI:

    Характеристика L4-балансировка (Транспортный уровень) L7-балансировка (Прикладной уровень)
    Модуль в Nginx stream { ... } http { ... }
    С чем работает Сырые TCP/UDP-пакеты (знает только IP и порт). Понимает протокол HTTP/HTTPS, заголовки, куки, URI-пути (/api, /static).
    Возможности маршрутизации Просто пересылает TCP-соединение на один из серверов пула. Умная маршрутизация: /api/* $\rightarrow$ на Python, /images/* $\rightarrow$ в S3, проверка заголовков, сжатие gzip, кэширование.
    Где применяется Балансировка СУБД (PostgreSQL), брокеров (RabbitMQ), DNS, нестандартных TCP-протоколов. 95% веб-приложений, REST API, gRPC и микросервисов.

    3.2. Алгоритмы балансировки в блоке upstream (Nginx)

    Внутри блока upstream описывается пул бэкенд-серверов:

    1. Round Robin (По умолчанию): Запросы распределяются по очереди по кругу ($1 \rightarrow 2 \rightarrow 3 \rightarrow 1$).
    2. least_conn (Наименьшее число активных соединений) — лучший выбор для API: Новый запрос отправляется на тот инстанс бэкенда, который прямо сейчас обрабатывает меньше всего запросов (защищает от ситуации, когда одному воркеру досталось 3 «тяжелых» запроса подряд).
    3. ip_hash: Привязывает клиента по его IP-адресу к конкретному инстансу (Sticky Sessions).
    4. Веса (weight=3): Позволяет отдавать более мощному серверу больше трафика.

    3.3. Особенность масштабирования (--scale) в Docker Compose и динамический DNS в Nginx

    Если мы хотим запустить сразу 3 реплики нашего бэкенда командой: 

    docker compose up -d --scale backend=3
    ...то мы не можем прописать в backend жесткий проброс портов ports: ["8000:8000"], потому что второй и третий контейнеры не смогут занять уже занятый на хосте порт 8000!

    Вместо этого: 1. У сервиса backend мы оставляем только внутренний expose: ["8000"]. 2. Встроенный DNS-сервер Docker (127.0.0.11) при обращении к имени backend автоматически возвращает все 3 IP-адреса запущенных реплик (DNS Round-Robin)! 3. В конфиге nginx.conf мы указываем resolver 127.0.0.11 valid=5s;, чтобы Nginx каждые 5 секунд обновлял список живых контейнеров при масштабировании без перезапуска.

    Обязательные заголовки Reverse Proxy: Когда Nginx пересылает запрос бэкенду, для бэкенда источником пакета становится IP самого контейнера Nginx. Чтобы бэкенд знал реальный IP пользователя и протокол, передают заголовки: 

    proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

    🛠 Практический проект Модуля 4: Развёртывание многоконтейнерного приложения с балансировкой Nginx

    Мы соберем полноценный кластер из 6 контейнеров в двух изолированных сетях с использованием секретов, YAML-якорей, проверок здоровья и балансировки нагрузки: * 1x Nginx (входной L7/L4 балансировщик на порту 8080). * 3x реплики Backend API (Python/Flask + Gunicorn), которые пишут транзакции в PostgreSQL и кэшируют счетчик в Redis. * 1x PostgreSQL 16 (с инициализацией схемы и паролем из Docker Secrets). * 1x Redis 7 (кэш в памяти).

    Этап 1. Создание структуры проекта и файла секретов

    Создай чистую директорию проекта и безопасный файл с паролем от базы данных: 

    mkdir -p ~/compose-cluster/{app,nginx,secrets} && cd ~/compose-cluster

# Записываем секретный пароль для PostgreSQL (без переноса строки -n)
echo -n "SuperStrongPgSecret2026" > secrets/db_password.txt
chmod 600 secrets/db_password.txt

# Создаем файл несекретных переменных окружения (.env)
cat << 'EOF' > .env
POSTGRES_USER=app_admin
POSTGRES_DB=cluster_db
REDIS_HOST=redis
APP_PORT=8000
EOF

    Этап 2. Код микросервиса (с поддержкой Docker Secrets и PostgreSQL + Redis)

    1. Создай список зависимостей app/requirements.txt: 

      cat << 'EOF' > app/requirements.txt
flask==3.0.3
psycopg2-binary==2.9.9
redis==5.0.8
gunicorn==23.0.0
EOF

    2. Создай код приложения app/main.py (обрати внимание: приложение читает пароль базы из примонтированного секрета /run/secrets/db_password и возвращает ID своей реплики hostname, чтобы мы наглядно увидели работу балансировщика Nginx): 

      cat << 'EOF' > app/main.py
import os
import socket
import psycopg2
import redis
from flask import Flask, jsonify, request

app = Flask(__name__)

def get_db_password():
    secret_path = "/run/secrets/db_password"
    if os.path.exists(secret_path):
        with open(secret_path, "r") as f:
            return f.read().strip()
    return os.getenv("POSTGRES_PASSWORD", "")

def get_db_conn():
    return psycopg2.connect(
        host=os.getenv("DB_HOST", "db"),
        database=os.getenv("POSTGRES_DB", "cluster_db"),
        user=os.getenv("POSTGRES_USER", "app_admin"),
        password=get_db_password(),
        connect_timeout=3
    )

cache = redis.Redis(host=os.getenv("REDIS_HOST", "redis"), port=6379, decode_responses=True)

@app.route("/health")
def health():
    try:
        conn = get_db_conn()
        conn.close()
        cache.ping()
        return jsonify({"status": "healthy", "node": socket.gethostname()}), 200
    except Exception as e:
        return jsonify({"status": "unhealthy", "error": str(e)}), 500

@app.route("/api/visit")
def visit():
    client_ip = request.headers.get("X-Real-IP", request.remote_addr)
    node_id = socket.gethostname()

    # 1. Увеличиваем быстрый счетчик в Redis
    total_hits = cache.incr("cluster_hits")

    # 2. Записываем визит в таблицу PostgreSQL
    conn = get_db_conn()
    cur = conn.cursor()
    cur.execute("""
        CREATE TABLE IF NOT EXISTS visits (
            id SERIAL PRIMARY KEY,
            node_id VARCHAR(64),
            client_ip VARCHAR(64),
            visited_at TIMESTAMPTZ DEFAULT NOW()
        );
    """)
    cur.execute("INSERT INTO visits (node_id, client_ip) VALUES (%s, %s);", (node_id, client_ip))
    cur.execute("SELECT COUNT(*) FROM visits;")
    db_rows = cur.fetchone()[0]
    conn.commit()
    cur.close()
    conn.close()

    return jsonify({
        "served_by_replica": node_id,
        "client_real_ip": client_ip,
        "redis_hits": total_hits,
        "postgres_saved_rows": db_rows
    }), 200
EOF

    3. Создай оптимизированный app/Dockerfile: 

      cat << 'EOF' > app/Dockerfile
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
RUN groupadd -r appgroup && useradd -r -g appgroup -u 10001 appuser
COPY --from=builder /install /usr/local
COPY --chown=appuser:appgroup main.py .
USER 10001:10001
EXPOSE 8000
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
  CMD ["python3", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"]
ENTRYPOINT ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "main:app"]
EOF

    Этап 3. Конфигурация L7 и L4 балансировки в Nginx (nginx/nginx.conf)

    Создай конфигурационный файл nginx/nginx.conf, который включает: * L7-балансировку (http) по алгоритму least_conn между всеми репликами сервиса backend:8000 с автоматическим переключением при сбое (proxy_next_upstream). * L4-проксирование (stream) на TCP-уровне для демонстрации работы L4.

    cat << 'EOF' > nginx/nginx.conf
worker_processes auto;

events {
    worker_connections 1024;
}

# =====================================================
# Уровень L7 (HTTP): Умная балансировка веб-трафика
# =====================================================
http {
    include       /etc/nginx/mime.types;
    default_type  application/json;

    # Кастомный формат логов с указанием времени ответа и IP конкретного контейнера-апстрима!
    log_format upstream_log '$remote_addr - [$time_local] "$request" '
                            'status=$status upstream=$upstream_addr '
                            'resp_time=$request_time';
    access_log /var/log/nginx/access.log upstream_log;

    # Встроенный DNS-резолвер Docker для обнаружения новых реплик при масштабировании
    resolver 127.0.0.11 valid=5s ipv6=off;

    upstream backend_pool {
        zone backend_zone 64k;
        least_conn;
        # resolve позволяет динамически обновлять IP всех реплик контейнера backend
        server backend:8000 max_fails=3 fail_timeout=10s;
    }

    server {
        listen 80;
        server_name localhost;

        # Эндпоинт проверки самого Nginx
        location /nginx-health {
            return 200 '{"nginx": "ok"}\n';
        }

        location / {
            proxy_pass http://backend_pool;
            proxy_http_version 1.1;

            # Передача заголовков реального клиента
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # Отказоустойчивость: если одна реплика упала, прозрачно передать запрос следующей
            proxy_next_upstream error timeout http_500 http_502 http_503;
            proxy_connect_timeout 3s;
            proxy_read_timeout 10s;
        }
    }
}

# Уровень L4 (TCP Stream): Балансировка сырого TCP-порта
# =====================================================
stream {
    resolver 127.0.0.11 valid=5s ipv6=off;

    upstream tcp_backend_pool {
        least_conn;
        server backend:8000;
    }

    server {
        listen 9000;
        proxy_pass tcp_backend_pool;
        proxy_connect_timeout 2s;
    }
}
EOF

    Этап 4. Сборка эталонного compose.yaml

    Создай файл compose.yaml в корне ~/compose-cluster/, использующий переиспользование конфигов (x-defaults), разделение сетей (frontend-net и изолированную backend-net), Docker Secrets и строгий порядок запуска через service_healthy:

    cat << 'EOF' > compose.yaml
# --- Шаблон переиспользования конфигураций (DRY) ---
x-service-defaults: &service-defaults
  restart: unless-stopped
  security_opt:
    - no-new-privileges:true
  logging:
    driver: "json-file"
    options:
      max-size: "10m"
      max-file: "3"

services:
  # 1. Реляционная БД PostgreSQL (Stateful)
  db:
    <<: *service-defaults
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - pg_cluster_data:/var/lib/postgresql/data
    networks:
      - backend-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 5

  # 2. Кэш Redis (In-Memory)
  redis:
    <<: *service-defaults
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_cluster_data:/data
    networks:
      - backend-net
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  # 3. Масштабируемый Бэкенд-сервис (Stateless)
  backend:
    <<: *service-defaults
    build:
      context: ./app
    environment:
      DB_HOST: db
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_DB: ${POSTGRES_DB}
      REDIS_HOST: ${REDIS_HOST}
    secrets:
      - db_password
    expose:
      - "8000"
    networks:
      - frontend-net
      - backend-net
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy

  # 4. Балансировщик нагрузки и Reverse Proxy (Nginx)
  nginx:
    <<: *service-defaults
    image: nginx:1.27-alpine
    ports:
      - "8080:80"   # L7 HTTP-балансировщик
      - "9000:9000" # L4 TCP-балансировщик
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    networks:
      - frontend-net
    depends_on:
      backend:
        condition: service_healthy

networks:
  # Сеть между Nginx и бэкендами
  frontend-net:
    driver: bridge
  # Изолированная сеть для БД и кэша (Nginx сюда доступа НЕ имеет!)
  backend-net:
    driver: bridge

volumes:
  pg_cluster_data:
  redis_cluster_data:

secrets:
  db_password:
    file: ./secrets/db_password.txt
EOF

    Этап 5. Запуск и горизонтальное масштабирование кластера

    Собери и запусти стек сразу с 3 репликами бэкенд-сервиса: 

    docker compose up -d --build --scale backend=3

    Подожди 10–15 секунд, пока сработают проверки healthcheck, и посмотри статус всех 6 контейнеров: 

    docker compose ps

    ✅ Чек-лист самопроверки по Модулю 4

    1. Проверка распределения нагрузки (L7 Load Balancing): Выполни цикл из 6 запросов к балансировщику Nginx на порту 8080: 

      for i in {1..6}; do curl -s http://localhost:8080/api/visit; echo ""; done
      Ожидаемый результат: В поле "served_by_replica" ты увидишь 3 разных ID контейнеров (запросы равномерно распределяются по 3 репликам!), а счетчики "redis_hits" и "postgres_saved_rows" синхронно растут от 1 до 6!

    2. Проверка работы L4 TCP-балансировщика на порту 9000: 

      curl -s http://localhost:9000/health
      Ожидаемый результат: {"node":"...","status":"healthy"}.

    3. Проверка логов апстримов в Nginx: Посмотри, на какие внутренние IP контейнеров Nginx раскидывал твои запросы: 

      docker compose logs nginx | tail -n 6

    4. Тест на отказоустойчивость (Zero-Downtime Failover): Насильно убей одну из 3 реплик бэкенда и сразу же отправь запрос: 

      docker kill compose-cluster-backend-2
curl -s http://localhost:8080/api/visit
      Ожидаемый результат: Пользователь не заметил сбоя! Nginx мгновенно переключил трафик на две оставшиеся живые реплики, а Docker автоматически перезапустил убитый контейнер благодаря политике restart: unless-stopped.
