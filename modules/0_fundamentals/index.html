    Linux, сети и автоматизация на Bash

    Этот модуль закладывает системный фундамент. Без понимания того, как ядро управляет процессами, куда пишутся логи, почему порт закрыт фаерволом и как автоматизировать рутину на Bash, работа с Docker, Ansible и Kubernetes превращается в «гадание по YAML-файлам».

    Блок 1. Устройство и администрирование Linux

    1.1. Архитектура ОС: Kernel Space vs User Space

    Операционная система Linux разделена на два уровня привилегий:

    • Kernel Space (Пространство ядра): Имеет прямой доступ к железу (CPU, RAM, диски, сетевые карты). Управляет планировщиком процессов, виртуальной памятью и драйверами.
    • User Space (Пространство пользователя): Здесь работают все приложения (Nginx, Python, базы данных, ваш терминал). Приложения не могут напрямую обратиться к диску или сетевой карте — они делают это через системные вызовы (syscalls) к ядру (например, open(), read(), write(), fork(), socket()).

    1.2. Файловая система FHS (Filesystem Hierarchy Standard)

    В Linux действует принцип «Everything is a file» (всё есть файл: обычные файлы, директории, жесткие диски, сокеты, пайпы и даже информация о процессах).

    Директория Назначение в работе DevOps-инженера
    / Корневая директория (Root), начало всей иерархии.
    /bin, /sbin Базовые бинарные утилиты (ls, cp, bash) и системные утилиты администратора (iptables, fdisk). В современных ОС часто являются симлинками на /usr/bin и /usr/sbin.
    /etc Конфигурационные файлы всей системы и установленных сервисов (/etc/nginx/, /etc/ssh/sshd_config, /etc/hosts).
    /var Изменяемые данные (Variable): логи (/var/log), базы данных (/var/lib/postgresql), слои и тома Docker (/var/lib/docker). Чаще всего именно /var переполняется в продакшене.
    /proc Псевдофайловая система в RAM. Хранит информацию о текущих процессах и параметрах ядра в реальном времени (/proc/cpuinfo, /proc/meminfo, /proc/<PID>/).
    /sys Псевдофайловая система с информацией об оборудовании, драйверах и cgroups (/sys/fs/cgroup).
    /dev Файлы устройств: диски (/dev/sda, /dev/nvme0n1), псевдоустройства (/dev/null — «черная дыра», /dev/urandom — генератор случайных байт).
    /tmp Временные файлы. Очищается при перезагрузке.
    /opt Стороннее проприетарное или самописное ПО, не входящее в стандартные репозитории.
    /home, /root Домашние каталоги обычных пользователей и суперпользователя root.

    Иноды (Inodes) — классическая ловушка на сервере

    Каждый файл имеет две составляющие: блоки данных на диске и метаданные в структуре inode (владелец, права, размер, таймстемпы, указатели на блоки данных). Имя файла хранится в директории и просто ссылается на номер inode.

    Кейс из продакшена: Команда df -h показывает, что на диске свободно 40 ГБ, но сервер выдает ошибку No space left on device. Причина: миллионы мелких файлов (например, сессии PHP или мелкие логи) исчерпали таблицу инодов.

    Диагностика дисков и инодов:

    # Свободное место на примонтированных разделах в человекочитаемом виде
df -h

# Проверка использования инодов (Inodes)
df -i

# Размер конкретной папки и её подпапок (топ-10 самых тяжелых в /var)
sudo du -h --max-depth=1 /var | sort -hr | head -n 10

    1.3. Пользователи и права доступа (chmod, chown)

    Безопасность Linux строится на разграничении пользователей (UID) и групп (GID).

    • Конфигурация пользователей: /etc/passwd (имя, UID, GID, домашняя папка, оболочка shell). Для сервисных аккаунтов (например, nginx), которым не нужен интерактивный вход, ставят оболочку /usr/sbin/nologin или /bin/false.
    • Пароли (хэши): /etc/shadow.
    • Группы: /etc/group.

    Разбор строки прав доступа

    Выполнив ls -la, мы видим строку вида: -rwxr-xr-- 1 deploy www-data 4096 Oct 18 12:00 app.sh

    1. Первый символ — тип файла: - (обычный файл), d (директория), l (симлинк).
    2. Три триады прав:
    3. Первая (rwx) — для владельца (User / u).
    4. Вторая (r-x) — для группы (Group / g).
    5. Третья (r--) — для всех остальных (Others / o).

    Веса прав (восьмеричная система):

    • r (read — чтение) = 4
    • w (write — запись) = 2
    • x (execute — исполнение / вход в директорию) = 1
    • - (отсутствие прав) = 0

    Складывая числа для каждой триады, получаем стандартные комбинации:

    • 755 (rwxr-xr-x) — стандарт для исполняемых скриптов и публичных папок (владелец может всё, остальные — читать и запускать).
    • 644 (rw-r--r--) — стандарт для обычных конфигурационных файлов.
    • 600 (rw-------) — обязательный стандарт для приватных SSH-ключей и файлов с секретами (доступ только у владельца).

    Специальные биты:

    • SUID (4000): Файл запускается с правами его владельца, а не того, кто запустил (классический пример — /usr/bin/passwd, который должен менять /etc/shadow, принадлежащий root).
    • SGID (2000): На директории заставляет все новые файлы внутри наследовать группу этой директории (удобно для командной работы).
    • Sticky Bit (1000): На директории (например, /tmp с правами 1777) запрещает удалять чужие файлы, даже если у всех есть права на запись в папку.

    Команды управления:

    # Создать системного пользователя без права входа в шелл и с домашней папкой
sudo useradd -r -m -d /opt/myservice -s /usr/sbin/nologin myservice

# Изменить владельца и группу рекурсивно (-R)
sudo chown -R myservice:myservice /opt/myservice

# Выдать права 750 на директорию и 640 на конфиг
sudo chmod 750 /opt/myservice
sudo chmod 640 /opt/myservice/config.env

# Сделать скрипт исполняемым
chmod +x deploy.sh

    1.4. Диагностика процессов (ps, top/htop, сигналы)

    Каждый процесс имеет PID (Process ID) и родителя PPID (Parent PID).

    Состояния процессов (в выводе ps и top):

    • R (Running / Runnable): Выполняется на ядре CPU или ждет в очереди планировщика.
    • S (Interruptible Sleep): Спит в ожидании события (например, веб-сервер ждет сетевого пакета от клиента).
    • D (Uninterruptible Sleep): Ждет ответа от оборудования (чаще всего дискового ввода/вывода — Disk I/O). **Такой процесс нельзя убить даже через kill -9**, пока не завершится системный вызов к диску.
    • Z (Zombie): Процесс уже завершился, но его родитель еще не прочитал код его завершения (exit status) через вызов wait(). Ресурсов (RAM/CPU) не потребляет, занимает только строчку в таблице PID.
    • T (Stopped): Приостановлен сигналом (SIGSTOP или комбинацией Ctrl+Z).

    Показатель Load Average (LA)

    В top, htop или uptime отображаются 3 числа (например, Load average: 1.50, 0.80, 0.45) — средняя нагрузка за 1, 5 и 15 минут.

    • В Linux LA показывает среднее количество процессов в состояниях R (работают на CPU) и D (ждут диска).
    • Если у вас 4 ядра CPU, то LA = 4.00 означает, что система загружена ровно на 100%. Если LA = 12.00 на 4 ядрах — процессы стоят в трехкратной очереди (либо не хватает CPU, либо «умер» диск и процессы зависли в статусе D).

    Таблица сигналов ядра

    Номер Имя Описание и применение
    1 SIGHUP Перечитать конфигурационный файл без разрыва текущих соединений (например, nginx -s reload).
    2 SIGINT Прерывание с клавиатуры (Ctrl+C).
    9 SIGKILL Безусловное уничтожение процесса ядром. Не перехватывается приложением. Использовать только в крайнем случае.
    15 SIGTERM Стандартный сигнал остановки (по умолчанию в kill <PID>, systemctl stop, docker stop). Позволяет приложению сделать Graceful Shutdown (закрыть коннекты к БД, дописать файлы).

    Практические команды диагностики:

    # Топ-5 процессов по потреблению оперативной памяти (RAM)
ps aux --sort=-%mem | head -n 6

# Топ-5 процессов по нагрузке на процессор (CPU)
ps aux --sort=-%cpu | head -n 6

# Найти процесс по имени и вывести его PID
pgrep -a python3

# Посмотреть, какие файлы и сокеты держит открытыми процесс с PID 1234
sudo lsof -p 1234

# Найти удаленные файлы, которые всё еще удерживаются процессами (частая причина нехватки места!)
sudo lsof +L1

    1.5. Системные службы (systemd и journalctl)

    systemd — это главный менеджер системы (PID 1), который запускает сервисы параллельно, следит за их состоянием и собирает их логи.

    Куда класть юнит-файлы:

    • /lib/systemd/system/ — системные юниты, установленные пакетным менеджером (apt). Редактировать вручную не рекомендуется (перезапишутся при обновлении).
    • /etc/systemd/system/ — пользовательские юниты и переопределения (приоритет выше). Свои сервисы создаем только здесь.

    Шаблон production-ready юнита (/etc/systemd/system/myapp.service)

    [Unit]
Description=My Custom Backend Service
# Запускать только после поднятия сети
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
# Безопасность: никогда не запускаем приложения от root без крайней необходимости
User=myservice
Group=myservice
WorkingDirectory=/opt/myservice

# Переменные окружения из файла
EnvironmentFile=-/etc/default/myservice

# Команда запуска (обязательно абсолютный путь к бинарнику)
ExecStart=/usr/bin/python3 /opt/myservice/app.py

# Автоматический перезапуск при падении с паузой в 5 секунд
Restart=on-failure
RestartSec=5s

# Ограничение ресурсов (защита сервера от утечки памяти)
MemoryMax=512M
LimitNOFILE=65535

# Логирование в systemd journal
StandardOutput=journal
StandardError=journal
SyslogIdentifier=myapp

[Install]
WantedBy=multi-user.target

    Шпаргалка по systemctl и journalctl:

    # Перечитать конфигурацию после создания или изменения .service файла (ОБЯЗАТЕЛЬНО)
sudo systemctl daemon-reload

# Включить автозапуск при старте сервера и сразу запустить(--now)
sudo systemctl enable --now myapp.service

# Проверить статус, PID и последние строки логов
sudo systemctl status myapp.service

# Читать логи сервиса в реальном времени (аналог tail -f)
sudo journalctl -u myapp.service -f

# Показать только ошибки (уровень err и выше) за последний час
sudo journalctl -u myapp.service -p err --since "1 hour ago"

# Очистить старые логи журнала, оставив только последние 500 МБ
sudo journalctl --vacuum-size=500M

    Блок 2. Сети и сетевые протоколы

    2.1. Стек TCP/IP и модель OSI на практике

    Чтобы быстро находить, почему «сервис не открывается», проблему всегда изолируют снизу вверх по уровням:

    Уровень OSI Единица данных Протоколы / Технологии Инструменты отладки в Linux
    L1 (Физический) Биты Кабель, оптика, радиоканал ethtool, ip link (флаг LOWER_UP)
    L2 (Канальный) Кадры (Frames) Ethernet, MAC-адреса, ARP, VLAN ip neigh (ARP-таблица), bridge
    L3 (Сетевой) Пакеты (Packets) IP (IPv4/IPv6), ICMP, маршрутизация ip addr, ip route, ping, traceroute, mtr
    L4 (Транспортный) Сегменты / Датаграммы TCP (надежный), UDP (быстрый), порты ss, netstat, nc (netcat), tcpdump
    L7 (Прикладной) Данные (Payload) HTTP/HTTPS, DNS, SSH, TLS, gRPC curl, dig, openssl s_client

    Приватные диапазоны IPv4 (RFC 1918) и CIDR

    Внутри локальных сетей, Docker и облачных VPC используются три диапазона серых (приватных) адресов:

    • 10.0.0.0/8 (от 10.0.0.0 до 10.255.255.255) — часто используется в облаках и Kubernetes.
    • 172.16.0.0/12 (от 172.16.0.0 до 172.31.255.255) — по умолчанию используется для сетей Docker (172.17.0.0/16).
    • 192.168.0.0/16 (от 192.168.0.0 до 192.168.255.255) — домашние и офисные сети.
    • 127.0.0.0/8 (127.0.0.1) — Loopback (lo), трафик внутри самого хоста.

    Важное правило: Если веб-сервер слушает 127.0.0.1:8080, к нему нельзя подключиться снаружи по сети (даже если фаервол открыт). Чтобы принимать внешние подключения со всех сетевых карт, сервис должен слушать 0.0.0.0:8080 (или конкретный IP сетевого интерфейса).

    Трехэтапное рукопожатие TCP (3-Way Handshake)

    Перед передачей данных по TCP устанавливается соединение:

    1. Клиент $\rightarrow$ Сервер: SYN (Хочу подключиться).
    2. Сервер $\rightarrow$ Клиент: SYN-ACK (Слышу тебя, готов).
    3. Клиент $\rightarrow$ Сервер: ACK (Отлично, начинаем передачу).

    2.2. Маршрутизация и утилита ip (пакет iproute2)

    Утилита ifconfig устарела более 15 лет назад. Современный стандарт — ip.

    # Краткий вывод всех интерфейсов и их IP-адресов с подсветкой
ip -br -c addr show

# Просмотр таблицы маршрутизации
ip route show
# Пример вывода:
# default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.50 metric 100
# 192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.50

# Проверить, через какой интерфейс и шлюз пойдет пакет до конкретного IP (например, 8.8.8.8)
ip route get 8.8.8.8

# Посмотреть таблицу ARP (соответствие IP и MAC-адресов в локальной сети)
ip neigh show

    2.3. DNS: Разрешение доменных имен (dig)

    Когда приложение обращается к api.example.com, Linux ищет IP-адрес в следующем порядке (определяется в /etc/nsswitch.conf, строка hosts: files dns):

    1. Локальный файл /etc/hosts (жестко прописанные соответствия).
    2. Локальный кэширующий резолвер (systemd-resolved на 127.0.0.53) или DNS-серверы, указанные в /etc/resolv.conf.

    Диагностика DNS через dig:

    # Обычный запрос A-записи
dig example.com

# Вывести ТОЛЬКО IP-адрес (идеально для использования внутри Bash-скриптов)
dig +short example.com

# Запросить конкретный тип записи (TXT, MX, CNAME, NS) у конкретного DNS-сервера (@1.1.1.1)
dig @1.1.1.1 example.com TXT +short

# Полная трассировка делегирования от корневых серверов (.) до конечного NS
dig +trace example.com

# Обратный DNS-запрос (PTR) — узнать имя хоста по IP
dig -x 8.8.8.8 +short

    2.4. Порты, сокеты и отладка HTTP (ss, curl, nc)

    Сокет — это комбинация IP-адрес : Порт : Протокол.

    Анализ портов утилитой ss (Socket Statistics)

    Запоминаем главный флаг администратора — ss -tulpn:

    • -t — показать TCP-сокеты.
    • -u — показать UDP-сокеты.
    • -l — показать только слушающие порты (LISTEN).
    • -p — показать процесс и PID, который занял порт (требует sudo).
    • -n — не переводить номера портов в имена (писать :80 вместо :http, работает мгновенно).
    # Кто слушает порты на сервере прямо сейчас?
sudo ss -tulpn

# Показать все установленные (активные) TCP-соединения
ss -tan state established

    Диагностика с помощью curl и nc (Netcat)

    # Проверить только HTTP-заголовки ответа (-I)
curl -I https://ya.ru

# Подробный режим (-v): покажет DNS-резолв, TCP-хендшейк, детали TLS-сертификата и заголовки
curl -v https://example.com > /dev/null

# Отправить POST-запрос с JSON-телом и кастомным заголовком
curl -X POST http://localhost:8080/api/v1/items \
     -H "Content-Type: application/json" \
     -d '{"name": "server-01", "role": "worker"}'

# Вывести только HTTP-код ответа (полезно для проверок в CI/CD и скриптах)
curl -s -o /dev/null -w "%{http_code}\n" https://example.com

# Проверить, открыт ли TCP-порт 5432 (PostgreSQL) на удаленном хосте с таймаутом 3 секунды
nc -zv -w 3 192.168.1.50 5432

    2.5. Перехват трафика (tcpdump) и фаервол (iptables / nftables / ufw)

    Перехват пакетов через tcpdump

    Когда логи пусты, а сервис не работает, tcpdump показывает реальную картину на сетевой карте.

    # Слушать интерфейс eth0, только TCP-порт 80, не резолвить имена (-nn)
sudo tcpdump -i eth0 -nn tcp port 80

# Слушать на всех интерфейсах (-i any) пинги (ICMP) от конкретного хоста
sudo tcpdump -i any -nn icmp and host 8.8.8.8

# Записать дамп трафика в файл для последующего визуального анализа в Wireshark
sudo tcpdump -i eth0 -nn port 443 -w capture.pcap

    Межсетевой экран: Netfilter (iptables, nftables, ufw)

    В ядре Linux встроен фреймворк Netfilter. iptables и более современный nftables — это консольные утилиты для управления правилами этого фреймворка.

    Базовые концепции iptables:

    • Таблицы (Tables):
    • filter (по умолчанию) — разрешать или блокировать пакеты.

    • nat — подмена адресов и проброс портов (именно здесь Docker прописывает правила проброса портов контейнеров!).

    • Цепочки (Chains):

    • INPUT — пакеты, адресованные самому нашему серверу.
    • OUTPUT — пакеты, исходящие от нашего сервера.

    • FORWARD — транзитные пакеты, проходящие сквозь сервер (например, в сеть Docker-контейнеров).

    • Действия (Targets):

    • ACCEPT — пропустить пакет.
    • DROP — молча уничтожить пакет (отправитель будет ждать до истечения таймаута).
    • REJECT — отбросить пакет и вежливо отправить в ответ сообщение «Порт закрыт» (ICMP Port Unreachable / TCP RST).
    # Посмотреть текущие правила таблицы filter с номерами строк и счетчиками пакетов
sudo iptables -L -v -n --line-numbers

# Посмотреть правила NAT (увидеть, как Docker пробрасывает порты)
sudo iptables -t nat -L -n -v

    На серверах Ubuntu для управления хостовым фаерволом используют удобную обертку ufw (Uncomplicated Firewall):

    # 1. По умолчанию запретить все входящие и разрешить все исходящие
sudo ufw default deny incoming
sudo ufw default allow outgoing

# 2. ОБЯЗАТЕЛЬНО сначала разрешить SSH, чтобы не отрезать себе доступ!
sudo ufw allow 22/tcp

# 3. Открыть веб-порты HTTP и HTTPS
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# 4. Включить фаервол и проверить статус
sudo ufw enable
sudo ufw status numbered

    Блок 3. Программирование и автоматизация на Bash

    3.1. Потоки ввода/вывода, пайпы и коды возврата

    Каждая команда возвращает Exit Code (код возврата от 0 до 255), который сохраняется в переменную $?:

    • 0 — успешное выполнение.
    • 1..255 — ошибка (например, 127 — команда не найдена, 126 — нет прав на исполнение).

    Операторы перенаправления и связки:

    • cmd1 | cmd2 (Pipe / Конвейер) — передает stdout первой команды на stdin второй.
    • cmd1 && cmd2 — выполнит cmd2 только если cmd1 завершилась успешно (код 0).
    • cmd1 || cmd2 — выполнит cmd2 только если cmd1 завершилась с ошибкой (код $\neq 0$).
    • > file — перезаписать файл выводом stdout.
    • >> file — дописать в конец файла.
    • 2> error.log — перенаправить только поток ошибок stderr.
    • > all.log 2>&1 (или &> all.log) — направить и stdout, и stderr в одно место.
    • 2> /dev/null — скрыть ошибки (отправить в «черную дыру»).

    3.2. Золотой стандарт надежного Bash-скрипта (Safe Bash)

    По умолчанию Bash продолжает выполнять скрипт даже тогда, когда одна из команд внутри упала с ошибкой или переменная оказалась пустой.

    Страшный пример: Если переменная $ APP_DIR не задана, команда rm -rf $APP_DIR/* превратится в rm -rf /*!

    Чтобы этого никогда не произошло, любой профессиональный скрипт начинается с заголовка set -euo pipefail:

    #!/usr/bin/env bash
set -euo pipefail
    • -e (errexit): Немедленно прервать скрипт, если любая команда вернула ненулевой код ошибки.
    • -u (nounset): Прервать скрипт при попытке обратиться к необъявленной переменной.
    • -o pipefail: Если в цепочке с пайпом (cmd1 | cmd2 | cmd3) упала любая промежуточная команда, весь конвейер считается упавшим (без этого флага Bash смотрит только на код последней команды).

    3.3. Переменные, условия, циклы и функции

    Разница кавычек и подстановка

    • 'Одинарные кавычки' — строгий литерал, внутри ничего не вычисляется (echo '$USER' выведет текст $USER).
    • "Двойные кавычки" — вычисляют переменные и подстановки (echo "Привет, $USER" выведет Привет, root). Всегда оборачивайте переменные в двойные кавычки ("$VAR"), чтобы пробелы в именах файлов не ломали скрипт.
    • $(команда) — выполнить команду и подставить её результат (например, CURRENT_DATE="$(date +%F)").

    Шпаргалка по условиям [[ ... ]]

    В современном Bash используют двойные квадратные скобки [[ ... ]] — они безопаснее одинарных [ ... ].

    Проверка файлов Проверка строк Проверка чисел
    [[ -f "$file" ]] — файл существует [[ -z "$str" ]] — строка пустая [[ "$a" -eq "$b" ]] — равно ($=$)
    [[ -d "$dir" ]] — директория существует [[ -n "$str" ]] — строка НЕ пустая [[ "$a" -ne "$b" ]] — не равно ($\neq$)
    [[ -r "$file" ]] — доступен для чтения [[ "$a" == "$b" ]] — строки равны [[ "$a" -gt "$b" ]] — больше ($>$)
    [[ -x "$file" ]] — файл исполняемый [[ "$a" != "$b" ]] — строки не равны [[ "$a" -lt "$b" ]] — меньше ($<$)

    Пример конструкции if, цикла for, while и функций

    #!/usr/bin/env bash
set -euo pipefail

# Позиционные аргументы: $1 - первый аргумент, ${1:-default} - значение по умолчанию
TARGET_ENV="${1:-staging}"
SERVICES=("nginx" "postgresql" "redis")

log_info() {
    local msg="$1"
    echo "[$(date +'%Y-%m-%d %H:%M:%S')] [INFO] ${msg}"
}

# Условие
if [[ "$TARGET_ENV" == "production" ]]; then
    log_info "Внимание! Работаем в PRODUCTION окружении."
else
    log_info "Тестовое окружение: ${TARGET_ENV}"
fi

# Цикл по массиву
for svc in "${SERVICES[@]}"; do
    if systemctl is-active --quiet "$svc"; then
        log_info "Сервис ${svc} работает штатно."
    else
        log_info "Сервис ${svc} ОСТАНОВЛЕН!"
    fi
done

# Безопасное построчное чтение файла через while
while IFS= read -r line; do
    echo "Прочитана строка: $line"
done < /etc/hosts

    3.4. Текстовый конвейер: grep, sed, awk

    Три кита парсинга логов и конфигураций в консоли.

    1. grep — поиск и фильтрация строк по регулярным выражениям

    # Найти слово ERROR (без учета регистра -i) с номерами строк (-n)
grep -in "error" /var/log/syslog

# Вывести только активные директивы конфига (исключить -v пустые строки ^$ и комментарии ^#)
grep -Ev '^\s*#|^\s*$' /etc/ssh/sshd_config

# Рекурсивно (-r) найти все файлы в /etc, где упоминается порт 8080
sudo grep -rnw '/etc/' -e '8080'

    2. sed — потоковый редактор (замена и удаление текста на лету)

    # Заменить слово "http" на "https" во всем файле и вывести на экран (флаг g - все вхождения в строке)
sed 's/http/https/g' config.txt

# Заменить значение прямо внутри файла (-i) с созданием резервной копии config.txt.bak (-i.bak)
sed -i.bak 's/PermitRootLogin yes/PermitRootLogin no/g' sshd_config

# Если в строке есть слэши (пути), в качестве разделителя вместо / можно использовать | или #
sed 's|/var/www/html|/opt/app/public|g' nginx.conf

# Удалить все пустые строки из файла
sed '/^$/d' file.txt

    3. awk — работа со столбцами и аналитика

    По умолчанию awk делит каждую строку на колонки по пробелам/табуляции: $1 — первая колонка, $2 — вторая, $NF — последняя колонка, $0 — вся строка целиком. Флаг -F задает свой разделитель.

    # Вывести первого пользователя и его shell из /etc/passwd (разделитель двоеточие)
awk -F':' '{print "User: " $1 " | Shell: " $7}' /etc/passwd

# Отфильтровать строки, где 9-я колонка (HTTP-код в логе Nginx) равна 500, и вывести IP ($1) и URL ($7)
awk '$9 == 500 {print $1, $7}' access.log

# Топ-10 IP-адресов, с которых идет больше всего запросов (классика отладки DDoS)
awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10

    Блок 4. Виртуализация и основы изоляции

    4.1. Классификация гипервизоров и контейнеров

    Чтобы понимать разницу между облачной ВМ и Docker-контейнером, разберем, как они делят ресурсы физического сервера (Host):

    Характеристика Гипервизор Type 1 (Bare-Metal) Гипервизор Type 2 (Hosted) Контейнеризация (OS-level)
    Примеры KVM, VMware ESXi, Xen, Hyper-V VirtualBox, VMware Workstation Docker, containerd, LXC
    Как работает Работает напрямую на железе (KVM встроен прямо в ядро Linux). Запускается как обычная программа поверх хостовой ОС (Windows/macOS). Процессы работают на общем ядре хоста, изолированные через namespaces и cgroups.
    Свое ядро ОС? Да (у каждой ВМ свое ядро и своя гостевая ОС). Да (полная гостевая ОС). Нет (используется ядро хоста).
    Время старта 15–60 секунд. 20–90 секунд. Доли секунды (как обычный процесс).
    Накладные расходы Низкие / Средние (требуется выделенная RAM под гостевую ОС). Высокие. Минимальные (почти равны нативному процессу).
    Изоляция Максимальная (аппаратная: Intel VT-x / AMD-V). Высокая. Логическая (на уровне ядра ОС).

    4.2. Связка KVM + QEMU + libvirt (основа всех облаков)

    Когда вы создаете виртуальную машину в Yandex Cloud, AWS или Proxmox, под капотом почти всегда работает связка:

    1. KVM (Kernel-based Virtual Machine): Модуль ядра Linux, который превращает само ядро в гипервизор Type 1, используя аппаратные расширения процессора (Intel VT-x или AMD-V).
    2. QEMU (Quick Emulator): Эмулирует периферийное железо для виртуальной машины (сетевые карты, контроллеры дисков, видеокарту). В паре с KVM выполняет код процессора напрямую без эмуляции.
    3. libvirt (virsh): Удобный API и демон для управления жизненным циклом виртуальных машин.

    4.3. Основы изоляции в ядре Linux (предвестник Docker)

    Контейнер — это не «легковесная виртуальная машина». Это обычный процесс Linux, которому ядро ограничило видимость и ресурсы с помощью трех механизмов:

    1. Namespaces (Пространства имен) — отвечают за то, ЧТО процесс ВИДИТ:
    2. pid — у процесса внутри свой PID 1, он не видит процессы хоста.
    3. net — свой изолированный сетевой стек (свои интерфейсы, IP, таблица маршрутизации и порты).
    4. mnt — своя точка монтирования файловой системы.
    5. uts — свое имя хоста (hostname).

    6. ipc и user — изоляция межпроцессного взаимодействия и ID пользователей.

    7. cgroups (Control Groups) — отвечают за то, СКОЛЬКО ресурсов процесс может ПОТРЕБЛЯТЬ:

    8. Ограничивают лимиты CPU, оперативной памяти (если процесс превысит лимит cgroup по RAM, в дело вступит OOM Killer и убьет его сигналом SIGKILL), дискового I/O и числа процессов.

    9. chroot / pivot_root: Переносит корневую директорию / процесса в отдельную подпапку на диске, чтобы он не имел доступа к файловой системе хоста.

# Создаем папку .ssh и кладем туда наш публичный ключ

    Этап 3. Разработка демона аудита сервера (sys-auditor) и упаковка в systemd

    Мы напишем Bash-скрипт, который контролирует здоровье сервера (диск, RAM, сеть, порты) и оформлен как полноценный системный сервис.

    1. Создай скрипт /usr/local/bin/sys-auditor.sh:

    sudo tee /usr/local/bin/sys-auditor.sh > /dev/null << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

LOG_FILE="/var/log/sys-auditor.log"
DISK_THRESHOLD=85
CHECK_URL="https://ya.ru"

log_msg() {
    local level="$1"
    local message="$2"
    local timestamp
    timestamp="$(date +'%Y-%m-%d %H:%M:%S')"
    echo "[${timestamp}] [${level}] ${message}" | tee -a "$LOG_FILE"
}

check_disk() {
    # Получаем процент заполнения корневого раздела / без знака %
    local usage
    usage="$(df -P / | awk 'NR==2 {gsub(/%/,"",$5); print $5}')"
    if [[ "$usage" -ge "$DISK_THRESHOLD" ]]; then
        log_msg "WARN" "Root disk usage is critical: ${usage}% (Threshold: ${DISK_THRESHOLD}%)"
    else
        log_msg "INFO" "Root disk usage OK: ${usage}%"
    fi
}

check_memory() {
    # Считаем доступную память в МБ из /proc/meminfo
    local mem_avail_mb
    mem_avail_mb="$(awk '/MemAvailable/ {printf "%d", $2/1024}' /proc/meminfo)"
    log_msg "INFO" "Available RAM: ${mem_avail_mb} MB"
}

check_network() {
    local http_code
    http_code="$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 "$CHECK_URL" || echo "000")"
    if [[ "$http_code" =~ ^(200|301|302)$ ]]; then
        log_msg "INFO" "Network connectivity to ${CHECK_URL} OK (HTTP ${http_code})"
    else
        log_msg "ERROR" "Network check failed for ${CHECK_URL} (HTTP ${http_code})"
    fi
}

check_listening_ports() {
    local port_count
    port_count="$(ss -tln | awk 'NR>1 {count++} END {print count+0}')"
    log_msg "INFO" "Active listening TCP sockets: ${port_count}"
}

main() {
    log_msg "INFO" "=== Starting System Audit Daemon ==="
    while true; do
        check_disk
        check_memory
        check_network
        check_listening_ports
        sleep 60
    done
}

main "$@"
EOF

# Делаем скрипт исполняемым
sudo chmod 755 /usr/local/bin/sys-auditor.sh

    2. Создай systemd-юнит /etc/systemd/system/sys-auditor.service:

    sudo tee /etc/systemd/system/sys-auditor.service > /dev/null << 'EOF'
[Unit]
Description=System Health Auditor Service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=root
ExecStart=/usr/local/bin/sys-auditor.sh
Restart=always
RestartSec=10s
StandardOutput=journal
StandardError=journal
SyslogIdentifier=sys-auditor

[Install]
WantedBy=multi-user.target
EOF

    3. Настрой ротацию логов /etc/logrotate.d/sys-auditor (чтобы лог не забил диск):

    sudo tee /etc/logrotate.d/sys-auditor > /dev/null << 'EOF'
/var/log/sys-auditor.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0640 root adm
}
EOF

    4. Запусти и протестируй сервис:

    sudo systemctl daemon-reload
sudo systemctl enable --now sys-auditor.service

    ✅ Чек-лист самопроверки по Модулю 0

    Проверь, что все 4 команды возвращают корректный результат:

    1. Статус сервиса active (running): 

      sudo systemctl status sys-auditor.service

    2. Логи пишутся и в журнал systemd, и в файл /var/log/sys-auditor.log: 

      sudo journalctl -u sys-auditor -n 10 --no-pager
cat /var/log/sys-auditor.log

    3. Проверь самовосстановление сервиса (Restart=always): найди PID процесса и убей его через kill -9, а через 12 секунд проверь, что systemd поднял его заново с новым PID: 

      sudo pkill -9 -f sys-auditor.sh
sleep 12
systemctl status sys-auditor.service
