    Наблюдаемость Observability и мониторинг

    Поднять многоконтейнерный кластер — это только половина дела. Если сервис тормозит или возвращает ошибки 500 в 3 часа ночи, инженер не должен узнавать об этом от разгневанных пользователей.

    В этом модуле мы разберем разницу между классическим мониторингом и наблюдаемостью (Observability), изучим сбор метрик в Prometheus, централизованный сбор логов в Grafana Loki, построение дашбордов в Grafana и настройку автоматических уведомлений о сбоях через Alertmanager.

    Блок 1. Основы мониторинга и наблюдаемости (Observability)

    1.1. Мониторинг против Наблюдаемости

    • Мониторинг (Monitoring): Отвечает на вопрос «Работает ли система?» по заранее известным порогам (например: «Диск заполнен на 90%» или «Сервер не отвечает на ping»).
    • Наблюдаемость (Observability): Свойство системы, позволяющее ответить на вопрос «ПОЧЕМУ она сломалась или тормозит?», исследуя её внутреннее состояние по внешним данным без выпуска нового кода.

    Три столпа наблюдаемости (Three Pillars of Observability):

    1. Метрики (Metrics — Что происходит?): Числовые показатели во времени (временные ряды / Time Series). Занимают мало места, идеальны для графиков и триггеров алертов (инструмент: Prometheus).
    2. Логи (Logs — Почему это произошло?): Детальные текстовые или JSON-записи о конкретных событиях с временной меткой (инструменты: Grafana Loki, ELK).
    3. Трейсы (Traces — Где именно застрял запрос?): Цепочка прохождения одного пользовательского запроса через десяток микросервисов и баз данных (инструменты: Jaeger, OpenTelemetry, Grafana Tempo).

    1.2. Методологии мониторинга: USE, RED и 4 золотых сигнала SRE

    Чтобы не мониторить тысячи бесполезных графиков, индустрия выработала две четкие формулы:

    Методология Для чего применяется Расшифровка показателей
    Метод USE (Брендан Грегг) Для «железа» и инфраструктуры (CPU, RAM, диски, сеть хоста) 1. Utilization (Утилизация): процент занятости ресурса (например, CPU 85%).
    2. Saturation (Насыщение): длина очереди ожидания ресурса (например, Load Average или очередь к диску).
    3. Errors (Ошибки): количество аппаратных/сетевых ошибок (dropped packets, disk read errors).
    Метод RED (Том Уилки) Для микросервисов и API (HTTP/gRPC трафик) 1. Rate (Частота): количество запросов в секунду (RPS).
    2. Errors (Ошибки): количество запросов в секунду, завершившихся ошибкой (HTTP 5xx).
    3. Duration (Длительность): время ответа сервиса (Latency — обычно смотрят 95-й и 99-й перцентили).

    Почему среднее время ответа (Average Latency) врет? Если 99 запросов выполнились за 10 мс, а 1 запрос завис на 10 секунд ($10\,000\text{ мс}$), среднее арифметическое составит всего ~110 мс — на графике всё будет выглядеть отлично! Поэтому в DevOps всегда используют перцентили (квантили): например, $p95 = 250\text{ мс}$ означает, что 95% пользователей получили ответ быстрее чем за $250\text{ мс}$, а 5% самых медленных запросов превысили этот порог.

    Блок 2. Сбор метрик через Prometheus

    2.1. Архитектура Prometheus и Pull-модель

    В отличие от старых систем (где агенты сами пушили данные на сервер), Prometheus работает по Pull-модели: он сам по расписанию (scrape_interval, обычно каждые 15 секунд) ходит по HTTP на заданные адреса (targets) по пути /metrics и забирает текстовый слепок метрик.

    Откуда берутся метрики? 1. Прикладные метрики (Instrumentation): Наше приложение на Python/Go/Java подключает клиентскую библиотеку Prometheus и само отдает свои бизнес-метрики на /metrics. 2. Экспортеры (Exporters): Для сервисов, которые не умеют отдавать метрики в формате Prometheus natively, рядом запускается маленький агент-переводчик: * node-exporter — собирает метрики самого Linux-сервера (CPU, RAM, Disk, Network). * cAdvisor — собирает метрики всех запущенных Docker-контейнеров. * postgres-exporter / redis-exporter / nginx-exporter — переводят внутреннюю статистику БД и веб-сервера в формат Prometheus.

    2.2. Четыре типа метрик в Prometheus

    Каждая метрика в Prometheus — это имя + набор меток (labels в фигурных скобках) + числовое значение: http_requests_total{method="GET", path="/api/visit", status="200"} 1452

    1. Counter (Счетчик): Монотонно растущее число, которое может только увеличиваться (и сбрасываться в 0 при перезапуске процесса). Примеры: общее число запросов http_requests_total, общее число ошибок.
    2. Gauge (Датчик / Шкала): Число, которое может как расти, так и уменьшаться. Примеры: текущая температура CPU, объем свободной памяти RAM, число активных соединений в моменте.
    3. Histogram (Гистограмма): Распределяет величины (например, время ответа запроса) по заранее заданным «корзинам» (buckets: le="0.05", le="0.1", le="0.5"...). Позволяет считать 95-й и 99-й перцентили времени ответа на стороне сервера Prometheus.
    4. Summary: Похожа на гистограмму, но вычисляет квантили прямо на стороне приложения (нельзя агрегировать между несколькими репликами сервиса).

    2.3. Основы языка запросов PromQL

    Чтобы построить график в Grafana или написать правило алерта, используют язык PromQL:

    # 1. Текущее значение свободной памяти (Gauge) в гигабайтах
node_memory_MemAvailable_bytes / 1024 / 1024 / 1024

# 2. Функция rate() — главный инструмент для Counter!
# Вычисляет скорость роста счетчика в секунду (RPS) за последние 1 минуту [1m]:
rate(http_requests_total[1m])

# 3. Агрегация sum() by () — сумма RPS по всем репликам с группировкой по HTTP-статусу:
sum by (status) (rate(http_requests_total[1m]))

# 4. Доля ошибок 5xx в процентах от общего трафика (Error Rate по методу RED):
sum(rate(http_requests_total{status=~"5.."}[1m])) 
/ 
sum(rate(http_requests_total[1m])) * 100

# 5. Вычисление 95-го перцентиля времени ответа по гистограмме (Duration по методу RED):
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

    Блок 3. Обработка логов и их передача в Grafana Loki

    3.1. Почему Loki, а не тяжелый ELK (Elasticsearch)?

    Классический стек ELK (Elasticsearch + Logstash + Kibana) индексирует каждое слово в каждом логе. Из-за этого кластер Elasticsearch под логи потребляет десятки гигабайт оперативной памяти и сотни гигабайт диска.

    Grafana Loki спроектирована по принципу «Like Prometheus, but for logs»: * Loki не индексирует текст лога! Она индексирует только компактный набор метаданных — меток (labels): например, {job="docker", service="backend", env="prod"}. * Сами текстовые строки сжимаются и сохраняются дешевыми блоками (в локальную папку или S3). Благодаря этому Loki потребляет в 10 раз меньше RAM, чем Elasticsearch!

    3.2. Архитектура доставки логов: Docker -> Promtail -> Loki -> Grafana

    1. Приложение пишет логи в стандартный поток вывода (stdout / stderr).
    2. Демон Docker сохраняет их в JSON-файлы в /var/lib/docker/containers/<ID>/<ID>-json.log.
    3. Агент Promtail (или Alloy / Vector) читает эти файлы, автоматически обогащает их метками из Docker Socket (имя контейнера, имя сервиса Compose) и отправляет по HTTP в Loki.
    4. Инженер читает и фильтрует логи в Grafana с помощью языка запросов LogQL.

    Примеры запросов на языке LogQL:

    # 1. Показать все логи контейнеров сервиса backend
{service="backend"}

# 2. Отфильтровать строки, содержащие слово "ERROR", и исключить проверки "/health"
{service="backend"} |= "ERROR" != "/health"

# 3. Распарсить JSON-лог на лету и найти запросы, которые выполнялись дольше 0.5 сек
{service="backend"} | json | duration > 0.5

# 4. Превратить логи в числовую метрику: количество ошибок в секунду за 1 минуту!
rate({service="backend"} |= "ERROR" [1m])

    Блок 4. Визуализация в Grafana и алертинг в Alertmanager

    4.1. Дашборды в Grafana

    Grafana — это единое окно визуализации, которое подключается одновременно к Data Source Prometheus (для графиков метрик) и к Data Source Loki (для просмотра логов). * Увидев всплеск ошибок 500 на графике Prometheus в 14:05, инженер в один клик нажимает Split View, открывает логи Loki ровно за 14:05 и сразу видит текст исключения Python/Postgres! * Все настройки источников данных (datasources) и сами дашборды (в формате JSON) в DevOps принято подключать декларативно через механизм Provisioning (чтобы при старте контейнера Grafana всё уже было настроено без ручных кликов мышкой).

    4.2. Реализация алертинга: Prometheus Rules + Alertmanager

    Алертинг разделен на две части: 1. Prometheus (Генератор тревоги): Каждые 15 секунд проверяет правила (alert_rules.yml). Если условие выполняется дольше заданного времени (секция for: 1m, чтобы не дергать дежурного из-за секундного скачка), алерт переходит из статуса Pending в статус Firing и отправляется в Alertmanager. 2. Alertmanager (Диспетчер уведомлений): Принимает алерты от Prometheus и отвечает за умную доставку: * Grouping (Группировка): Если на сервере упала база и 10 микросервисов одновременно выдали ошибки, Alertmanager склеит их в одно компактное сообщение в Telegram/Slack, а не пришлет 100 отдельных СМС. * Inhibition (Подавление): Если недоступен весь физический сервер, подавить мелкие алерты о сервисах внутри него. * Silences (Заглушки): Временное отключение уведомлений на время плановых технических работ.

    🛠 Практический проект Модуля 5: Построение полной системы наблюдаемости

    Мы возьмем наш микросервисный стек и развернем полноценную Production-grade систему наблюдаемости из 9 компонентов: 1. Бэкенд-сервис (Python/Flask) — добавим генерацию реальных метрик Prometheus (RED: счетчик запросов, гистограмма времени ответа, датчик ошибок) и структурированных JSON-логов. 2. PostgreSQL + Redis + Nginx — рабочее ядро приложения. 3. Node Exporter — сбор системных метрик самого Linux-хоста (CPU, RAM, Disk). 4. Prometheus — сбор всех метрик и вычисление правил тревоги (alert_rules.yml). 5. Alertmanager + Webhook Receiver — перехват и доставка алертов. 6. Loki + Promtail — автоматический сбор логов со всех контейнеров Docker с привязкой к именам сервисов. 7. Grafana — с автоматическим Provisioning источников данных Prometheus и Loki со старта!

    Этап 1. Подготовка директорий и инструментация микросервиса

    Создадим проект ~/observability-stack с папками под конфигурации всех систем мониторинга:

    mkdir -p ~/observability-stack/{app,prometheus,alertmanager,loki,promtail,grafana/provisioning/datasources}
cd ~/observability-stack

    1. Создай app/requirements.txt с библиотекой prometheus-client: 

      cat << 'EOF' > app/requirements.txt
flask==3.0.3
prometheus-client==0.20.0
gunicorn==23.0.0
EOF

    2. Создай код приложения app/main.py (сервис отдает метрики на /metrics, пишет структурированные JSON-логи в stdout и имеет специальный эндпоинт /api/fail, чтобы мы могли искусственно вызвать каскад ошибок 500 и проверить срабатывание боевого алерта!): 

      cat << 'EOF' > app/main.py
import os
import time
import json
import random
import socket
import logging
from flask import Flask, jsonify, request, Response
from prometheus_client import Counter, Histogram, Gauge, generate_latest, CONTENT_TYPE_LATEST

# Настраиваем вывод чистых JSON-логов в stdout для Promtail/Loki
logging.basicConfig(level=logging.INFO, format='%(message)s')
logger = logging.getLogger("backend")

def log_json(level, msg, **kwargs):
    payload = {
        "timestamp": time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime()),
        "level": level,
        "service": "backend-api",
        "node": socket.gethostname(),
        "message": msg,
        **kwargs
    }
    logger.info(json.dumps(payload))

app = Flask(__name__)

# --- Метрики Prometheus (Метод RED) ---
REQUEST_COUNT = Counter(
    "http_requests_total",
    "Total HTTP requests count",
    ["method", "endpoint", "status"]
)
REQUEST_LATENCY = Histogram(
    "http_request_duration_seconds",
    "HTTP request latency in seconds",
    ["endpoint"],
    buckets=[0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5]
)
ACTIVE_REQUESTS = Gauge(
    "http_active_requests",
    "Currently active HTTP requests"
)

@app.route("/metrics")
def metrics():
    return Response(generate_latest(), mimetype=CONTENT_TYPE_LATEST)

@app.route("/health")
def health():
    return jsonify({"status": "healthy"}), 200

@app.route("/api/order")
def order():
    ACTIVE_REQUESTS.inc()
    start_time = time.time()
    # Симулируем рабочую задержку от 20 до 150 мс
    delay = random.uniform(0.02, 0.15)
    time.sleep(delay)
    duration = time.time() - start_time

    REQUEST_COUNT.labels(method="GET", endpoint="/api/order", status="200").inc()
    REQUEST_LATENCY.labels(endpoint="/api/order").observe(duration)
    ACTIVE_REQUESTS.dec()

    log_json("INFO", "Order processed successfully", endpoint="/api/order", status=200, duration_sec=round(duration, 4))
    return jsonify({"status": "ok", "duration_sec": round(duration, 4)}), 200

@app.route("/api/fail")
def fail():
    start_time = time.time()
    time.sleep(0.05)
    duration = time.time() - start_time

    REQUEST_COUNT.labels(method="GET", endpoint="/api/fail", status="500").inc()
    REQUEST_LATENCY.labels(endpoint="/api/fail").observe(duration)

    log_json("ERROR", "Database transaction deadlock detected!", endpoint="/api/fail", status=500, error_code="DB_DEADLOCK")
    return jsonify({"error": "Internal Server Error"}), 500
EOF

    3. Создай app/Dockerfile: 

      cat << 'EOF' > app/Dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt && \
    useradd -r -u 10001 appuser
COPY main.py .
USER 10001
EXPOSE 8000
ENTRYPOINT ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "1", "main:app"]
EOF

    Этап 2. Конфигурация Prometheus и правил алертинга (alert_rules.yml)

    1. Создай правила алертинга prometheus/alert_rules.yml (два боевых алерта: на падение любого сервиса InstanceDown и на всплеск ошибок HighErrorRate при появлении HTTP 500): 

      cat << 'EOF' > prometheus/alert_rules.yml
groups:
  - name: devops_service_alerts
    interval: 10s
    rules:
      # Алерт 1: Любой сервис перестал отдавать метрики
      - alert: ServiceInstanceDown
        expr: up == 0
        for: 15s
        labels:
          severity: critical
        annotations:
          summary: "Сервис {{ $labels.job }} ({{ $labels.instance }}) НЕДОСТУПЕН!"
          description: "Экземпляр {{ $labels.instance }} не отвечает на запросы скрейпинга более 15 секунд."

      # Алерт 2: Всплеск HTTP 500 ошибок на бэкенде
      - alert: BackendHighErrorRate
        expr: sum(rate(http_requests_total{status="500"}[1m])) > 0.1
        for: 10s
        labels:
          severity: warning
        annotations:
          summary: "Высокий уровень ошибок HTTP 500 на backend-api!"
          description: "Частота ошибок 500 превысила порог (текущее значение: {{ $value | printf \"%.2f\" }} req/s)."
EOF

    2. Создай главный конфиг prometheus/prometheus.yml: 

      cat << 'EOF' > prometheus/prometheus.yml
global:
  scrape_interval: 10s
  evaluation_interval: 10s

# Подключаем файл правил алертинга
rule_files:
  - "/etc/prometheus/alert_rules.yml"

# Настраиваем отправку сработавших алертов в Alertmanager
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]

scrape_configs:
  # 1. Самомониторинг Prometheus
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]

  # 2. Системные метрики Linux-сервера (Node Exporter)
  - job_name: "node-exporter"
    static_configs:
      - targets: ["node-exporter:9100"]

  # 3. Прикладные метрики нашего микросервиса (RED)
  - job_name: "backend-api"
    metrics_path: "/metrics"
    static_configs:
      - targets: ["backend:8000"]
EOF

    Этап 3. Конфигурация Alertmanager

    Создай конфигурацию alertmanager/alertmanager.yml. Мы настроим группировку алертов по имени сервиса и отправку уведомлений (при желании ты можешь подставить сюда свой bot_token и chat_id для Telegram, а по умолчанию алерты будут отображаться в веб-интерфейсе Alertmanager и Grafana):

    cat << 'EOF' > alertmanager/alertmanager.yml
global:
  resolve_timeout: 5m

route:
  group_by: ['alertname', 'job']
  group_wait: 5s
  group_interval: 10s
  repeat_interval: 1h
  receiver: 'default-webhook'

receivers:
  - name: 'default-webhook'
    webhook_configs:
      # Отправляем вебхук-уведомление (можно заменить на telegram_configs)
      - url: 'http://backend:8000/health'
        send_resolved: true
EOF

    Этап 5. Автоматический Provisioning источников данных в Grafana

    Чтобы при входе в Grafana не настраивать ничего вручную, создай файл grafana/provisioning/datasources/datasources.yml — он автоматически подключит и Prometheus, и Loki:

    cat << 'EOF' > grafana/provisioning/datasources/datasources.yml
apiVersion: 1

datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    editable: true

  - name: Loki
    type: loki
    access: proxy
    url: http://loki:3100
    editable: true
EOF

    Этап 6. Сборка единого compose.yaml и запуск стека Observability

    Создай файл compose.yaml в корне ~/observability-stack/:

    cat << 'EOF' > compose.yaml
services:
  # 1. Наше приложение с метриками и JSON-логами
  backend:
    build: ./app
    ports:
      - "8000:8000"
    networks:
      - obs-net
    restart: unless-stopped

  # 2. Экспортер системных метрик Linux-хоста (CPU, RAM, Disk)
  node-exporter:
    image: prom/node-exporter:v1.8.2
    command:
      - '--path.rootfs=/host'
    volumes:
      - '/:/host:ro,rslave'
    networks:
      - obs-net

  # 3. Сервер сбора метрик Prometheus
  prometheus:

      - '--storage.tsdb.path=/prometheus'
      - '--web.enable-lifecycle'

      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro

      - obs-net

    networks:
      - obs-net
    restart: unless-stopped

  # 5. Хранилище логов Grafana Loki
  loki:
    image: grafana/loki:3.1.1
    ports:
      - "3100:3100"
    command: -config.file=/etc/loki/local-config.yaml
    volumes:
      - ./loki/loki-config.yml:/etc/loki/local-config.yaml:ro
      - loki_data:/loki
    networks:
      - obs-net
    restart: unless-stopped

  # 6. Агент сбора логов контейнеров Promtail
  promtail:
    image: grafana/promtail:3.1.1
    command: -config.file=/etc/promtail/config.yml
    volumes:
      - ./promtail/promtail-config.yml:/etc/promtail/config.yml:ro
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
    networks:
      - obs-net

      - loki

      - grafana_data:/var/lib/grafana
    networks:
      - obs-net
    depends_on:
      - prometheus
      - loki
    restart: unless-stopped

networks:
  obs-net:
    driver: bridge

volumes:
  prom_data:
  loki_data:
  grafana_data:
EOF

    ✅ Чек-лист самопроверки и боевые испытания по Модулю 5

    Выполни эти 4 шага, чтобы увидеть всю мощь Observability своими глазами:

    1. Генерация рабочего трафика и проверка сырых метрик

    Сгенерируй 20 успешных заказов и посмотри, как они отразились в текстовом выводе /metrics: 

    for i in {1..20}; do curl -s http://localhost:8000/api/order > /dev/null; done
curl -s http://localhost:8000/metrics | grep http_requests_total
    Ожидаемый результат: Строка http_requests_total{endpoint="/api/order",method="GET",status="200"} 20.0.

    2. Проверка целей (Targets) в Prometheus

    • Открой в браузере http://localhost:9090/targets (или проверь через curl -s http://localhost:9090/api/v1/targets | grep -o '"health":"up"').
    • Все 3 цели (backend-api, node-exporter, prometheus) должны гореть зеленым статусом UP.

    3. Исследование метрик и логов в Grafana (порт 3000)

    1. Открой в браузере http://localhost:3000 (логин: admin, пароль: admin).
    2. Перейди в меню слева в раздел Explore (иконка компаса):
    3. Выбери сверху источник Prometheus, переключись в режим Code и введи запрос: sum by (status) (rate(http_requests_total[1m])) — ты увидишь график RPS в реальном времени!
    4. Переключи источник сверху на Loki и введи запрос: {service="backend"} | json — ты увидишь все структурированные JSON-логи своего контейнера с распарсенными полями duration_sec, node и status!
    5. Импорт готового дашборда Linux-сервера за 10 секунд: Перейди в Dashboards $\rightarrow$ New $\rightarrow$ Import, введи популярный ID официального дашборда Node Exporter 1860, нажми Load, выбери Data Source Prometheus и нажми Import — перед тобой откроется профессиональный пульт управления всеми ресурсами твоего сервера!

    4. Симуляция аварии и срабатывание боевого алерта!
