    Continuous Delivery и безопасность внедрения (CD)

    В предыдущем модуле (CI) мы научились автоматически проверять код и собирать защищенный Docker-образ. Но сам по себе образ, лежащий в реестре (Registry), не приносит бизнесу никакой пользы, пока он не окажется на боевых серверах.

    Continuous Delivery / Deployment (Непрерывная доставка и развертывание) отвечает за самую рискованную часть жизни кода — его доставку в тестовые (staging) и боевые (production) окружения без простоя (Zero-Downtime), с безопасным обновлением базы данных и гарантированным механизмом автоматического отката (Rollback), если что-то пошло не так.

    Блок 1. Разница между Continuous Delivery и Continuous Deployment

    В обоих случаях сокращение пишется как CD, но между ними есть ключевая организационная и техническая граница:

    [Git Push] ──► [CI: Build & Test] ──► [Deploy to Staging] ──► [Auto Smoke Tests] ──┬──► (Ручная кнопка Approve) ──► [Production]  (Continuous Delivery)
                                                                                   │
                                                                                   └──► (100% Автоматически)    ──► [Production]  (Continuous Deployment)
    Характеристика Continuous Delivery (Непрерывная доставка) Continuous Deployment (Непрерывное развертывание)
    Что происходит автоматически Сборка, тесты, деплой на тестовый стенд (staging), автотесты. Артефакт на 100% готов к выходу в прод. Абсолютно всё, включая финальную выкатку в production.
    Выход в Production По нажатию кнопки человеком (Manual Trigger в GitLab CI: when: manual). Автоматически после успешного прохождения всех стадий тестирования без участия человека.
    Зачем нужен ручной шаг? Бизнес-ограничения, согласование релизного окна, регуляторные требования (банки, финтех, госсектор). Максимальная скорость вывода фич (SaaS, веб-платформы, маркетплейсы). Требует идеального покрытия тестами и мониторингом.

    Блок 2. Семантическое версионирование (SemVer) и управление артефактами

    2.1. Стандарт SemVer (MAJOR.MINOR.PATCH)

    Чтобы инженеры и автоматика понимали масштаб изменений в каждом релизе, используется стандарт Semantic Versioning 2.0.0 в формате X.Y.Z (например, v2.4.1):

    1. MAJOR (X — Мажорная версия, например 1.0.0 $\rightarrow$ 2.0.0): Увеличивается, когда вносятся обратно несовместимые изменения API (Breaking Changes: удалили поле из JSON, изменили формат ответа, переписали схему БД).
    2. MINOR (Y — Минорная версия, например 1.1.0 $\rightarrow$ 1.2.0): Увеличивается, когда добавлена новая функциональность без поломки обратной совместимости (добавили новый эндпоинт /api/v2/export, при этом старые работают как прежде).
    3. PATCH (Z — Патч-версия, например 1.2.0 $\rightarrow$ 1.2.1): Увеличивается при исправлении багов (bugfix) или закрытии уязвимостей без изменения логики и контрактов API.

    Дополнительные суффиксы: Для тестовых сборок перед релизом используют пре-релизные метки: 1.3.0-alpha.1, 1.3.0-rc.2 (Release Candidate).

    2.2. Неизменяемость артефактов (Immutable Artifacts) и 12-Factor App

    В соответствии с методологией Twelve-Factor App (Фактор V: Build, release, run): * Строго разделяются три этапа: Сборка (Build) $\rightarrow$ Релиз (Release = Сборка + Конфиг окружения) $\rightarrow$ Запуск (Run). * Золотое правило CD: Один и тот же собранный бинарный Docker-образ (с уникальным SHA256-хэшем) должен пройти через dev $\rightarrow$ staging $\rightarrow$ production. Запрещено пересобирать образ заново перед выкаткой в прод! Меняются только внешние переменные окружения (.env, Secrets), но сам контейнер остается бит-в-бит тем же самым, который прошел тесты на staging.

    Блок 3. Стратегии безопасного деплоя и Feature Flags

    Как обновить приложение с версии v1.0.0 на v1.1.0 так, чтобы ни один активный пользователь не увидел ошибку 502 Bad Gateway?

    Стратегия деплоя Как работает Плюсы Минусы
    1. Recreate Убить все старые контейнеры v1.0 $\rightarrow$ запустить новые v1.1. Просто, не требует лишних ресурсов. Есть простой (Downtime). Пока стартует v1.1, сайт недоступен. Для продакшена не подходит.
    2. Rolling Update (По умолчанию) Контейнеры заменяются по очереди: подняли один v1.1 $\rightarrow$ проверили его healthcheck $\rightarrow$ погасили один v1.0, и так далее. Zero-Downtime, не требует удвоения серверов. Несколько минут версии v1.0 и v1.1 работают одновременно (база данных должна быть совместима с обеими!).
    3. Blue-Green Поднимаем рядом полный дубль кластера (Green с v1.1), тестируем его и за 1 миллисекунду переключаем весь трафик на балансировщике Nginx со старого (Blue v1.0) на новый (Green). Мгновенный деплой и мгновенный откат (просто вернуть свитч в Nginx на Blue). Требует в 2 раза больше ресурсов (RAM/CPU) на момент переключения.
    4. Canary (Канареечный) Выкатываем v1.1 на 1 контейнер и направляем на него только 5% реального трафика. Смотрим в Grafana 15 минут: если ошибок 500 нет — плавно доводим трафик до 100%. Минимальный радиус поражения (Blast Radius): если в релизе баг, пострадают только 5% запросов, а не 100%. Сложнее в настройке маршрутизации на балансировщике / Ingress.

    3.1. Feature Flags (Фича-флаги / Feature Toggles)

    Классическая ошибка новичка — считать, что Деплой (Deployment) и Релиз (Release) — это одно и то же. В современном DevOps эти понятия разделены: * Deployment (Техническая выкатка): Доставка нового контейнера на прод-серверы. * Release (Включение функции для бизнеса): Момент, когда новая кнопка или алгоритм становятся доступны реальным пользователям.

    Feature Flag — это условный рубильник (if feature_enabled("new_checkout_flow"):), который позволяет выкатить новый код в продакшен в выключенном состоянии! * Код уже лежит на проде, но спрятан за флагом (FEATURE_NEW_PAYMENT=false в конфиге или БД/Redis). * Если после включения флага база начала тормозить, нам даже не нужно делать откат контейнера или перезапускать CI/CD — мы просто за 1 секунду переключаем флаг обратно в false!

    Блок 4. Особенности CD для Stateful-приложений и автомиграции БД

    Обновить Stateless-контейнер бэкенда легко, но как быть с базой данных PostgreSQL? Во время Rolling Update, Blue-Green или Canary старая (v1.0) и новая (v1.1) версии бэкенда одновременно обращаются к одной и той же базе данных!

    4.1. Паттерн Expand and Contract (Расширение и Сжатие) для миграций БД

    Если в релизе v1.1 нужно переименовать колонку client_ip в user_ip: * ❌ Как делать НЕЛЬЗЯ: Выполнить ALTER TABLE visits RENAME COLUMN client_ip TO user_ip; перед деплоем. Как только миграция пройдет, все еще работающие контейнеры v1.0 мгновенно упадут с фатальной ошибкой column "client_ip" does not exist! И самое страшное: вы не сможете откатить код v1.1 назад на v1.0, потому что схема базы уже сломана для v1.0! * ✅ Как делать ПРАВИЛЬНО (обратно совместимые миграции): 1. Шаг 1 (Expand — в текущем релизе v1.1): Миграция только добавляет новую колонку ALTER TABLE visits ADD COLUMN IF NOT EXISTS user_ip VARCHAR(64);, не трогая старую. Код v1.1 умеет работать с обеими колонками. Если v1.1 упадет, мы спокойно откатываемся на v1.0 — старая колонка на месте! 2. Шаг 2 (Contract — через неделю в релизе v1.2): Когда v1.0 давно ушла в историю, мы спокойно удаляем старую колонку.

    4.2. Порядок шагов в CD-пайплайне

    В конвейере доставки строго соблюдается последовательность: 1. Снятие автоматического бэкапа БД (pre-deploy backup) перед любыми изменениями. 2. Запуск одноразового контейнера миграций (db-migrate) с новыми SQL-скриптами. 3. Обновление контейнеров приложения (deploy). 4. Проверка жизнеспособности (post-deploy smoke test): автоматический скрипт стучится в /health и /api/visit и проверяет, что ответ равен 200 OK. 5. Автоматический откат (auto-rollback): если smoke-тест не прошел — скрипт немедленно возвращает предыдущую стабильную версию образа!

    Блок 5. Оптимизация релизов и расчет DORA-метрик

    Как понять, что построенный нами CI/CD-конвейер действительно эффективен? Мы измеряем 4 метрики DORA прямо по данным из GitLab CI и нашей базы деплоев:

    Метрика DORA Как считается технически в CI/CD Уровень Elite-команд
    1. Deployment Frequency (Частота деплоев) Количество успешных запусков стадии deploy:production в день/неделю. Несколько раз в день (по требованию).
    2. Lead Time for Changes (Время доставки коммита) $T_{\text{deploy_finished}} - T_{\text{commit_created}}$ (разница между временем коммита и завершением деплоя в прод). Менее 1 часа.
    3. Change Failure Rate (Процент неудачных релизов) $\frac{\text{Деплои со статусом FAILED или ROLLED_BACK}}{\text{Общее число деплоев в прод}} \times 100\%$. $0\% - 15\%$.
    4. MTTR (Среднее время восстановления) $T_{\text{rollback_or_hotfix_ok}} - T_{\text{incident_alert_fired}}$ (время от срабатывания алерта до успешного автоотката). Менее 1 часа (при автооткате в CD — менее 2 минут!).

    🛠 Практический проект Модуля 7: Сквозной CD-конвейер с миграциями БД, Feature Flags и автоматическим откатом (Rollback)

    Мы модернизируем наш кластер в ~/compose-cluster: 1. Добавим в приложение поддержку Семантического версионирования (APP_VERSION) и Feature Flags (FEATURE_VIP_MODE). 2. Создадим систему версионированных SQL-миграций БД. 3. Напишем боевой скрипт оркестрации релиза deploy_with_rollback.sh, который: * Снимает предрелизный бэкап PostgreSQL. * Накатывает SQL-миграции. * Выкатывает новую версию сервиса без простоя (Blue-Green / Rolling). * Прогоняет автоматические Smoke-тесты. * Автоматически откатывает кластер на предыдущую стабильную версию, если новая версия оказалась с багом! 4. Дополним .gitlab-ci.yml полноценными CD-стадиями для staging и production.

    Этап 1. Обновление приложения: SemVer, Feature Flags и симуляция сбоя релиза

    Перейдем в директорию ~/compose-cluster и обновим app/main.py, добавив поддержку фича-флага FEATURE_VIP_MODE и специального флага SIMULATE_CRASH (чтобы мы могли вживую протестировать, как наш конвейер сам обнаружит сломанный релиз и выполнит автоматический откат!):

    cd ~/compose-cluster

cat << 'EOF' > app/main.py
import os
import socket
import psycopg2
import redis
from flask import Flask, jsonify, request

app = Flask(__name__)

APP_VERSION = os.getenv("APP_VERSION", "1.0.0")
FEATURE_VIP_MODE = os.getenv("FEATURE_VIP_MODE", "false").lower() == "true"
SIMULATE_CRASH = os.getenv("SIMULATE_CRASH", "false").lower() == "true"

def get_db_password():
    secret_path = "/run/secrets/db_password"
    if os.path.exists(secret_path):
        with open(secret_path, "r") as f:
            return f.read().strip()
    return os.getenv("POSTGRES_PASSWORD", "")

def get_db_conn():
    return psycopg2.connect(
        host=os.getenv("DB_HOST", "db"),
        database=os.getenv("POSTGRES_DB", "cluster_db"),
        user=os.getenv("POSTGRES_USER", "app_admin"),
        password=get_db_password(),
        connect_timeout=3
    )

cache = redis.Redis(host=os.getenv("REDIS_HOST", "redis"), port=6379, decode_responses=True)

@app.route("/health")
def health():
    # Если в релизе допущена критическая ошибка — healthcheck возвращает 500
    if SIMULATE_CRASH:
        return jsonify({"status": "unhealthy", "reason": "Simulated critical bug in release!", "version": APP_VERSION}), 500
    try:
        conn = get_db_conn()
        conn.close()
        cache.ping()
        return jsonify({
            "status": "healthy",
            "version": APP_VERSION,
            "feature_vip_mode": FEATURE_VIP_MODE,
            "node": socket.gethostname()
        }), 200
    except Exception as e:
        return jsonify({"status": "unhealthy", "error": str(e)}), 500

@app.route("/api/visit")
def visit():
    if SIMULATE_CRASH:
        return jsonify({"error": "Internal Server Error in broken release"}), 500

    client_ip = request.headers.get("X-Real-IP", request.remote_addr)
    node_id = socket.gethostname()
    total_hits = cache.incr("cluster_hits")

    conn = get_db_conn()
    cur = conn.cursor()
    cur.execute("""
        CREATE TABLE IF NOT EXISTS visits (
            id SERIAL PRIMARY KEY,
            node_id VARCHAR(64),
            client_ip VARCHAR(64),
            app_version VARCHAR(32) DEFAULT '1.0.0',
            visited_at TIMESTAMPTZ DEFAULT NOW()
        );
    """)
    cur.execute(
        "INSERT INTO visits (node_id, client_ip, app_version) VALUES (%s, %s, %s);",
        (node_id, client_ip, APP_VERSION)
    )
    cur.execute("SELECT COUNT(*) FROM visits;")
    db_rows = cur.fetchone()[0]
    conn.commit()
    cur.close()
    conn.close()

    response_data = {
        "version": APP_VERSION,
        "served_by_replica": node_id,
        "redis_hits": total_hits,
        "postgres_saved_rows": db_rows,
        "feature_vip_enabled": FEATURE_VIP_MODE
    }
    # Логика, скрытая за Feature Flag (включается без пересборки кода!)
    if FEATURE_VIP_MODE:
        response_data["vip_bonus_message"] = "Welcome to VIP Canary Feature!"

    return jsonify(response_data), 200
EOF

    cat << 'EOF' > compose.yaml

    volumes:
      - redis_cluster_data:/data
    networks:
      - backend-net
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    <<: *service-defaults

    Этап 2. Создание системы обратно-совместимых миграций БД (Expand Pattern)

    Создай папку migrations/ с идемпотентным SQL-скриптом миграции V1__add_app_version_column.sql, который безопасно расширяет таблицу visits и создает таблицу аудита релизов release_history (для подсчета DORA-метрик!):

    mkdir -p ~/compose-cluster/migrations ~/compose-cluster/backups

cat << 'EOF' > migrations/V1__expand_schema_and_dora_audit.sql
BEGIN;

-- 1. Создаем основную таблицу, если она еще не создана
CREATE TABLE IF NOT EXISTS visits (
    id SERIAL PRIMARY KEY,
    node_id VARCHAR(64),
    client_ip VARCHAR(64),
    visited_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. Паттерн Expand: безопасно добавляем новую колонку без блокировки старого кода
ALTER TABLE visits ADD COLUMN IF NOT EXISTS app_version VARCHAR(32) DEFAULT '1.0.0';

-- 3. Таблица для трекинга релизов и расчета DORA-метрик (Change Failure Rate)
CREATE TABLE IF NOT EXISTS release_history (
    id SERIAL PRIMARY KEY,
    version VARCHAR(32) NOT NULL,
    status VARCHAR(32) NOT NULL CHECK (status IN ('DEPLOYED', 'ROLLED_BACK')),
    deployed_at TIMESTAMPTZ DEFAULT NOW()
);

COMMIT;
EOF

    Этап 3. Создание боевого скрипта деплоя с авто-бэкапом, миграциями, Smoke-тестом и Rollback

    Создай скрипт deploy.sh, который выполняет всю магию безопасного CD:

    cat << 'EOF' > deploy.sh
#!/usr/bin/env bash
set -euo pipefail

NEW_VERSION="${1:?Укажите версию для деплоя (например: ./deploy.sh 1.1.0)}"
VIP_FLAG="${2:-false}"
CRASH_SIM="${3:-false}"
STATE_FILE=".last_stable_version"

log() {
    echo "[$(date +'%H:%M:%S')] [CD-PIPELINE] $*"
}

# 1. Определяем текущую стабильную версию для возможного отката (Rollback)
if [[ -f "$STATE_FILE" ]]; then
    PREV_VERSION="$(cat "$STATE_FILE")"
else
    PREV_VERSION="1.0.0"
fi

log "Начинаем релиз версии v${NEW_VERSION} (Предыдущая стабильная: v${PREV_VERSION})"

# 2. Убеждаемся, что БД и Redis запущены
docker compose up -d db redis
sleep 3

# 3. Pre-Deploy Backup: снимаем бэкап БД перед накатом миграций
BACKUP_FILE="backups/pre_deploy_v${NEW_VERSION}_$(date +%s).dump"
log "Снимаем страховочный бэкап PostgreSQL -> ${BACKUP_FILE}"
DB_CONTAINER="$(docker compose ps -q db)"
docker exec "$DB_CONTAINER" pg_dump -U app_admin -d cluster_db -Fc -f /tmp/backup.dump
docker cp "${DB_CONTAINER}:/tmp/backup.dump" "$BACKUP_FILE"

# 4. Накатываем обратно-совместимые SQL-миграции
log "Применяем SQL-миграции из папки migrations/..."
for sql_file in migrations/*.sql; do
    log " -> Выполняется миграция: ${sql_file}"
    docker exec -i "$DB_CONTAINER" psql -v ON_ERROR_STOP=1 -U app_admin -d cluster_db < "$sql_file"
done

# 5. Выкатываем новую версию контейнеров
log "Запускаем контейнеры backend версии v${NEW_VERSION} (FEATURE_VIP_MODE=${VIP_FLAG})..."
export APP_VERSION="$NEW_VERSION"
export FEATURE_VIP_MODE="$VIP_FLAG"
export SIMULATE_CRASH="$CRASH_SIM"

docker compose up -d --scale backend=2 --no-deps backend nginx

# 6. Post-Deploy Smoke Tests (проверяем здоровье выкаченной версии)
log "Ожидание готовности сервиса и запуск Smoke-тестов..."
sleep 5

HTTP_STATUS="$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/health || echo "000")"

if [[ "$HTTP_STATUS" == "200" ]]; then
    log "✅ SMOKE TEST PASSED (HTTP 200)! Релиз v${NEW_VERSION} успешно введен в эксплуатацию!"
    echo "$NEW_VERSION" > "$STATE_FILE"
    docker exec -i "$DB_CONTAINER" psql -U app_admin -d cluster_db -c \
      "INSERT INTO release_history (version, status) VALUES ('${NEW_VERSION}', 'DEPLOYED');" > /dev/null
else
    log "❌ CRITICAL ALERT: Smoke Test провалился (HTTP ${HTTP_STATUS}) на версии v${NEW_VERSION}!"
    log "⏪ ЗАПУСК АВТОМАТИЧЕСКОГО ОТКАТА (ROLLBACK) НА СТАБИЛЬНУЮ ВЕРСИЮ v${PREV_VERSION}..."

    export APP_VERSION="$PREV_VERSION"
    export SIMULATE_CRASH="false"
    docker compose up -d --scale backend=2 --no-deps backend nginx
    sleep 4

    ROLLBACK_STATUS="$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/health || echo "000")"
    if [[ "$ROLLBACK_STATUS" == "200" ]]; then
        log "✅ ROLLBACK УСПЕШЕН! Кластер восстановлен на версии v${PREV_VERSION} (HTTP 200)."
        docker exec -i "$DB_CONTAINER" psql -U app_admin -d cluster_db -c \
          "INSERT INTO release_history (version, status) VALUES ('${NEW_VERSION}', 'ROLLED_BACK');" > /dev/null
        exit 1
    else
        log "🚨 FATAL: Не удалось восстановиться автоматически!"
        exit 2
    fi
fi
EOF

chmod +x deploy.sh

    Этап 5. Как это выглядит в .gitlab-ci.yml (CD-стадии и environments)

    Добавим в конец нашего .gitlab-ci.yml из Модуля 6 стадии доставки deploy_staging, deploy_prod и ручную кнопку отката rollback_prod:

    # Дополнение к .gitlab-ci.yml для реализации Continuous Delivery:
deploy:staging:
  stage: deploy_staging
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  script:
    - ./deploy.sh "$CI_COMMIT_SHORT_SHA" "true" "false"

deploy:production:
  stage: deploy_prod
  needs: ["deploy:staging"]
  environment:
    name: production
    url: https://example.com
    on_stop: rollback:production
  rules:
    # Continuous Delivery: выкатка в прод по нажатию кнопки в UI (when: manual)
    #Только для релизных тегов SemVer (например, v1.1.0)
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: manual
  script:
    - ./deploy.sh "$CI_COMMIT_TAG" "false" "false"

rollback:production:
  stage: deploy_prod
  environment:
    name: production
    action: stop
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: manual
  script:
    - PREV_VER=$(cat .last_stable_version)
    - ./deploy.sh "$PREV_VER" "false" "false"

    ✅ Чек-лист самопроверки по Модулю 7 (Расчет DORA-метрик в SQL!)

    Вспомним навыки SQL из Модуля 3 и посчитаем реальные DORA-метрики (включая Change Failure Rate) по нашей таблице release_history, куда скрипт deploy.sh автоматически записывал результаты всех выкаток:

    docker exec -i "$(docker compose ps -q db)" psql -U app_admin -d cluster_db << 'EOF'
\echo '=== История всех релизов CD-конвейера ==='
SELECT id, version, status, TO_CHAR(deployed_at, 'YYYY-MM-DD HH24:MI:SS') AS release_time
FROM release_history
ORDER BY id;

\echo '=== Расчет DORA-метрики Change Failure Rate (CFR) ==='
SELECT 
    COUNT(*) AS total_releases,
    SUM(CASE WHEN status = 'DEPLOYED' THEN 1 ELSE 0 END) AS successful_releases,
    SUM(CASE WHEN status = 'ROLLED_BACK' THEN 1 ELSE 0 END) AS rollbacks,
    ROUND(
        SUM(CASE WHEN status = 'ROLLED_BACK' THEN 1.0 ELSE 0.0 END) / COUNT(*) * 100, 
        1
    ) || '%' AS change_failure_rate
FROM release_history;
EOF

    Ожидаемый результат: В отчете отобразятся 3 релиза (1.0.0 — DEPLOYED, 1.1.0 — DEPLOYED, 1.2.0 — ROLLED_BACK) и автоматически рассчитанный показатель change_failure_rate = 33.3%, а также свежие дампы БД в папке ls -lh backups/!
