    Инфраструктура как код (IaC) — Terraform

    До этого момента мы работали с уже существующим сервером или локальной машиной. Но откуда берутся сами виртуальные машины, облачные сети (VPC), подсети, балансировщики нагрузки, группы безопасности (Firewalls), управляемые базы данных и S3-бакеты в облаке?

    Создавать их мышкой в веб-консоли облачного провайдера (ClickOps) в реальных проектах строго запрещено: вы не сможете повторить такую инфраструктуру один-в-один для тестового стенда (staging), никто не знает, кто и зачем вчера открыл порт 22 на весь мир, а при случайном удалении сети восстановление займет дни.

    Infrastructure as Code (IaC) решает эту проблему: вся облачная инфраструктура описывается декларативным кодом в Git-репозитории, проходит Code Review и автоматически создается или обновляется утилитой Terraform (или его open-source форком OpenTofu).

    Блок 1. Принципы IaC и Immutable Infrastructure

    1.1. Декларативный подход против Императивного

    Инструменты автоматизации делятся на два лагеря:

    Характеристика Императивный подход (КАК сделать) Декларативный подход (ЧТО получить)
    Примеры Bash-скрипты, CLI (yc compute instance create, aws ec2 run-instances) Terraform / OpenTofu, Kubernetes манифесты, Docker Compose
    Логика работы Вы пишете пошаговый алгоритм команд. Если запустить скрипт второй раз — он упадет с ошибкой «Сервер уже существует» или создаст дубликат! Вы описываете желаемое конечное состояние (например: «Хочу 3 сервера с 4 ГБ RAM»). Инструмент сам сравнивает это с текущим состоянием и вычисляет, что нужно добавить, изменить или удалить.
    Идемпотентность Требует ручного написания сложных if-else проверок. Встроена из коробки: если ничего не менялось в коде, повторный запуск ничего не трогает (No changes).

    1.2. Концепция Immutable Infrastructure (Неизменяемая инфраструктура) — Pets vs Cattle

    В классическом системном администрировании к серверам относились как к Домашним питомцам (Pets): * У каждого сервера было ласковое имя (zeus, apollo), админы заходили на них по SSH, годами ставили пакеты руками, правили конфиги. Со временем наступал Configuration Drift (Дрейф конфигурации) — два сервера должны быть одинаковыми, но работают по-разному. Если такой сервер умирал, вся компания впадала в панику.

    В современном DevOps серверы — это Стадо (Cattle / Неизменяемая инфраструктура): * Серверы имеют безликие номера (app-node-01, app-node-02) и создаются из одного шаблона по коду Terraform. * Золотое правило Immutable Infrastructure: После создания сервера мы никогда не меняем его вручную. Если нужно обновить версию ОС, ядра или конфигурацию — мы меняем код в Terraform, и он автоматически создает новый чистый сервер, переключает на него трафик и уничтожает старый!

    Блок 2. Архитектура Terraform и синтаксис HCL

    2.1. Как работает Terraform (Ядро, Провайдеры и Жизненный цикл)

    Terraform написан на Go и состоит из двух частей: 1. Terraform Core: Читает ваш код на языке HCL (HashiCorp Configuration Language), строит граф зависимостей между ресурсами и сравнивает желаемое состояние с файлом текущего состояния (terraform.tfstate). 2. Providers (Провайдеры): Плагины, которые умеют переводить команды Terraform на язык REST API конкретного облака или сервиса (например: yandex, aws, google, kubernetes, docker, gitlab).

    Четыре главные команды жизненного цикла Terraform:

    [terraform init] ──► [terraform plan] ──► [terraform apply] ──► [terraform destroy]
 Скачивание плагинов   Сухой прогон (Diff)   Создание ресурсов     Полное удаление стенда
    * terraform init: Инициализирует рабочую директорию, скачивает нужные провайдеры и модули, настраивает подключение к хранилищу стейта (Backend). * terraform validate & terraform fmt: Проверяет синтаксис кода и автоматически выравнивает отступы по стандарту. * terraform plan: Самая важная команда! Ничего не меняет в облаке, но опрашивает API провайдера и показывает точный план изменений (как git diff): * + create (зеленый) — ресурс будет создан. * ~ update in-place (желтый) — ресурс будет изменен без перезагрузки (например, добавится тег или правило фаервола). * -/+ destroy and then create replacement (красный!) — ОПАСНО! Изменение параметра (например, смена образа ОС или зоны доступности) требует полного удаления старого ресурса и создания нового. * terraform apply: Выполняет план и вносит изменения в реальное облако.

    2.2. Базовые строительные блоки языка HCL

    # 1. Блок настройки версии Terraform и требуемых провайдеров
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      version = "~> 0.120.0"
    }
  }
}

# 2. Настройка самого провайдера (авторизация через переменные окружения!)
provider "yandex" {
  zone = var.default_zone
}

# 3. Data Source (Источник данных) — НИЧЕГО не создает, а только ЧИТАЕТ существующий объект из облака
data "yandex_compute_image" "ubuntu_2404" {
  family = "ubuntu-2404-lts"
}

# 4. Resource (Ресурс) — главный блок: СОЗДАЕТ и управляет объектом инфраструктуры
# Синтаксис: resource "<ТИП_РЕСУРСА>" "<ЛОКАЛЬНОЕ_ИМЯ_В_КОДЕ>"
resource "yandex_vpc_network" "app_net" {
  name = "production-vpc"
}

resource "yandex_vpc_subnet" "app_subnet" {
  name           = "production-subnet-a"
  zone           = var.default_zone
  # Неявная зависимость: Terraform сам поймет, что сначала нужно создать сеть app_net!
  network_id     = yandex_vpc_network.app_net.id
  v4_cidr_blocks = ["10.10.1.0/24"]
}

    Блок 3. Управление состоянием инфраструктуры (State) и защита от дрейфа

    3.1. Зачем нужен файл terraform.tfstate и почему его НЕЛЬЗЯ хранить в Git

    Откуда Terraform знает, какие именно виртуальные машины в облаке создал он, а какие — другие отделы? После первого выполнения terraform apply создается JSON-файл terraform.tfstate, в котором записано соответствие между вашим кодом (yandex_vpc_network.app_net) и реальным ID объекта в облаке (enp9abc12345).

    ❌ Почему категорически запрещено коммитить terraform.tfstate в Git:

    1. Секреты в открытом виде: Даже если вы пометили переменную пароля БД как sensitive = true (она скрыта в выводе консоли), внутри файла terraform.tfstate все пароли, приватные ключи и токены хранятся открытым текстом (Plaintext)!
    2. Конфликты командной работы (Race Condition): Если два DevOps-инженера одновременно запустят terraform apply со своих ноутбуков со старым локальным стейтом, они перезапишут инфраструктуру друг друга и сломают облако.

    ✅ Промышленный стандарт: Remote State в S3 + State Locking (Блокировки)

    В реальных проектах стейт хранится удаленно (Remote Backend) в объектном хранилище S3 (Yandex Object Storage / AWS S3 / MinIO / GitLab Managed Terraform State) с включенным шифрованием и механизмом блокировки (State Lock): * Когда Инженер №1 запускает terraform apply, Terraform вешает замок (.tflock в S3 или запись в таблице DynamoDB/YDB). * Если в эту же секунду Инженер №2 запустит apply, Terraform выдаст ему сообщение: «Error acquiring the state lock: стейт сейчас занят Инженером №1, подождите».

    terraform {
  backend "s3" {
    endpoints = {
      s3 = "https://storage.yandexcloud.net"
    }
    bucket = "my-company-tfstate-prod"
    region = "ru-central1"
    key    = "infra/network/terraform.tfstate"

    # Включение нативной блокировки стейта (.tflock в S3 бакете, доступно в современных версиях Terraform)
    use_lockfile        = true
    skip_region_validation      = true
    skip_credentials_validation = true
    skip_requesting_account_id  = true
  }
}

    3.2. Предотвращение дрейфа конфигураций (Drift Detection)

    Дрейф конфигурации (Configuration Drift) возникает, когда кто-то зашел руками в веб-консоль облака и изменил настройки ресурса (например, поменял порт в Security Group или увеличил RAM сервера), в обход кода Terraform.

    Как бороться с дрейфом: 1. Регулярный terraform plan -detailed-exitcode по расписанию в GitLab CI: * Код возврата 0 — дрейфа нет, облако на 100% совпадает с кодом Git. * Код возврата 1 — ошибка выполнения. * Код возврата 2 — ОБНАРУЖЕН ДРЕЙФ (есть расхождения)! Пайплайн немедленно шлет алерт в Telegram/Slack дежурному инженеру. 2. Блок lifecycle (Защита критических ресурсов от случайного удаления): Чтобы никто случайно не пересоздал боевую базу данных или S3-бакет, добавляют защиту прямо в код ресурса: 

    lifecycle {
  prevent_destroy = true # Terraform выдаст фатальную ошибку при любой попытке удалить этот ресурс!
  ignore_changes  = [tags] # Игнорировать ручные изменения конкретных полей
}

    Блок 4. Гибкость кода: Переменные, Секреты, Циклы и Принцип DRY (Модули)

    4.1. Переменные (variables), Выходные значения (outputs) и Секреты (sensitive)

    Чтобы один и тот же код работал для dev, staging и production, все параметры выносятся в переменные (variables.tf):

    # variables.tf
variable "environment" {
  description = "Имя окружения (dev, staging, prod)"
  type        = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Окружение должно быть только dev, staging или prod!"
  }
}

variable "db_password" {
  description = "Пароль администратора БД"
  type        = string
  sensitive   = true # Скрывает значение в выводе terraform plan и apply ([sensitive value])
}

# Locals — вычисляемые внутренние константы для удобства
locals {
  name_prefix = "cluster-${var.environment}"
  common_tags = {
    managed_by  = "terraform"
    environment = var.environment
  }
}

# outputs.tf — значения, которые Terraform выведет на экран после создания (например, выданный IP сервера)
output "load_balancer_public_ip" {
  description = "Внешний IP-адрес входного балансировщика"
  value       = yandex_compute_instance.balancer.network_interface[0].nat_ip_address
}

    Как передавать секретные переменные (например, db_password): Никогда не пишите их в terraform.tfvars в Git! Передавайте их через переменные окружения с префиксом TF_VAR_: 

    export TF_VAR_db_password="MySuperSecretPassword"
terraform apply

    4.2. Динамические конфигурации: count, for_each и dynamic блоки

    Как создать сразу 3 разных контейнера или 3 подсети без копипасты (Copy-Paste) одного и того же блока resource?

    • count: Простой числовой счетчик (count = 3). Создает массив ресурсов [0], [1], [2]. Минус: если удалить средний элемент из списка, все последующие сдвинутся по индексу и пересоздадутся!
    • for_each (Рекомендуемый стандарт): Принимает словарь (map) или множество (set строк). Каждый ресурс получает осмысленный текстовый ключ (each.key и each.value), поэтому удаление одного элемента никак не затрагивает остальные!
    variable "microservices" {
  type = map(object({
    port     = number
    replicas = number
  }))
  default = {
    "auth-api"    = { port = 8001, replicas = 2 }
    "billing-api" = { port = 8002, replicas = 1 }
  }
}

# Один блок создаст ресурсы для каждого сервиса из словаря!
# Обращение к конкретному ресурсу: docker_container.service["auth-api"]

    4.3. Принцип DRY: Переиспользование модулей Terraform (Modules)

    Когда проект растет, хранить 2000 строк кода в одном файле main.tf невозможно. Кроме того, нам нужно поднять абсолютно одинаковую архитектуру для staging (на маленьких дешевых ВМ) и для production (на мощных серверах).

    Решение — Модули Terraform (аналог функций/библиотек в программировании): * Мы один раз пишем универсальный модуль modules/app_service/ (со своими входными variables.tf, main.tf и выходными outputs.tf). * А в папках окружений (environments/staging и environments/prod) просто вызываем этот модуль блок-схемой module "...", передавая разные размеры ресурсов!

    terraform-infra/
├── modules/                      # Переиспользуемые строительные кирпичики (DRY)
│   ├── network/                  # Модуль создания изолированной сети
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── microservice_node/        # Модуль создания узла сервиса
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
└── environments/                 # Конкретные окружения
    ├── staging/
    │   └── main.tf               # Вызывает модули с параметрами для Staging
    └── production/
        └── main.tf               # Вызывает те же модули с параметрами для Prod

    🛠 Практический проект Модуля 8: Проектирование и реализация модулей Terraform с безопасным хранением State и проверкой Drift

    Чтобы ты мог выполнить этот практикум прямо сейчас на своем компьютере бесплатно и без привязки банковской карты к облаку, мы применим хитрость профессиональных DevOps-инженеров: 1. Мы поднимем локальное облачное S3-хранилище MinIO (100% совместимое с AWS S3 и Yandex Object Storage) для удаленного хранения terraform.tfstate и блокировок. 2. Напишем два переиспользуемых модуля Terraform (modules/network и modules/app_tier), используя официальный провайдер kreuzwerker/docker (при этом рядом я оставлю эталонный код модуля для Yandex Cloud, чтобы у тебя были оба шаблона!). 3. Развернем инфраструктуру одной командой terraform apply, симулируем ручной взлом/дрейф конфигурации и обнаружим его через Drift Detection!

    Этап 1. Установка Terraform (или OpenTofu) и запуск S3-хранилища для Remote State

    1. Проверим наличие terraform (если еще не установлен — установим бинарник в /usr/local/bin за 10 секунд): 

      if ! command -v terraform &> /dev/null; then
    echo "Устанавливаем Terraform..."
    ARCH=$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')
    curl -fsSL "https://hashicorp-releases.yandexcloud.net/terraform/1.9.8/terraform_1.9.8_linux_${ARCH}.zip" -o /tmp/tf.zip
    sudo unzip -o /tmp/tf.zip -d /usr/local/bin/ && rm /tmp/tf.zip
fi
terraform version

    2. Запустим локальный S3-сервер MinIO и автоматически создадим в нём защищенный бакет tfstate-bucket для хранения состояния нашей инфраструктуры: 

      mkdir -p ~/terraform-practice && cd ~/terraform-practice

docker run -d \
  --name s3-minio \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=tf_admin \
  -e MINIO_ROOT_PASSWORD=TfSecretKey2026 \
  minio/minio server /data --console-address ":9001"

sleep 3
# Создаем бакет tfstate-bucket внутри S3 через клиент mc
docker run --rm --network host --entrypoint /bin/sh minio/mc -c "
  mc alias set local http://127.0.0.1:9000 tf_admin TfSecretKey2026 &&
  mc mb --ignore-existing local/tfstate-bucket &&
  mc version enable local/tfstate-bucket
"

      Обрати внимание на команду mc version enable: мы включили версионирование S3-бакета. Если стейт когда-либо повредится, мы сможем откатить любую его прошлую ревизию!

    Этап 2. Разработка переиспользуемых модулей Terraform (Принцип DRY)

    Создадим модульную структуру проекта: 

    mkdir -p ~/terraform-practice/modules/{network,app_tier}
mkdir -p ~/terraform-practice/environments/staging

    1. Модуль сети (modules/network):

    cat << 'EOF' > ~/terraform-practice/modules/network/variables.tf
variable "env_name" {
  description = "Имя окружения"
  type        = string
}

variable "subnet_cidr" {
  description = "Подсеть в формате CIDR"
  type        = string
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/network/main.tf
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0.2"
    }
  }
}

resource "docker_network" "vpc_net" {
  name   = "tf-${var.env_name}-vpc"
  driver = "bridge"
  ipam_config {
    subnet = var.subnet_cidr
  }
  labels {
    label = "managed_by"
    value = "terraform"
  }
  labels {
    label = "environment"
    value = var.env_name
  }
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/network/outputs.tf
output "network_id" {
  value = docker_network.vpc_net.id
}

output "network_name" {
  value = docker_network.vpc_net.name
}
EOF

    2. Модуль кластера приложений с использованием for_each и секретов (modules/app_tier):

    cat << 'EOF' > ~/terraform-practice/modules/app_tier/variables.tf
variable "env_name" {
  type = string
}

variable "network_name" {
  type = string
}

variable "api_secret_token" {
  type      = string
  sensitive = true
}

variable "nodes" {
  description = "Карта узлов для развертывания через for_each"
  type = map(object({
    external_port = number
    memory_mb     = number
  }))
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/app_tier/main.tf
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0.2"
    }
  }
}

resource "docker_image" "nginx_img" {
  name         = "nginx:1.27-alpine"
  keep_locally = true
}

# Динамическое создание узлов по словарю var.nodes через for_each
resource "docker_container" "app_node" {
  for_each = var.nodes

  name   = "tf-${var.env_name}-${each.key}"
  image  = docker_image.nginx_img.image_id
  memory = each.value.memory_mb

  # Передача чувствительного секрета и метаданных в окружение
  env = [
    "ENV_NAME=${var.env_name}",
    "NODE_NAME=${each.key}",
    "API_SECRET_TOKEN=${var.api_secret_token}"
  ]

  ports {
    internal = 80
    external = each.value.external_port
  }

  networks_advanced {
    name = var.network_name
  }

  labels {
    label = "managed_by"
    value = "terraform"
  }
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/app_tier/outputs.tf
output "deployed_endpoints" {
  description = "Список развернутых узлов и их внешних URL"
  value = {
    for k, node in docker_container.app_node :
    k => "http://localhost:${node.ports[0].external}"
  }
}
EOF

    Этап 3. Сборка окружения staging с подключением Remote S3 State

    Теперь перейдем в папку окружения environments/staging и соберем инфраструктуру из наших модулей, настроив хранение стейта в S3-бакете tfstate-bucket:

    cd ~/terraform-practice/environments/staging

# 1. Настройка удаленного хранения State в S3 и провайдеров (backend.tf)
cat << 'EOF' > backend.tf
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0.2"
    }
  }

  # Удаленный Backend в S3 (MinIO / Yandex Object Storage / AWS S3)
  backend "s3" {
    endpoints = {
      s3 = "http://127.0.0.1:9000"
    }
    bucket                      = "tfstate-bucket"
    key                         = "staging/terraform.tfstate"
    region                      = "us-east-1"
    use_path_style              = true
    skip_credentials_validation = true
    skip_metadata_api_check     = true
    skip_requesting_account_id  = true
  }
}
EOF

# 2. Вызов модулей network и app_tier (main.tf)
cat << 'EOF' > main.tf
variable "api_secret_token" {
  type        = string
  sensitive   = true
  description = "Секретный токен, передаваемый через TF_VAR_api_secret_token"
}

# Вызываем модуль сети
module "vpc" {
  source      = "../../modules/network"
  env_name    = "staging"
  subnet_cidr = "172.28.0.0/16"
}

# Вызываем модуль узлов приложения
module "cluster_nodes" {
  source           = "../../modules/app_tier"
  env_name         = "staging"
  network_name     = module.vpc.network_name
  api_secret_token = var.api_secret_token

  nodes = {
    "web-01" = { external_port = 8181, memory_mb = 64 }
    "web-02" = { external_port = 8182, memory_mb = 64 }
  }
}

output "vpc_network_id" {
  value = module.vpc.network_id
}

output "cluster_urls" {
  value = module.cluster_nodes.deployed_endpoints
}
EOF

cat << 'EOF' > .gitignore

*.tfstate.*
crash.log
*.tfvars
EOF

    Этап 4. Инициализация, Plan, Apply и проверка Remote State

    Передадим ключи доступа к нашему S3-хранилищу и секретный токен приложения через переменные окружения и развернем инфраструктуру:

    cd ~/terraform-practice/environments/staging

export AWS_ACCESS_KEY_ID="tf_admin"
export AWS_SECRET_ACCESS_KEY="TfSecretKey2026"
export TF_VAR_api_secret_token="ProdSecretVaultToken777"

# 1. Инициализируем проект и подключаем S3 backend
terraform init

# 2. Проверяем форматирование и валидность кода
terraform fmt -check
terraform validate

# 3. Строим план выполнения (обрати внимание: api_secret_token скрыт как (sensitive value)!)
terraform plan -out=tfplan

# 4. Применяем план без лишнего запроса подтверждения
terraform apply "tfplan"

    ✅ Чек-лист самопроверки по Модулю 8 (и тест Drift Detection!)

    Выполни эти 4 проверки, чтобы убедиться, что вся цепочка IaC работает по промышленному стандарту:

    1. Проверка того, что локально НЕТ файла terraform.tfstate, а он лежит в S3-бакете: 

      ls -la terraform.tfstate || echo "Локального стейта нет — отлично!"
docker run --rm --network host --entrypoint /bin/sh minio/mc -c "
  mc alias set local http://127.0.0.1:9000 tf_admin TfSecretKey2026 >/dev/null &&
  mc ls local/tfstate-bucket/staging/
"
      Ожидаемый результат: В S3-бакете лежит файл terraform.tfstate!

    2. Проверка работы развернутых узлов по URL из terraform output: 

      terraform output
curl -I http://localhost:8181
curl -I http://localhost:8182
      Ожидаемый результат: Оба узла возвращают HTTP/1.1 200 OK.

    3. Боевое учение: Симуляция дрейфа конфигурации (Configuration Drift) и самовосстановление! Представим, что кто-то зашел на сервер в обход Terraform и вручную удалил узел tf-staging-web-02: 

      # Вручную ломаем инфраструктуру (удаляем второй контейнер)
docker rm -f tf-staging-web-02

# Запускаем проверку дрейфа через terraform plan -detailed-exitcode
terraform plan -detailed-exitcode || echo "🚨 ОБНАРУЖЕН ДРЕЙФ КОНФИГУРАЦИИ (Exit Code 2)!"
      Посмотри на вывод Terraform: # module.cluster_nodes.docker_container.app_node["web-02"] will be created. Он мгновенно заметил пропажу узла!

    4. Устранение дрейфа одной командой: 

      terraform apply -auto-approve
docker ps --filter "name=tf-staging"
      Ожидаемый результат: Узел tf-staging-web-02 автоматически пересоздан и возвращен в строй за 1 секунду!

    (Очистка стенда после завершения модуля: terraform destroy -auto-approve && docker rm -f s3-minio).
