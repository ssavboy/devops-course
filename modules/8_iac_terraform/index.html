    Инфраструктура как код (IaC) — Terraform

    До этого момента мы разворачивали контейнеры, базы данных и мониторинг на уже существующем сервере или локальной машине. Но откуда в реальном проекте берутся сами облачные серверы, виртуальные сети (VPC), подсети, таблицы маршрутизации, межсетевые экраны (Security Groups), управляемые кластеры СУБД и бакеты объектного хранилища S3?

    На заре облачных технологий администраторы создавали всё это вручную, кликая мышкой в веб-консоли облачного провайдера — антипаттерн, получивший ироничное название ClickOps. В промышленной разработке ClickOps строго запрещен по трем причинам: вы физически не сможете без ошибок повторить созданную вручную инфраструктуру из 50 компонентов для тестового стенда (staging); никто в компании не знает, кто, когда и зачем вчера открыл порт 22 на весь интернет; а в случае случайного удаления облачной сети восстановление инфраструктуры по памяти займет несколько дней.

    Практика Infrastructure as Code (IaC — Инфраструктура как код) переводит управление облаком на рельсы классической разработки ПО. Вся архитектура дата-центра описывается декларативным кодом в Git-репозитории, проходит обязательное Code Review в Merge Request и автоматически воплощается в «железе» с помощью индустриального стандарта — инструмента Terraform (или его полностью открытого форка OpenTofu).

    Блок 1. Принципы IaC и концепция Immutable Infrastructure

    1.1. Декларативный подход против Императивного

    Все инструменты автоматизации в инженерии делятся на две фундаментальные парадигмы в зависимости от того, как вы формулируете задачу компьютеру:

    Характеристика Императивный подход (Отвечает на вопрос «КАК сделать?») Декларативный подход (Отвечает на вопрос «ЧТО получить в итоге?»)
    Примеры инструментов Скрипты на Bash/Python, консольные утилиты облаков (yc compute instance create, aws ec2 run-instances) Terraform / OpenTofu, манифесты Kubernetes, Docker Compose
    Механика работы Инженер пишет пошаговый алгоритм команд. Если запустить такой скрипт второй раз подряд — он либо упадет с фатальной ошибкой «Сеть с таким именем уже существует», либо создаст в облаке вторую дублирующую копию серверов, удвоив ваш счет за облако! Инженер описывает желаемое конечное состояние системы (например: «В облаке должна быть одна сеть и 3 виртуальные машины с 4 ГБ RAM»). Инструмент сам считывает текущее состояние облака, вычисляет разницу (дельту) и выполняет ровно те вызовы API, которых не хватает для достижения цели.
    Идемпотентность Отсутствует по умолчанию — требует ручного написания сотен строк проверок if/else перед каждой командой. Встроена в саму архитектуру: если реальное облако уже совпадает с вашим кодом, повторный запуск ничего не тронет и мгновенно вернет статус No changes.

    1.2. Концепция Immutable Infrastructure (Неизменяемая инфраструктура): Pets vs Cattle

    Переход к облакам и Terraform изменил само отношение инженеров к серверам, что лучше всего описывается классической метафорой Pets vs Cattle (Домашние питомцы против Стада):

    • Серверы как «Домашние питомцы» (Pets — изменяемая инфраструктура): В традиционном администрировании каждый сервер был уникален, получал собственное имя в честь греческих богов или планет (zeus, apollo), и администраторы годами вручную заходили на него по SSH, обновляли пакеты и правили конфиги на живую. Неизбежным следствием этого становился Configuration Drift (Дрейф конфигурации) — ситуация, когда два сервера на бумаге числятся одинаковыми, но по факту работают совершенно по-разному из-за забытых ручных правок. Выход из строя такого уникального сервера превращался для компании в катастрофу.
    • Серверы как «Стадо» (Cattle — неизменяемая инфраструктура / Immutable Infrastructure): В современной архитектуре серверы обезличены, имеют серийные номера (app-node-01, app-node-02) и штампуются по единому шаблону Terraform.

    Золотое правило Immutable Infrastructure: после того как виртуальная машина или контейнер созданы, мы никогда не заходим на них руками для обновления ОС или софта. Если нужно обновить ядро Linux или поменять конфигурацию — мы меняем версию образа в коде Terraform, после чего автоматика создает рядом новую чистую виртуальную машину, переключает на неё балансировщик нагрузки, а старую машину безжалостно уничтожает!

    Блок 2. Архитектура Terraform и синтаксис языка HCL

    2.1. Внутреннее устройство Terraform и 4 шага жизненного цикла

    Terraform написан на языке Go и архитектурно разделен на два независимых компонента: 1. Terraform Core (Ядро): Отвечает за парсинг ваших конфигурационных файлов на декларативном языке HCL (HashiCorp Configuration Language), строит направленный граф зависимостей между ресурсами (понимая, что сначала нужно создать сеть, затем подсеть, и только потом — сервер внутри неё) и сверяет желаемую картину с файлом текущего состояния (terraform.tfstate). 2. Providers (Провайдеры): Сменные бинарные плагины, которые скачиваются из реестра при инициализации проекта. Ядро Terraform не знает, как устроен AWS или Yandex Cloud — эту работу делают провайдеры (yandex, aws, google, kubernetes, docker, gitlab), которые переводят абстрактные команды ядра на язык конкретных REST API запросов к целевой платформе.

    [terraform init] ──► [terraform plan] ──► [terraform apply] ──► [terraform destroy]
 Скачивание плагинов   Сухой прогон (Diff)   Создание ресурсов     Полное удаление стенда

    Работа инженера с любым изменением в Terraform всегда идет по строгому четырехшаговому циклу:

    • terraform init: Первая команда в любом проекте. Инициализирует рабочую папку, подключается к удаленному хранилищу состояния (Backend) и автоматически скачивает бинарные плагины всех указанных в коде провайдеров и модулей.
    • terraform fmt и terraform validate: Встроенная гигиена кода — fmt автоматически выравнивает все отступы в файлах .tf по единому стандарту, а validate проверяет синтаксическую корректность связей и типов без обращения к сети.
    • terraform plan: Главный предохранитель инженера! Эта команда ничего не меняет в облаке (Dry Run): она опрашивает API провайдера, сверяет реальность с вашим кодом и выводит в терминал детальный план предстоящих операций. Внимательно читайте символы слева от каждого ресурса в выводе plan:
    • + create (зеленый плюс) — в облаке будет создан новый объект.
    • ~ update in-place (желтая тильда) — безопасное изменение параметров существующего объекта на лету без его перезагрузки и удаления (например, добавление нового правила в фаервол или переименование тега).
    • -/+ destroy and then create replacement (красный минус/плюс) — ВНИМАНИЕ, ОПАСНОСТЬ! Вы изменили фундаментальный параметр ресурса, который облако не умеет менять на лету (например, сменили зону доступности, ID подсети или базовый образ диска ВМ). Чтобы выполнить вашу просьбу, Terraform полностью уничтожит существующий сервер и создаст на его месте новый!
    • terraform apply: Применяет утвержденный план, выполняя реальные API-вызовы к облаку и записывая новые идентификаторы созданных объектов в файл состояния.

    2.2. Базовые строительные блоки языка HCL

    Код проекта разбивается на логические файлы с расширением .tf (при запуске Terraform автоматически склеивает и читает все файлы .tf в текущей папке как единое целое). Разберем четыре главные конструкции языка HCL на примере развертывания облачной сети в Yandex Cloud:

    # 1. Блок terraform: фиксируем минимальную версию самого бинарника и точные версии плагинов провайдеров
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      version = "~> 0.120.0"
    }
  }
}

# 2. Блок provider: настройка подключения к целевому облаку
# (Токены авторизации никогда не пишутся в коде — они считываются из переменных окружения!)
provider "yandex" {
  zone = var.default_zone
}

# 3. Блок data (Источник данных / Data Source):
# НИЧЕГО не создает в облаке! Он работает только на чтение (Read-Only): делает запрос к API провайдера,
# чтобы узнать ID уже существующего объекта (например, найти свежий ID официального образа Ubuntu 24.04)
data "yandex_compute_image" "ubuntu_2404" {
  family = "ubuntu-2404-lts"
}

# 4. Блок resource (Ресурс) — главная рабочая лошадка: СОЗДАЕТ, изменяет и удаляет объект в облаке.
# Строгий синтаксис: resource "<ТИП_РЕСУРСА_ПРОВАЙДЕРА>" "<ВАШЕ_ЛОКАЛЬНОЕ_ИМЯ_В_КОДЕ>"
resource "yandex_vpc_network" "app_net" {
  name = "production-vpc"
}

resource "yandex_vpc_subnet" "app_subnet" {
  name           = "production-subnet-a"
  zone           = var.default_zone
  # Неявная связь (Implicit Dependency): мы ссылаемся на атрибут .id ресурса сети, объявленного выше.
  # Благодаря этой ссылке ядро Terraform само построит граф и поймет, что подсеть нельзя создавать,
  # пока облако не завершит создание родительской сети yandex_vpc_network.app_net!
  network_id     = yandex_vpc_network.app_net.id
  v4_cidr_blocks = ["10.10.1.0/24"]
}

    Блок 3. Управление состоянием инфраструктуры (State) и защита от дрейфа

    3.1. Анатомия файла terraform.tfstate и почему его категорически нельзя коммитить в Git

    Зададимся архитектурным вопросом: в облачном аккаунте компании могут крутиться сотни виртуальных машин. Откуда Terraform при запуске знает, какие именно машины создал он по вашему коду, а какие были созданы соседним отделом аналитики?

    Для этого существует сердце Terraform — JSON-файл состояния terraform.tfstate. В момент первого terraform apply ядро записывает в этот файл полную карту соответствия между вашим локальным именем ресурса в коде (yandex_vpc_network.app_net) и реальным физическим идентификатором, который вернуло облако (enp9abc12345), а также сохраняет все текущие параметры созданного объекта.

    По умолчанию этот файл создается прямо в вашей рабочей папке на ноутбуке. Однако в реальной работе хранить terraform.tfstate локально и тем более коммитить его в Git — грубейшая ошибка безопасности и архитектуры по двум причинам:

    1. Утечка всех секретов в открытом виде (Plaintext Secrets): Даже если вы пометили переменную пароля базы данных в коде защитным флагом sensitive = true (благодаря чему Terraform аккуратно скрывает пароль звездочками (sensitive value) в выводе терминала), внутри самого JSON-файла terraform.tfstate абсолютно все пароли, приватные ключи и токены записываются чистым незашифрованным текстом! Отправка tfstate в Git равносильна публикации всех паролей компании.
    2. Коллизии при командной работе (Race Condition): Представьте, что два DevOps-инженера склонировали репозиторий и одновременно со своих ноутбуков запустили terraform apply. Каждый процесс опирается на свою локальную копию стейта, они одновременно начинают дергать API облака, перетирают изменения друг друга и оставляют инфраструктуру в разрушенном неконсистентном состоянии.

    Промышленное решение: Remote State в S3 + Механизм блокировок (State Locking)

    В профессиональной эксплуатации файл состояния никогда не хранится на дисках инженеров — для него настраивается удаленный бэкенд (Remote Backend) в защищенном объектном хранилище S3 (Yandex Object Storage, AWS S3, локальный MinIO или встроенный GitLab Managed Terraform State).

    Это решает обе проблемы одновременно: * Стейт хранится в единственном экземпляре в зашифрованном бакете с включенным версионированием (историей ревизий файла). * Включается механизм блокировки состояния (State Locking): как только Инженер №1 запускает terraform apply, Terraform мгновенно создает рядом со стейтом в бакете специальный файл-замок (.tflock) с именем инженера и ID операции. Если через секунду Инженер №2 (или пайплайн CI/CD) попытается запустить параллельный apply, Terraform увидит замок и вежливо заблокирует запуск с сообщением Error acquiring the state lock, гарантируя стопроцентную целостность облака!

    terraform {
  backend "s3" {
    endpoints = {
      s3 = "[https://storage.yandexcloud.net](https://storage.yandexcloud.net)"
    }
    bucket = "my-company-tfstate-prod"
    region = "ru-central1"
    key    = "infra/network/terraform.tfstate"

    # Активация нативной файловой блокировки стейта (.tflock прямо внутри S3-бакета)
    use_lockfile                = true
    skip_region_validation      = true
    skip_credentials_validation = true
    skip_requesting_account_id  = true
  }
}

    3.2. Предотвращение и обнаружение дрейфа конфигураций (Drift Detection)

    Даже когда вся инфраструктура описана в Terraform, в компании может случиться инцидент: ночью во время аварии дежурный администратор зашел руками в веб-консоль облака и в обход Git открыл дополнительный порт в фаерволе или вручную увеличил объем оперативной памяти сервера с 8 до 16 ГБ. В этот момент реальность в облаке разошлась с кодом в Git — возник дрейф конфигурации (Configuration Drift).

    Чтобы инфраструктура не расползалась, применяются два эшелона защиты:

    1. Автоматический радар дрейфа (terraform plan -detailed-exitcode по расписанию в CI/CD): В GitLab CI настраивается регламентная задача (Scheduled Pipeline), которая каждый час в фоновом режиме запускает проверку terraform plan -detailed-exitcode. Флаг -detailed-exitcode меняет логику кодов возврата утилиты:
    2. Код возврата 0 — план пуст (No changes), реальное облако на 100% соответствует коду в Git.
    3. Код возврата 1 — произошла техническая ошибка связи с API или синтаксический сбой.
    4. Код возврата 2 — ОБНАРУЖЕН ДРЕЙФ (есть несанкционированные расхождения между облаком и кодом)! Пайплайн перехватывает код 2 и немедленно бьет тревогу в рабочий чат команды, прикладывая точный список того, что было изменено в облаке руками.
    5. Предохранители жизненного цикла (lifecycle) в коде ресурсов: Чтобы защитить особо критичные Stateful-объекты (боевые базы данных, S3-бакеты с документами клиентов) от случайного пересоздания или удаления из-за неосторожной правки кода, внутрь ресурса встраивают жесткий блок lifecycle: 
      lifecycle {
  # Железный предохранитель: при любой попытке удалить или пересоздать (-/+) этот ресурс
  # Terraform немедленно прервет выполнение с фатальной ошибкой!
  prevent_destroy = true

  # Приказать Terraform игнорировать внешние изменения конкретных второстепенных атрибутов
  ignore_changes  = [tags, labels]
}

    Блок 4. Гибкость кода: Переменные, Секреты, Циклы и Принцип DRY (Модули)

    4.1. Входные переменные (variables), Выходные данные (outputs) и защита секретов (sensitive)

    Хардкодить IP-адреса, размеры дисков и имена окружений прямо внутри ресурсов — антипаттерн. Чтобы один и тот же код можно было гибко параметризовать, в Terraform используются три типа переменных и выводов:

    # 1. Входные переменные (обычно выносятся в файл variables.tf) с автоматической валидацией!
variable "environment" {
  description = "Имя целевого контура окружения (dev, staging, prod)"
  type        = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Ошибка: допустимые значения для environment — только dev, staging или prod!"
  }
}

variable "db_password" {
  description = "Мастер-пароль для создаваемой СУБД"
  type        = string
  # Флаг sensitive = true маскирует значение переменной во всех логах terraform plan и apply!
  sensitive   = true
}

# 2. Локальные вычисляемые константы (locals) — позволяют один раз сформировать сложный префикс
# или набор общих тегов и переиспользовать их во всех ресурсах файла без дублирования
locals {
  name_prefix = "cluster-${var.environment}"
  common_tags = {
    managed_by  = "terraform"
    environment = var.environment
  }
}

# 3. Выходные значения (outputs.tf) — возвращают динамические реквизиты после завершения apply
# (например, сгенерированный облаком публичный IP-адрес сервера или DNS-имя базы данных)
output "load_balancer_public_ip" {
  description = "Внешний IP-адрес созданного балансировщика нагрузки"
  value       = yandex_compute_instance.balancer.network_interface[0].nat_ip_address
}

    Как безопасно передавать секретные переменные (db_password) при запуске? Никогда не записывайте пароли в текстовые файлы параметров terraform.tfvars в репозитории! Terraform умеет автоматически считывать значения любых объявленных variable "<имя>" напрямую из переменных окружения операционной системы, если перед именем переменной добавить специальный префикс TF_VAR_: 

    export TF_VAR_db_password="MySuperSecretProdPassword"
terraform apply

    4.2. Генерация множества ресурсов без копипасты: count против for_each

    Представьте, что вам нужно создать 5 виртуальных машин или 4 микросервисных контейнера с разными портами. Копировать блок resource пять раз подряд — нарушение принципа DRY. В языке HCL для динамического размножения ресурсов предусмотрены два итератора, выбор между которыми имеет огромное значение при последующей эксплуатации:

    • count (Простой числовой индекс): Вы пишете count = 3, и Terraform создает массив однотипных ресурсов с числовыми индексами: node[0], node[1], node[2].
    • Скрытая ловушка count: если вы передали в count список из трех серверов ["auth", "billing", "front"], а через месяц решили удалить средний сервер "billing", то сервер "front" сдвинется в списке с индекса [2] на индекс [1] — и Terraform уничтожит и пересоздаст работающий сервер "front" просто из-за сдвига нумерации массива!
    • for_each (Итерация по ключу словаря — промышленный стандарт): Принимает на вход ассоциативный словарь (map) или множество уникальных строк (set). Каждый создаваемый ресурс адресуется не безликой цифрой, а осмысленным текстовым ключом словаря (each.key), например docker_container.service["auth-api"] и docker_container.service["billing-api"]. Теперь вы можете свободно удалять или добавлять любые элементы в середину словаря — соседние ресурсы останутся абсолютно нетронутыми!
    variable "microservices" {
  type = map(object({
    port     = number
    replicas = number
  }))
  default = {
    "auth-api"    = { port = 8001, replicas = 2 }
    "billing-api" = { port = 8002, replicas = 1 }
  }
}
# При итерации через for_each = var.microservices внутри ресурса доступны:
# each.key (имя сервиса, например "auth-api") и each.value.port (значение порта 8001)

    4.3. Архитектура переиспользуемых модулей Terraform (Modules — Принцип DRY)

    По мере роста компании инфраструктурный код разрастается до тысяч строк. Более того, бизнесу требуется иметь как минимум два идентичных по архитектуре контура — предрелизный staging (на небольших дешевых виртуальных машинах) и боевой production (на мощных отказоустойчивых серверах). Если просто скопировать файлы .tf из папки staging в папку production, уже через месяц они безнадежно разъедутся.

    Для решения этой задачи в Terraform используется концепция Модулей (Modules) — полный аналог функций или подключаемых библиотек в программировании: 1. В папке modules/ мы один раз разрабатываем универсальные «строительные блоки» нашей архитектуры (например, модуль сети modules/network и модуль кластера приложений modules/app_tier) со своими входными переменными variables.tf и выходными данными outputs.tf. 2. А в папках конкретных окружений (environments/staging и environments/production) вообще нет сырых ресурсов — там лежат короткие файлы main.tf, которые просто вызывают готовые модули через блок module "...", передавая им разные лимиты памяти и портов!

    terraform-infra/
├── modules/                      # Универсальные переиспользуемые чертежи (Принцип DRY)
│   ├── network/                  # Модуль создания изолированной сети
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── app_tier/                 # Модуль кластера микросервисов (на базе for_each)
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
└── environments/                 # Конкретные живые контуры компании
    ├── staging/
    │   ├── backend.tf            # Настройка хранения стейта Staging в S3
    │   └── main.tf               # Вызывает модули с малыми ресурсами (64 МБ RAM)
    └── production/
        ├── backend.tf            # Настройка хранения стейта Prod в S3
        └── main.tf               # Вызывает те же модули с боевыми ресурсами (1024 МБ RAM)

    🛠 Практический проект Модуля 8: Разработка модульной архитектуры Terraform с хранением State в S3 и защитой от Drift

    Чтобы ты мог отработать все промышленные практики Terraform прямо сейчас на своей машине — бесплатно, без регистрации в платных облаках и без привязки банковской карты, — мы построим полноценный локальный облачный стенд:

    1. Мы развернем локальное S3-совместимое объектное хранилище MinIO (которое работает по тому же самому протоколу AWS S3 API, что и Yandex Object Storage) и создадим в нем версионированный бакет tfstate-bucket для удаленного хранения terraform.tfstate.
    2. Разработаем с нуля два универсальных модуля Terraform по принципу DRY (modules/network и modules/app_tier с использованием итератора for_each и защищенных переменных sensitive), управляющих инфраструктурой через официальный провайдер kreuzwerker/docker.
    3. Развернем окружение staging, убедимся, что стейт безопасно сохранился в S3, а затем проведем боевые учения по обнаружению и автоматическому устранению дрейфа конфигурации (Configuration Drift)!

    Этап 1. Установка Terraform и подъем объектного S3-хранилища для Remote State

    1. Проверим наличие бинарника terraform в системе (если он еще не установлен, скрипт за 10 секунд скачает и установит официальный релиз напрямую из быстрого зеркала Yandex Cloud):
    if ! command -v terraform &> /dev/null; then
    echo "Устанавливаем Terraform..."
    ARCH=$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')
    curl -fsSL "[https://hashicorp-releases.yandexcloud.net/terraform/1.9.8/terraform_1.9.8_linux_$](https://hashicorp-releases.yandexcloud.net/terraform/1.9.8/terraform_1.9.8_linux_$){ARCH}.zip" -o /tmp/tf.zip
    sudo unzip -o /tmp/tf.zip -d /usr/local/bin/ && rm /tmp/tf.zip
fi
terraform version
    1. Создадим рабочую директорию ~/terraform-practice, запустим сервер объектного хранилища S3 (MinIO) и с помощью консольного клиента mc автоматически создадим внутри него бакет tfstate-bucket с включенным версионированием истории файлов:
    mkdir -p ~/terraform-practice && cd ~/terraform-practice

docker run -d \
  --name s3-minio \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=tf_admin \
  -e MINIO_ROOT_PASSWORD=TfSecretKey2026 \
  minio/minio server /data --console-address ":9001"

sleep 3
# Инициализируем бакет tfstate-bucket и включаем защиту версионирования (mc version enable)
docker run --rm --network host --entrypoint /bin/sh minio/mc -c "
  mc alias set local [http://127.0.0.1:9000](http://127.0.0.1:9000) tf_admin TfSecretKey2026 &&
  mc mb --ignore-existing local/tfstate-bucket &&
  mc version enable local/tfstate-bucket
"

    Этап 2. Разработка переиспользуемых модулей Terraform (network и app_tier)

    Создадим дерево каталогов для наших модулей и целевого окружения staging:

    mkdir -p ~/terraform-practice/modules/{network,app_tier}
mkdir -p ~/terraform-practice/environments/staging

    1. Проектируем универсальный модуль сети (modules/network):

    Этот модуль принимает имя окружения и CIDR-маску подсети, создает изолированную сеть с метками managed_by = terraform и возвращает её сгенерированный id и name через блок outputs:

    cat << 'EOF' > ~/terraform-practice/modules/network/variables.tf
variable "env_name" {
  description = "Имя контура окружения"
  type        = string
}

variable "subnet_cidr" {
  description = "Подсеть в формате CIDR"
  type        = string
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/network/main.tf
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0.2"
    }
  }
}

resource "docker_network" "vpc_net" {
  name   = "tf-${var.env_name}-vpc"
  driver = "bridge"
  ipam_config {
    subnet = var.subnet_cidr
  }
  labels {
    label = "managed_by"
    value = "terraform"
  }
  labels {
    label = "environment"
    value = var.env_name
  }
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/network/outputs.tf
output "network_id" {
  value = docker_network.vpc_net.id
}

output "network_name" {
  value = docker_network.vpc_net.name
}
EOF

    2. Проектируем модуль кластера приложений (modules/app_tier) с итератором for_each и защитой секретов:

    Обрати внимание на файл outputs.tf этого модуля: с помощью цикла генерации словаря (for k, node in ...) он динамически собирает и возвращает готовую карту всех созданных узлов и их внешних HTTP-ссылок!

    cat << 'EOF' > ~/terraform-practice/modules/app_tier/variables.tf
variable "env_name" {
  type = string
}

variable "network_name" {
  type = string
}

variable "api_secret_token" {
  type      = string
  sensitive = true
}

variable "nodes" {
  description = "Словарь (карта) узлов кластера для динамического развертывания через for_each"
  type = map(object({
    external_port = number
    memory_mb     = number
  }))
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/app_tier/main.tf
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0.2"
    }
  }
}

resource "docker_image" "nginx_img" {
  name         = "nginx:1.27-alpine"
  keep_locally = true
}

# Динамическое создание узлов кластера по ключам словаря var.nodes через итератор for_each
resource "docker_container" "app_node" {
  for_each = var.nodes

  name   = "tf-${var.env_name}-${each.key}"
  image  = docker_image.nginx_img.image_id
  memory = each.value.memory_mb

  # Пробрасываем внутрь узла метаданные и защищенный секретный токен
  env = [
    "ENV_NAME=${var.env_name}",
    "NODE_NAME=${each.key}",
    "API_SECRET_TOKEN=${var.api_secret_token}"
  ]

  ports {
    internal = 80
    external = each.value.external_port
  }

  networks_advanced {
    name = var.network_name
  }

  labels {
    label = "managed_by"
    value = "terraform"
  }
}
EOF

cat << 'EOF' > ~/terraform-practice/modules/app_tier/outputs.tf
output "deployed_endpoints" {
  description = "Карта развернутых узлов кластера и их внешних HTTP-адресов"
  value = {
    for k, node in docker_container.app_node :
    k => "http://localhost:${node.ports[0].external}"
  }
}
EOF

    Этап 3. Сборка окружения staging с подключением удаленного S3 Backend

"
      Ожидаемый результат: Клиент S3 показывает лежащий в хранилище актуальный файл terraform.tfstate!

    2. Проверка доступности развернутых узлов по данным из terraform output: 

      terraform output
curl -I http://localhost:8181
curl -I http://localhost:8182
      Ожидаемый результат: Команда terraform output выводит словарь URL-адресов обеих нод (web-01 и web-02), и обе они отвечают HTTP/1.1 200 OK.

    3. Боевое учение: Симуляция дрейфа конфигурации (Configuration Drift) и работа радара detailed-exitcode! Представим, что кто-то зашел на сервер руками в обход Terraform и случайно (или злонамеренно) удалил боевой узел tf-staging-web-02: 

      # Вручную ломаем инфраструктуру в обход IaC (уничтожаем второй узел кластера)
docker rm -f tf-staging-web-02

# Запускаем радар обнаружения дрейфа с флагом -detailed-exitcode
terraform plan -detailed-exitcode || echo "🚨 ТРЕВОГА: ОБНАРУЖЕН ДРЕЙФ КОНФИГУРАЦИИ В ОБЛАКЕ (Exit Code 2)!"
      Ожидаемый результат: Terraform мгновенно опрашивает систему, сверяет её со стейтом в S3, замечает пропажу узла app_node["web-02"], показывает план его восстановления (+ create) и сигнализирует кодом возврата 2!

    4. Автоматическое исправление дрейфа (Self-Healing Infrastructure): Вернем инфраструктуру в эталонное состояние одной командой: 

      terraform apply -auto-approve
docker ps --filter "name=tf-staging"
      Ожидаемый результат: Terraform не тронул работающий первый узел web-01, но за 1 секунду пересоздал и вернул в строй недостающий узел tf-staging-web-02!

    (Для штатной очистки тестового стенда после завершения работы выполни: terraform destroy -auto-approve && docker rm -f s3-minio).
