    Контейнеризация приложений Docker

    Контейнеризация навсегда решила проблему «У меня на ноутбуке всё работало, а на сервере упало!». Вместо того чтобы вручную устанавливать на сервер нужную версию Python/Node.js/Go, системные библиотеки и зависимости, мы упаковываем приложение вместе со всем его окружением в единый неизменяемый артефакт — Docker-образ (Image), который гарантированно одинаково запустится на любом Linux-сервере.

    Блок 1. Архитектура контейнеров и пространства имён Linux

    1.1. Как устроен контейнер под капотом (Namespaces, cgroups, OverlayFS)

    В физическом смысле «контейнера» в ядре Linux не существует. Контейнер — это обычный изолированный процесс на хостовой ОС, созданный с помощью трёх технологий ядра Linux:

    1. Пространства имён (Namespaces) — изолируют видимость:

    2. pid: Процесс внутри контейнера видит себя как PID 1 и не видит остальные процессы сервера.

    3. net: Контейнер получает собственный виртуальный сетевой интерфейс (eth0), свой IP-адрес, свою таблицу маршрутизации и свои порты.

    4. mnt: Своя изолированная корневая файловая система /.

    5. uts: Своё собственное имя хоста (hostname).

    6. ipc и user: Изоляция общей памяти и маппинг идентификаторов пользователей (UID/GID).

    7. Контрольные группы (cgroups) — ограничивают ресурсы:

    8. Не дают одному контейнеру «съесть» всю оперативную память или 100% процессора хоста.

    9. Слоёная файловая система (UnionFS / OverlayFS):

    10. Образ контейнера состоит из неизменяемых (Read-Only) слоёв, наложенных друг на друга. Когда контейнер запускается, поверх них создаётся один тонкий записываемый слой (Read-Write Container Layer).

    11. Если 10 контейнеров запущены из одного образа Ubuntu + Python (весом 300 МБ), на диске эти 300 МБ хранятся только в одном экземпляре, а каждый контейнер занимает лишь пару килобайт под свои изменения (механизм Copy-on-Write).

    1.2. Архитектура Docker Engine

    Docker работает по клиент-серверной архитектуре:

    • Docker CLI (docker): Консольный клиент, в котором вы вводите команды. Он отправляет REST API-запросы демону через UNIX-сокет /var/run/docker.sock.

    • Docker Daemon (dockerd): Фоновая служба, которая управляет образами, сетями и томами.

    • containerd и runc: Низкоуровневые компоненты (по стандарту OCI), которым dockerd делегирует непосредственный запуск контейнеров через системные вызовы ядра Linux.

    1.3. Базовое управление контейнерами и образами

    Команда Описание
    docker run -d --name web -p 8080:80 nginx:alpine Запустить контейнер в фоне (-d), дать имя web, пробросить порт 8080 хоста на порт 80 контейнера (-p).
    docker ps / docker ps -a Показать запущенные контейнеры / показать вообще все контейнеры (включая остановленные).
    docker logs -f --tail 100 web Читать логи контейнера (stdout/stderr) в реальном времени (-f), начиная с последних 100 строк.
    docker exec -it web /bin/sh Зайти внутрь работающего контейнера в интерактивный терминал (-i и -t) для диагностики.
    docker stats Живой мониторинг потребления CPU, RAM и сети всеми контейнерами (аналог htop).
    docker inspect web Вывести полный JSON-паспорт контейнера (IP-адрес, переменные, примонтированные тома, лимиты).
    docker stop web / docker kill web Корректно остановить (SIGTERM $\rightarrow$ пауза 10 сек $\rightarrow$ SIGKILL) / мгновенно убить (SIGKILL).
    docker system df / docker system prune -a Посмотреть, сколько места занимают образы и кэш / очистить все неиспользуемые контейнеры, сети и образы.

    Блок 2. Создание Dockerfile, параметризация и реестры

    2.1. Ключевые директивы Dockerfile

    • FROM: Задает базовый образ (например, python:3.12-slim или alpine:3.20).
    • WORKDIR: Устанавливает рабочую директорию внутри контейнера (все последующие команды RUN, COPY, CMD будут выполняться в ней). Никогда не используйте RUN cd /app — используйте WORKDIR /app.
    • COPY vs ADD:
    • COPY src dest — простое и прозрачное копирование файлов с хоста в образ. Используйте в 99% случаев.

    • ADD — умеет автоматически распаковывать локальные .tar.gz-архивы и скачивать файлы по URL (считается неявным поведением).

    • RUN: Выполняет команду во время сборки образа и фиксирует результат как новый слой.

    • ARG vs ENV (Параметризация образов):

    • ARG — переменная, доступная только во время сборки (docker build --build-arg). В запущенном контейнере её нет (например, версия пакета ARG APP_VERSION=1.0.0).

    • ENV — переменная окружения, которая сохраняется внутри готового образа и доступна работающему приложению (docker run -e PORT=9000).

    • EXPOSE: Документирует, какой порт слушает приложение внутри контейнера (сам по себе порт наружу не открывает!).

    • ENTRYPOINT и CMD: Определяют команду, которая запустится как PID 1 при старте контейнера:
    • Всегда пишите их в JSON/exec-форме (["python3", "app.py"]), а не в shell-форме (python3 app.py). В shell-форме PID 1 займет оболочка /bin/sh -c, которая **не передает сигнал SIGTERM** вашему приложению — в итоге контейнер не сможет корректно завершаться и будет каждый раз зависать на 10 секунд при остановке!

    2.2. Кэширование слоев и оптимизация размера образа

    Каждая инструкция RUN, COPY, ADD создает новый слой. Если при повторной сборке файлы в COPY не изменились, Docker берет этот слой и все последующие из кэша за 0.1 секунды. Но как только один слой изменился — весь кэш ниже него сбрасывается.

    ❌ Плохой Dockerfile (Антипаттерн — 1.1 ГБ, долгая сборка):

    FROM ubuntu:24.04
WORKDIR /app
# ОШИБКА 1: Копируем весь код ДО установки зависимостей. 
# Любая правка в коде сбросит кэш, и pip install будет качать пакеты заново!
COPY . .
# ОШИБКА 2: Раздельные RUN и неочищенный кэш apt остаются в слоях навсегда
RUN apt-get update
RUN apt-get install -y python3 python3-pip gcc
RUN pip install -r requirements.txt
CMD python3 main.py

    ✅ Оптимизированный Multi-Stage Dockerfile (60 МБ, мгновенная пересборка)

    :

    Multi-stage build (Многоэтапная сборка) позволяет в первом временном образе (builder) скомпилировать код со всеми тяжелыми компиляторами (gcc, maven, go, npm), а в финальный чистый образ скопировать только готовый бинарник или зависимости.

    # --- Этап 1: Сборка зависимостей (Builder) ---
FROM python:3.12-slim AS builder
WORKDIR /build

# Сначала копируем ТОЛЬКО файл зависимостей (слой закэшируется!)
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# --- Этап 2: Финальный легковесный образ (Runtime) ---
FROM python:3.12-slim
WORKDIR /app

# Параметризация сборки и окружения
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION} \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# Копируем установленные библиотеки из этапа builder
COPY --from=builder /install /usr/local

# Копируем исходный код в самом конце
COPY src/ ./src/

EXPOSE 8000
ENTRYPOINT ["python3", "src/app.py"]

    Обязательный файл .dockerignore: Как и .gitignore, создавайте в корне проекта файл .dockerignore и добавляйте туда .git, .env, venv, node_modules, *.log, чтобы они не улетали в контекст сборки и не попадали внутрь образа!

    2.3. Управление реестрами образов (Docker Registries)

    Собранные образы хранятся в реестрах (Docker Hub, GitLab Container Registry, GitHub Container Registry ghcr.io, Yandex Container Registry).

    Полное имя (тег) образа всегда имеет структуру: [АДРЕС_РЕЕСТРА]/[ПРОЕКТ_ИЛИ_ЛОГИН]/[ИМЯ_СЕРВИСА]:[ВЕРСИЯ] (например: [registry.gitlab.com/myteam/backend-api:1.2.4](https://registry.gitlab.com/myteam/backend-api:1.2.4)).

    Правило продакшена: Никогда не используйте тег :latest в продакшене! Тег :latest перезаписывается при каждой сборке — вы не поймете, какая именно версия кода сейчас запущена, и не сможете быстро сделать откат (rollback). Всегда используйте фиксированные версии (:1.2.4 или короткий SHA коммита :a1b2c3d).

    # Авторизоваться в реестре
docker login registry.gitlab.com

# Собрать образ с двумя тегами (конкретная версия и latest) и передать build-arg
docker build --build-arg APP_VERSION=1.2.0 -t myuser/myapp:1.2.0 -t myuser/myapp:latest .

# Отправить образ в удаленный реестр
docker push myuser/myapp:1.2.0

    Блок 3. Сети и постоянные тома (Volumes) в Docker

    3.1. Хранение данных: Volumes vs Bind Mounts

    По умолчанию все файлы, созданные внутри контейнера, живут в его верхнем Read-Write слое и бесследно исчезают при удалении контейнера (docker rm). Чтобы сохранять данные (базы данных, загруженные файлы), используют монтирование:

    1. Docker Volume (Именованный том) — выбор для продакшена:

    2. Управляется самим Docker (хранится в /var/lib/docker/volumes/). Изолирован от хоста, легко бэкапится и безопасно подключается к контейнерам.

    docker volume create pg_data
docker run -d --name db -v pg_data:/var/lib/postgresql/data postgres:16-alpine
    1. Bind Mount (Прямой проброс папки хоста):
    2. Монтирует конкретный файл или папку с сервера напрямую внутрь контейнера. Удобно для проброса конфигурационных файлов (nginx.conf, только для чтения :ro) или кода при локальной разработке.
    docker run -d --name proxy -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro nginx:alpine
    1. tmpfs Mount:
    2. Монтирует временную папку прямо в оперативную память (RAM) хоста. Идеально для хранения временных чувствительных данных или кэша, который не должен попадать на диск.

    3.2. Изолированные сети и взаимодействие контейнеров

    В Docker есть несколько сетевых драйверов:

    • bridge (По умолчанию): Создает виртуальный сетевой мост (docker0 на хосте). Контейнеры получают внутренние IP (например, 172.17.0.2) и выходят в интернет через NAT (iptables).

    • User-Defined Bridge (Пользовательская сеть) — стандарт работы:

    • В стандартном мосту bridge контейнеры видят друг друга только по IP-адресам.

    • Но если создать свою изолированную сеть (docker network create), Docker поднимает внутри неё встроенный DNS-сервер! Контейнеры в одной пользовательской сети могут обращаться друг к другу просто по имени контейнера (например, http://backend-api:8000 или postgres://db:5432)!

    • host (--network host): Убирает сетевую изоляцию — контейнер использует сетевую карту самого сервера напрямую (максимальная производительность, нет NAT).

    • none (--network none): Полное отключение сети у контейнера (только интерфейс lo).
    # Создать изолированную сеть для нашего проекта
docker network create app-net

# Запустить Redis в этой сети (порт наружу на хост НЕ пробрасываем — он доступен только внутри сети!)
docker run -d --name redis-cache --network app-net redis:7-alpine

# Запустить второй контейнер в той же сети и проверить связь по имени "redis-cache"
docker run --rm --network app-net alpine ping -c 2 redis-cache

    Блок 4. DevSecOps: Безопасный запуск, секреты и проверка на уязвимости

    4.1. Безопасный запуск компонентов (Hardening контейнеров)

    По умолчанию процесс внутри контейнера запускается от пользователя root (UID 0). Поскольку ядро у контейнера и у хоста общее, при обнаружении уязвимости в приложении или ядре злоумышленник может совершить Container Escape и получить права root на всем физическом сервере!

    4 золотых правила защиты контейнера:

    1. Запуск от непривилегированного пользователя (USER): Всегда создавайте в Dockerfile системного пользователя без прав root и переключайтесь на него перед запуском приложения:
    RUN groupadd -r appgroup && useradd -r -g appgroup -u 10001 appuser
USER 10001:10001
    1. Файловая система только для чтения (--read-only): Запускайте контейнер с флагом --read-only (а для временных файлов давайте --tmpfs /tmp), чтобы взломщик не смог скачать и записать вредоносный скрипт внутрь контейнера.
    2. Сброс привилегий ядра (--cap-drop=ALL): Отбирайте у контейнера все Linux Capabilities (--cap-drop=ALL и --security-opt=no-new-privileges).
    3. Ограничение ресурсов (--memory, --cpus, --pids-limit): Защищает сервер от утечек памяти и fork-бомб внутри контейнера.

    4.2. Безопасная работа с секретами

    • Никогда не запекайте пароли, токены и приватные ключи внутрь Dockerfile через ENV или ARG! Любой человек может выполнить docker history <image> или docker inspect <image> и увидеть все ваши пароли открытым текстом.

    • Как передавать секреты правильно:

    • Во время запуска (Runtime): Передавать переменные окружения снаружи через --env-file .env или монтировать файл с секретом в память контейнера (в Docker Compose / Kubernetes — через механизм secrets).

    • Во время сборки (Build-time): Если при сборке нужно скачать пакет из приватного репозитория по токену, используйте BuildKit Secret Mount (RUN --mount=type=secret,id=my_token ...) — такой секрет монтируется в оперативную память только на одну секунду выполнения команды и гарантированно не попадает в слои образа.

    4.3. Проверка образов на уязвимости (Vulnerability Scanning — Trivy)

    Даже если ваш собственный код идеален, базовый образ (например, python:3.9 или debian) может содержать десятки известных уязвимостей (CVE) в системных библиотеках (openssl, curl, libc).

    Индустриальный стандарт для сканирования образов — утилита Trivy от Aqua Security:

    • Проверяет как системные пакеты ОС (apt, apk), так и библиотеки языков программирования (pip, npm, go.mod, pom.xml).
    • Ищет случайно забытые в слоях секреты и ключи.
    # Запустить сканирование образа через сам Docker (без установки Trivy на хост!)
# Проверить только критические (CRITICAL) и высокие (HIGH) уязвимости:
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image --severity HIGH,CRITICAL python:3.12-slim

    🛠 Практический проект Модуля 2: Полный цикл упаковки и защиты приложения

    Мы пройдем полный цикл DevOps-инженера: возьмем исходный код микросервиса на Python, проведем его ревизию, упакуем в оптимизированный Multi-stage образ с непривилегированным пользователем, проверим на уязвимости с помощью Trivy и запустим в связке с Redis внутри изолированной сети с передачей секретов.

    Этап 1. Подготовка исходного кода приложения

    Создай рабочую директорию и файлы микросервиса, который подключается к Redis, проверяет секретный API-ключ и считает количество обращений:

    mkdir -p ~/docker-practice/src && cd ~/docker-practice

# 1. Зависимости приложения
cat << 'EOF' > requirements.txt
flask==3.0.3
redis==5.0.8
gunicorn==23.0.0
EOF

# 2. Исходный код сервиса (src/app.py)
cat << 'EOF' > src/app.py
import os
import socket
from flask import Flask, jsonify, request
import redis

app = Flask(__name__)

REDIS_HOST = os.getenv("REDIS_HOST", "localhost")
REDIS_PORT = int(os.getenv("REDIS_PORT", 6379))
API_SECRET_KEY = os.getenv("API_SECRET_KEY", "not-set")

cache = redis.Redis(host=REDIS_HOST, port=REDIS_PORT, decode_responses=True)

@app.route("/health")
def health():
    return jsonify({"status": "healthy", "hostname": socket.gethostname()}), 200

@app.route("/hit")
def hit():
    client_key = request.headers.get("X-API-Key")
    if client_key != API_SECRET_KEY:
        return jsonify({"error": "Unauthorized: invalid X-API-Key"}), 403
    try:
        count = cache.incr("hits")
        return jsonify({
            "message": "Success",
            "hits": count,
            "container_id": socket.gethostname(),
            "version": os.getenv("APP_VERSION", "unknown")
        }), 200
    except redis.ConnectionError:
        return jsonify({"error": "Redis connection failed"}), 500

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)
EOF

    Этап 2. Настройка .dockerignore и создание защищенного Multi-Stage Dockerfile

    1. Создай файл .dockerignore, чтобы исключить попадание секретов и мусора в образ:
    cat << 'EOF' > .dockerignore
.git
.env
*.env
*.log
__pycache__
README.md
EOF
    1. Создай production-ready Dockerfile с многоэтапной сборкой, параметризацией, встроенным HEALTHCHECK и запуском от non-root пользователя appuser (UID 10001):
    cat << 'EOF' > Dockerfile
# ==========================================
# Stage 1: Builder (сборка зависимостей)
# ==========================================
FROM python:3.12-slim AS builder

WORKDIR /build
COPY requirements.txt .

# Устанавливаем зависимости в отдельную директорию /install без сохранения кэша
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ==========================================
# Stage 2: Production Runtime
# ==========================================
FROM python:3.12-slim

# Параметризация версии при сборке
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION} \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PORT=8000

WORKDIR /app

# Обновляем системные пакеты безопасности и создаем non-root пользователя (UID 10001)
RUN apt-get update && apt-get upgrade -y && \
    rm -rf /var/lib/apt/lists/* && \
    groupadd -r appgroup && \
    useradd -r -g appgroup -u 10001 -s /usr/sbin/nologin appuser

# Копируем собранные библиотеки из Stage 1
COPY --from=builder /install /usr/local

# Копируем исходный код и сразу назначаем владельца
COPY --chown=appuser:appgroup src/ ./src/

# Переключаемся на непривилегированного пользователя
USER 10001:10001

EXPOSE 8000

# Встроенная проверка здоровья контейнера средствами Python (без установки лишнего curl!)
HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=3 \
  CMD ["python3", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"]

# Запускаем через промышленный WSGI-сервер gunicorn в exec-форме (PID 1)
ENTRYPOINT ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "src.app:app"]
EOF

    Этап 3. Сборка и сканирование образа на уязвимости через Trivy

    1. Собери образ с передачей параметра APP_VERSION=1.0.5:
    docker build --build-arg APP_VERSION=1.0.5 -t hit-counter:1.0.5 .
    1. Проверь размер собранного образа и его слои:
    docker images hit-counter:1.0.5
docker history hit-counter:1.0.5
    1. Просканируй свой образ сканером уязвимостей Trivy на наличие критических CVE и забытых секретов:
    docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image --severity HIGH,CRITICAL hit-counter:1.0.5

    Этап 4. Изолированная сеть, том данных и безопасный запуск с секретами

    1. Создай изолированную сеть backend-net и постоянный том redis-data:
    docker network create backend-net
docker volume create redis-data
    1. Запусти контейнер базы Redis в этой сети с подключением тома (обрати внимание: мы не публикуем порт 6379 на хост — база полностью закрыта от внешнего мира и доступна только внутри backend-net!):
    docker run -d \
  --name redis-db \
  --network backend-net \
  -v redis-data:/data \
  --restart unless-stopped \
  redis:7-alpine redis-server --appendonly yes
    1. Создай локальный файл .env с секретным ключом на хосте (благодаря .dockerignore и .gitignore он никогда не попадет ни в образ, ни в Git):
    cat << 'EOF' > .env
REDIS_HOST=redis-db
REDIS_PORT=6379
API_SECRET_KEY=ProdSuperSecretToken999
EOF
chmod 600 .env
    1. Запусти наше приложение в максимально защищенном режиме (Read-Only файловая система, сброс привилегий ядра --cap-drop=ALL, лимит памяти 128 МБ, передача секретов через --env-file):
    docker run -d \
  --name hit-app \
  --network backend-net \
  --env-file .env \
  -p 8080:8000 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --memory="128m" \
  --cpus="0.5" \
  --restart unless-stopped \
  hit-counter:1.0.5

    ✅ Чек-лист самопроверки по Модулю 2

    Выполни 5 проверочных шагов, чтобы убедиться, что весь стек работает по стандартам DevSecOps:

    1. Проверка статуса healthy: Подожди 15 секунд и выполни: 
      docker ps

    Ожидаемый результат: В колонке STATUS у контейнера hit-app горит пометка (healthy). 2. Проверка работы под non-root пользователем:

    docker exec hit-app id

    Ожидаемый результат: uid=10001(appuser) gid=10001(appgroup) groups=10001(appgroup). 3. Проверка защиты Read-Only файловой системы: Попробуй создать файл внутри контейнера:

    docker exec hit-app touch /app/hacked.txt

    Ожидаемый результат: touch: cannot touch '/app/hacked.txt': Read-only file system (атака заблокирована!). 4. Проверка авторизации по секрету и связки с Redis по внутреннему DNS:

    • Запрос без секретного ключа (должен вернуть 403 Unauthorized): 

      curl -i http://localhost:8080/hit

    • Запрос с правильным ключом из .env (выполни 2–3 раза подряд — счетчик hits в Redis будет увеличиваться!): 

      curl -H "X-API-Key: ProdSuperSecretToken999" http://localhost:8080/hit

    • Проверка сохранности данных в Volume (redis-data): Удали контейнер redis-db, создай его заново с тем же томом redis-data и снова вызови curl — счетчик hits не сбросится в 1, а продолжит считать с прежнего значения!
