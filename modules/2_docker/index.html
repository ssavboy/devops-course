    Контейнеризация приложений (Docker)

    Десятилетиями главной головной болью при выкатке софта была классическая проблема несовпадения окружений: «У меня на ноутбуке всё работало, а на боевом сервере упало!». Причина всегда крылась в деталях: на ноутбуке разработчика стоял Python 3.12 и свежая системная библиотека libssl, а на продакшен-сервере — Python 3.10, старые пакеты ОС и другие переменные окружения. Попытки вручную синхронизировать десятки серверов приводили к хрупким конфигурациям, которые ломались при любом обновлении.

    Контейнеризация решила эту проблему радикально. Вместо того чтобы доставлять на сервер голый код и пытаться настроить под него операционную систему, мы упаковываем само приложение вместе со всеми его библиотеками, системными зависимостями и конфигурацией в единый неизменяемый артефакт — Docker-образ (Image). Такой образ гарантированно запустится с точностью до байта одинаково и на ноутбуке разработчика, и на сервере тестирования, и в облачном кластере.

    Блок 1. Архитектура контейнеров и пространства имён Linux

    1.1. Как устроен контейнер под капотом (Namespaces, cgroups, OverlayFS)

    Как мы выяснили в нулевом модуле, в физическом смысле никакого объекта «контейнер» в ядре Linux не существует. Когда вы запускаете Docker-контейнер, вы не поднимаете виртуальную машину со своим ядром — вы запускаете обычный изолированный процесс напрямую на хостовой ОС. Иллюзия отдельного выделенного сервера создается совместной работой трёх фундаментальных механизмов ядра Linux:

    1. Пространства имён (Namespaces) — изолируют видимость процесса: Ядро оборачивает процесс в изолированные «капсулы» восприятия:
    2. pid: Процесс внутри контейнера видит себя как главный процесс системы (PID 1) и физически не видит остальные процессы хостового сервера.
    3. net: Контейнер получает собственный независимый сетевой стек — виртуальный интерфейс eth0, внутренний IP-адрес, свою таблицу маршрутизации и собственное пространство портов.
    4. mnt: Процесс получает собственную изолированную корневую файловую систему / и не имеет доступа к дискам хоста.
    5. uts: Позволяет контейнеру иметь собственное имя хоста (hostname), отличное от имени физического сервера.

    6. ipc и user: Изолируют общую межпроцессную память и позволяют сопоставлять (маппить) идентификаторы пользователей UID/GID внутри контейнера с непривилегированными пользователями на хосте.

    7. Контрольные группы (cgroups) — ограничивают аппаратные аппетиты: Если пространства имён отвечают за то, что процесс видит, то cgroups отвечают за то, сколько ресурсов он может потребить[cite: 1, 3]. Они ставят жесткие лимиты и гарантируют, что один контейнер с утечкой памяти не сможет «съесть» всю оперативную память или занять 100% процессорного времени физического сервера, обрушив соседние сервисы.

    8. Слоёная файловая система (UnionFS / OverlayFS) — экономит место и ускоряет старт: Файловая система Docker-образа устроена по принципу слоёного пирога: она состоит из набора неизменяемых (Read-Only) слоёв, наложенных друг на друга. В момент старта контейнера поверх этих застывших слоёв образа монтируется всего один тонкий записываемый слой (Read-Write Container Layer), куда идут все текущие изменения.

    В этом кроется главная инженерная магия эффективности Docker: если вы запустите на сервере 10 контейнеров из одного базового образа Ubuntu + Python весом 300 МБ, эти 300 МБ будут храниться на диске только в одном экземпляре и разделяться между всеми контейнерами в режиме чтения. Сам же запущенный контейнер весит считанные килобайты. А если один из контейнеров захочет изменить какой-то системный файл из нижнего слоя, сработает механизм Copy-on-Write (Копирование при записи): драйвер OverlayFS прозрачно скопирует только этот конкретный файл в верхний записываемый слой данного контейнера и изменит его там, не затрагивая оригинал для остальных девяти соседей.

    1.2. Архитектура Docker Engine

    Сам инструментарий Docker построен по модульной клиент-серверной архитектуре и разделен на три уровня в соответствии с открытыми индустриальными стандартами OCI (Open Container Initiative):

    • Docker CLI (docker): Привычная консольная утилита, в которой вы набираете команды. Сама по себе она не запускает контейнеры — она лишь формирует REST API-запросы и отправляет их демону Docker через локальный защищенный UNIX-сокет /var/run/docker.sock (или по сети).
    • Docker Daemon (dockerd): Фоновая системная служба, которая принимает запросы от CLI, управляет жизненным циклом образов, виртуальными сетями, дисковыми томами и логированием.
    • containerd и runc: Низкоуровневое ядро контейнеризации. Демон dockerd давно не общается с ядром Linux напрямую: он передает задачу службе containerd, а та вызывает легкую консольную утилиту runc, единственная задача которой — обратиться к ядру Linux, создать нужные namespaces и cgroups, запустить внутри них целевой процесс и завершиться. Благодаря этому разделению, даже если вы перезапустите демон dockerd, работающие контейнеры не упадут.

    1.3. Базовое управление контейнерами и образами

    Ниже приведены основные рабочие команды, закрывающие 90% ежедневных задач по управлению и диагностике контейнеров на сервере:

    Команда Инженерное описание и механика работы
    docker run -d --name web -p 8080:80 nginx:alpine Создать и запустить контейнер из образа nginx:alpine в фоновом режиме демона (-d), присвоить ему понятное имя web и пробросить порт 8080 хостовой машины на внутренний порт 80 контейнера (-p).
    docker ps / docker ps -a Вывести список только работающих в данный момент контейнеров / вывести абсолютно все контейнеры в системе, включая остановившиеся и упавшие с ошибкой (Exited).
    docker logs -f --tail 100 web Подключиться к потокам stdout/stderr контейнера web и читать его логи в реальном времени (-f), выведя для контекста последние 100 строк истории (--tail 100).
    docker exec -it web /bin/sh Запустить внутри уже работающего контейнера web дополнительный процесс командной оболочки /bin/sh и подключить к нему интерактивный терминал (-i и -t) для живой отладки изнутри.
    docker stats Открыть живую панель мониторинга потребления ресурсов (CPU, RAM, лимиты памяти, сетевой и дисковый I/O) всеми запущенными контейнерами в реальном времени (аналог htop).
    docker inspect web Вывести исчерпывающий низкоуровневый JSON-паспорт контейнера: его внутренний IP-адрес, пути к логам на хосте, переменные окружения, примонтированные тома и коды завершения (OOMKilled, ExitCode).
    docker stop web / docker kill web Штатно остановить контейнер (посылает SIGTERM, ждет до 10 секунд для Graceful Shutdown и лишь затем добивает через SIGKILL) / мгновенно уничтожить процесс контейнера сигналом SIGKILL.
    docker system df / docker system prune -a Показать сводную статистику занятого дискового пространства (образы, контейнеры, тома, сборочный кэш) / полностью очистить диск от всех остановленных контейнеров, неиспользуемых сетей и висячих образов.

    Блок 2. Создание Dockerfile, параметризация и реестры

    2.1. Ключевые директивы Dockerfile

    Чтобы автоматизировать сборку образа, все шаги описываются декларативно в текстовом сценарии Dockerfile. Каждая директива в нём несет четкую архитектурную нагрузку:

    • FROM: Точка отсчета любого образа — задает базовый родительский образ (например, минималистичный python:3.12-slim или сверхлегкий alpine:3.20).
    • WORKDIR: Создает (если её нет) и устанавливает рабочую директорию внутри контейнера для всех последующих инструкций RUN, COPY, CMD и ENTRYPOINT. Правило хорошего тона: никогда не пишите в Dockerfile RUN cd /app/... (поскольку каждый RUN запускается в новой подоболочке, смена папки тут же сбросится на следующей строчке); всегда переключайте контекст через WORKDIR /app.
    • COPY против ADD:
    • COPY src dest — выполняет прямое, предсказуемое и прозрачное копирование файлов и папок из сборочной директории хоста внутрь образа. Используйте COPY в 99% случаев.
    • ADD — обладает скрытой магией: умеет автоматически распаковывать локальные .tar.gz-архивы и скачивать файлы по URL из интернета. В индустрии ADD считается антипаттерном из-за неявного поведения и рисков безопасности (лучше явно скачать и распаковать файл в одном слое RUN curl ... | tar ...).
    • RUN: Выполняет любую команду оболочки внутри временного контейнера во время сборки (установка пакетов, компиляция кода, создание пользователей) и намертво фиксирует измененное состояние файловой системы как новый неизменяемый слой образа.
    • Параметризация: ARG против ENV:
    • ARG (Build Argument) — переменная, которая существует только в момент сборки образа (её можно переопределить флагом docker build --build-arg APP_VERSION=1.2.0). Как только образ собран, переменные ARG исчезают, и работающее приложение внутри контейнера их не видит.
    • ENV (Environment Variable) — переменная окружения, которая запекается в метаданные готового образа и остается доступной внутри запущенного контейнера во время работы приложения (её можно переопределить на старте флагом docker run -e PORT=9000).
    • EXPOSE: Служит исключительно встроенной документацией для других инженеров, указывая, какой сетевой порт слушает приложение внутри контейнера. Важно помнить: сама по себе строчка EXPOSE 8000 не открывает и не пробрасывает порт наружу на хост (для реального проброса при запуске нужен флаг -p).
    • ENTRYPOINT и CMD (и критическая разница между Shell и Exec формой): Эти директивы определяют главный процесс, который будет запущен как PID 1 при старте контейнера (контейнер живет ровно до тех пор, пока жив этот процесс).
    • Всегда записывайте ENTRYPOINT и CMD в JSON/exec-форме с квадратными скобками: ["python3", "app.py"], а не в строковой shell-форме python3 app.py!
    • Почему это критично в продакшене: Если написать команду без скобок (CMD python3 app.py), Docker негласно обернет её в вызов оболочки /bin/sh -c "python3 app.py". В результате заветное место PID 1 внутри контейнера займет процесс /bin/sh, а не ваш Python. Проблема в том, что оболочка /bin/sh не пересылает системные сигналы (включая SIGTERM) своим дочерним процессам! Когда вы выполните docker stop, ваше приложение даже не узнает, что ему пора закрывать транзакции БД: контейнер просто зависнет на 10 секунд до истечения таймаута, после чего Docker брутально убьет его сигналом SIGKILL. Запись в квадратных скобках ["python3", "app.py"] запускает бинарник напрямую как PID 1, обеспечивая мгновенный и чистый Graceful Shutdown.

    2.2. Кэширование слоев и оптимизация размера образа (Multi-Stage Builds)

    Грамотное проектирование Dockerfile отличает опытного DevOps-инженера от новичка. Каждая инструкция RUN, COPY и ADD порождает новый слой. Чтобы сборки в CI/CD не шли по 20 минут, Docker использует умное послойное кэширование: если при повторной сборке команда в RUN или контрольная сумма копируемых в COPY файлов не изменились, Docker не выполняет шаг заново, а за 0.1 секунды берет готовый слой из локального кэша.

    Однако у кэша есть жесткое правило: как только один слой изменился, кэш для всех последующих шагов ниже по файлу полностью сбрасывается (инвалидируется). Отсюда вытекает фундаментальный принцип структуры Dockerfile: располагайте инструкции сверху вниз от самых редко меняющихся (системные пакеты, зависимости requirements.txt / package.json) к самым часто меняющимся (исходный код приложения).

    Сравним два подхода на реальном примере упаковки Python-сервиса:

    ❌ Плохой Dockerfile (Антипаттерн — размер 1.1 ГБ, долгая пересборка при каждой правке):

    # ОШИБКА 0: Берется тяжелый базовый образ полной ОС вместо легковесного -slim или -alpine
FROM ubuntu:24.04
WORKDIR /app

# ОШИБКА 1: Мы копируем весь исходный код проекта ДО установки библиотек!
# Теперь при изменении одной запятой в main.py кэш этого слоя сбросится, 
# и все нижние шаги (apt-get и pip install) будут качать сотни мегабайт из сети заново!
COPY . .

# ОШИБКА 2: Раздельные инструкции RUN и неочищенный кэш пакетного менеджера.
# Даже если вы удалите файлы в следующем RUN, они навсегда останутся весить в предыдущем слое!
RUN apt-get update
RUN apt-get install -y python3 python3-pip gcc
RUN pip install -r requirements.txt

# ОШИБКА 3: Shell-форма запуска (ломает обработку сигнала SIGTERM) и работа от root
CMD python3 main.py

    ✅ Оптимизированный Multi-Stage Dockerfile (Размер 60 МБ, пересборка кода за 1 секунду):

    Для компилируемых языков (Go, Rust, Java, C++, TypeScript) и Python-пакетов с C-расширениями применяется стандарт Multi-stage builds (Многоэтапная сборка). В одном Dockerfile мы описываем несколько блоков FROM: в первом временном сборочном образе (builder) мы устанавливаем тяжелые компиляторы (gcc, make, SDK) и собираем артефакт, а во второй — финальный чистый образ — копируем флагом COPY --from=builder только готовые скомпилированные библиотеки или бинарник, оставляя весь сборочный мусор за бортом:

    # --- Этап 1: Сборка зависимостей (Временный сборочный контур Builder) ---
FROM python:3.12-slim AS builder
WORKDIR /build

# Сначала копируем ТОЛЬКО текстовый файл списка зависимостей!
# Пока программист не добавит новую библиотеку в requirements.txt, следующий тяжелый шаг
# всегда будет мгновенно браться из кэша, сколько бы раз ни менялся код в папке src/!
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# --- Этап 2: Финальный легковесный образ для продакшена (Runtime) ---
FROM python:3.12-slim
WORKDIR /app

# Параметризация версии сборки и базовых настроек Python
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION} \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# Забираем только чистые скомпилированные библиотеки из этапа builder
COPY --from=builder /install /usr/local

# Исходный код меняется чаще всего — поэтому копируем его на самом последнем шаге!
COPY src/ ./src/

EXPOSE 8000
ENTRYPOINT ["python3", "src/app.py"]

    Обязательный фильтр .dockerignore: Прежде чем выполнить первую строчку Dockerfile, клиент Docker CLI упаковывает всю текущую папку проекта (Build Context) и пересылает её демону dockerd. Чтобы сборка не тормозила, а внутрь образа при команде COPY . . случайно не улетели локальные пароли и история репозитория, в корне любого проекта обязательно создается файл .dockerignore, куда вносятся .git, .env, venv, node_modules и *.log.

    2.3. Управление реестрами образов (Docker Registries)

    Чтобы собранный образ можно было скачать на десятках боевых серверов, его публикуют в централизованном хранилище артефактов — Container Registry (публичный Docker Hub, корпоративные GitLab Container Registry, GitHub Container Registry ghcr.io, Yandex Container Registry или Harbor).

    Полный адрес (тег) любого образа в мире подчиняется строгой структуре: [АДРЕС_РЕЕСТРА]/[ПРОЕКТ_ИЛИ_ЛОГИН]/[ИМЯ_СЕРВИСА]:[ВЕРСИЯ] (например: registry.gitlab.com/myteam/backend-api:1.2.4; если адрес реестра в начале не указан, Docker по умолчанию обращается к публичному docker.io — Docker Hub).

    Железное правило продакшена: табу на тег :latest! Никогда не используйте плавающий тег :latest в конфигурациях боевых серверов (compose.yaml, Ansible или манифестах Kubernetes). Тег :latest не означает «лучший» — он просто перезаписывается при каждой новой сборке. Если вы задеплоили myapp:latest, через неделю вы не сможете понять, какая именно версия кода сейчас крутится на сервере, а при аварии не сможете сделать быстрый откат (Rollback), так как старый образ под этим именем уже затерт. В продакшене каждый образ должен иметь строго иммутабельный (неизменяемый) тег: семантическую версию релиза (:1.2.4) или короткий хэш Git-коммита (:a1b2c3d).

    # Пройти аутентификацию в приватном корпоративном реестре
docker login registry.gitlab.com

# Собрать образ с передачей аргумента сборки (--build-arg) и сразу присвоить ему два тега (-t)
docker build --build-arg APP_VERSION=1.2.0 -t myuser/myapp:1.2.0 -t myuser/myapp:latest .

# Опубликовать конкретную иммутабельную версию образа в удаленный реестр
docker push myuser/myapp:1.2.0

    Блок 3. Сети и постоянные тома (Volumes) в Docker

    3.1. Хранение данных: почему контейнеры эфемерны (Volumes vs Bind Mounts)

    По своей природе любой контейнер эфемерен (stateless): все файлы, которые приложение создает или меняет внутри контейнера в процессе работы, записываются в его тонкий верхний Read-Write слой. Как только вы удалите контейнер командой docker rm для обновления версии, этот верхний слой уничтожается вместе со всеми записанными в него данными.

    Поэтому для любых данных, которые должны переживать пересоздание контейнера (базы данных PostgreSQL/Redis, загруженные пользователями файлы, внешние конфиги), часть файловой системы контейнера выносят наружу на хост с помощью трёх механизмов монтирования:

    1. Docker Volume (Именованный том) — промышленный стандарт для баз данных и продакшена: Выделенное хранилище на диске сервера (внутри /var/lib/docker/volumes/), жизненным циклом которого полностью управляет сам Docker. Именованный том изолирован от случайного вмешательства на хосте, корректно выставляет права доступа и никогда не удаляется при удалении контейнера: 

      # Создать постоянный том и подключить его к директории данных PostgreSQL внутри контейнера
docker volume create pg_data
docker run -d --name db -v pg_data:/var/lib/postgresql/data postgres:16-alpine

    2. Bind Mount (Прямой проброс директории или файла с хоста): Монтирует конкретный существующий путь из файловой системы вашего сервера напрямую поверх папки внутри контейнера. Этот механизм идеален в двух случаях: когда нужно пробросить внутрь контейнера статический конфигурационный файл с сервера (например, nginx.conf, причем с защитным флагом :ro — Read-Only, чтобы контейнер не мог его изменить) или когда разработчик пробрасывает папку с кодом на ноутбуке для мгновенной отладки: 

      docker run -d --name proxy -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro nginx:alpine

    3. tmpfs Mount (Монтирование в оперативную память): Создает временную директорию внутри контейнера, которая физически размещается напрямую в оперативной памяти (RAM) хоста и никогда не касается жесткого диска. Это лучшее решение для временных папок (/tmp), быстрых файловых кэшей или чувствительных криптографических секретов, которые должны мгновенно испариться при выключении питания.

    3.2. Изолированные сети и встроенный DNS-сервер Docker

    Чтобы микросервисы могли общаться друг с другом, но при этом оставались надежно защищены от внешнего доступа, в Docker реализована подсистема программно-определяемых сетей (SDN) с несколькими сетевыми драйверами:

    • bridge (Стандартная мостовая сеть по умолчанию): При установке Docker создает на сервере виртуальный сетевой коммутатор — интерфейс docker0. Все контейнеры, запущенные без указания сети, подключаются к этому мосту, получают внутренние серые IP-адреса (из подсети 172.17.0.0/16) и выходят во внешний мир через NAT (iptables)[cite: 1, 3]. Однако у дефолтного моста есть серьезный минус: в нем все контейнеры свалены в одну общую кучу и могут обращаться друг к другу только по числовым IP-адресам (которые меняются при каждом перезапуске контейнера).
    • User-Defined Bridge (Пользовательская изолированная сеть) — стандарт микросервисной архитектуры: Когда вы создаете собственную сеть командой docker network create <имя>, происходят две важнейшие вещи:
    • Контейнеры внутри этой сети надежно изолируются на уровне фаервола от всех остальных контейнеров на сервере.
    • Docker автоматически включает для этой сети встроенный внутренний DNS-сервер (Service Discovery)! Теперь контейнерам внутри одной пользовательской сети не нужно знать IP-адреса друг друга — они обращаются друг к другу напрямую по имени контейнера (например, бэкенд просто стучится по адресу http://redis-cache:6379 или postgres://db:5432)!
    • host (--network host): Полностью отключает сетевое пространство имен (net namespace): контейнер получает прямой доступ к физической сетевой карте самого хостового сервера. Используется для задач, где критична максимальная сетевая производительность без накладных расходов на NAT (например, высоконагруженные балансировщики или агенты сетевого мониторинга).
    • none (--network none): Полная сетевая изоляция: внутри контейнера остается только локальная петля lo, любые внешние и внутренние сетевые связи физически отключены (применяется для пакетной обработки чувствительных данных).
    # 1. Создаем собственную изолированную сеть со встроенным DNS
docker network create app-net

# 2. Запускаем базу данных Redis внутри этой сети.
# Обрати внимание: мы НЕ указываем флаг -p! Порт 6379 намертво закрыт для внешнего интернета
# и хоста, но полностью открыт для наших сервисов внутри изолированного контура app-net!
docker run -d --name redis-cache --network app-net redis:7-alpine

# 3. Запускаем временный тестовый контейнер (--rm удалит его сразу после завершения команды)
# в той же сети и проверяем, что встроенный DNS автоматически резолвит имя "redis-cache" в IP!
docker run --rm --network app-net alpine ping -c 2 redis-cache

    Блок 4. DevSecOps: Безопасный запуск, секреты и проверка на уязвимости

    4.1. Безопасный запуск компонентов (Hardening контейнеров)

    Огромное количество взломов серверной инфраструктуры происходит из-за одной особенности Docker: по умолчанию процесс внутри контейнера запускается от имени суперпользователя root (UID 0).

    Поскольку ядро Linux у контейнера и у физического сервера одно и то же, UID 0 внутри контейнера технически является тем же самым UID 0 для ядра хоста. Если злоумышленник найдет уязвимость в вашем веб-приложении (RCE) и в связке с ней использует свежую уязвимость ядра или ошибку конфигурации проброшенных томов, он совершит побег из контейнера (Container Escape) и мгновенно окажется на физическом сервере с полными правами root!

    В практике DevSecOps безопасность закладывается прямо в архитектуру контейнера с помощью четырех обязательных рубежей обороны:

    1. Запуск строго от непривилегированного пользователя (USER в Dockerfile): Внутри Dockerfile всегда создается бесправный системный пользователь с высоким UID (например, 10001), на которого переключается контекст перед стартом приложения: 
      RUN groupadd -r appgroup && useradd -r -g appgroup -u 10001 appuser
USER 10001:10001
    2. Неизменяемая файловая система контейнера (--read-only): Если ваше приложение не должно менять свои собственные исходники (а оно никогда не должно этого делать!), запускайте контейнер с флагом --read-only (а для временных системных файлов монтируйте в память --tmpfs /tmp). Даже если хакер найдет уязвимость в коде Python или Node.js, он не сможет ни скачать на диск эксплойт, ни подменить исполняемый скрипт — файловая система заблокирована на запись на уровне ядра!
    3. Принудительный сброс привилегий ядра (--cap-drop=ALL): В Linux полномочия суперпользователя разбиты на десятки мелких привилегий — Capabilities (право менять сетевые настройки, монтировать диски, менять системное время). Обычному веб-сервису на порту 8000 не нужна ни одна из них! Флаги --cap-drop=ALL и --security-opt=no-new-privileges полностью лишают процесс любых системных полномочий ядра.
    4. Жесткие квоты ресурсов (--memory, --cpus, --pids-limit): Защищают хостовый сервер от отказа в обслуживании (DoS) при утечке памяти или запуске fork-бомбы внутри скомпрометированного контейнера.

    4.2. Безопасная работа с секретами

    • Критическое табу: Никогда не передавайте пароли от баз данных, API-токены и приватные ключи внутрь Dockerfile через инструкции ENV или ARG! Начинающие инженеры иногда делают ARG SECRET_KEY, используют его и удаляют файл в следующем слое, думая, что секрет спрятан. На самом деле любой человек, получивший образ, выполнит одну команду docker history --no-trunc <image> или docker inspect <image> и увидит все переданные значения ENV и ARG открытым текстом!
    • Как передавать секреты правильно:
    • Во время работы (Runtime): Образ должен быть абсолютно обезличенным (в нем нет ни одного пароля). Все секреты пробрасываются в контейнер динамически в момент старта снаружи — через защищенный файл окружения --env-file .env на сервере или через монтирование секрета в оперативную память (tmpfs в механизме Docker Secrets / Kubernetes Secrets).
    • Во время сборки (Build-time): Если во время самого docker build вам необходимо скачать закрытую корпоративную библиотеку по приватному токену, используется механизм BuildKit Secret Mount (RUN --mount=type=secret,id=my_token ...). При таком подходе секрет монтируется как виртуальный файл в RAM ровно на ту секунду, пока идет скачивание пакета, и гарантированно не оставляет никаких следов ни в истории команд, ни в слоях готового образа.

    4.3. Проверка образов на уязвимости (Vulnerability Scanning — Trivy)

    Даже если ваш собственный код на Python или Go написан безупречно, вы упаковываете его поверх базового образа ОС (Debian, Ubuntu или Alpine), который содержит сотни системных библиотек (openssl, libcurl, glibc, zlib). В этих библиотеках ежедневно обнаруживаются новые уязвимости безопасности, регистрируемые в мировых базах под номерами CVE (Common Vulnerabilities and Exposures).

    Золотым стандартом индустрии для автоматического аудита Docker-образов является open-source сканер Trivy от компании Aqua Security: * Он за секунды разбирает образ по слоям, распознает установленные системные пакеты ОС (dpkg/apt, apk, rpm) и зависимости языков программирования (pip, npm, go.mod, Cargo.lock, pom.xml) и сверяет их версии с актуальной базой CVE. * Кроме того, Trivy автоматически сканирует файловую систему образа на предмет случайно забытых приватных SSH-ключей, облачных токенов AWS и паролей.

    Самое удобное, что для запуска Trivy его даже не нужно устанавливать на сервер — мы можем запустить сам сканер как одноразовый Docker-контейнер, пробросив ему сокет демона Docker:

    # Просканировать образ python:3.12-slim и вывести таблицу только тех уязвимостей,
# которые имеют высокий (HIGH) и критический (CRITICAL) уровень опасности:
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image --severity HIGH,CRITICAL python:3.12-slim

    🛠 Практический проект Модуля 2: Полный цикл упаковки и защиты микросервиса (DevSecOps)

    В этом практикуме мы пройдем весь боевой цикл работы с контейнерами: напишем микросервис на Python (Flask + промышленный сервер Gunicorn), который работает в связке с базой данных Redis и защищен проверкой секретного API-ключа. Мы упакуем его в эталонный Multi-stage Dockerfile с непривилегированным пользователем и самодиагностикой (HEALTHCHECK), прогоним через сканер уязвимостей Trivy, а затем развернем весь стек в изолированной сети с постоянным томом данных и максимальной защитой (Read-Only FS + cap-drop=ALL).

    Этап 1. Подготовка исходного кода микросервиса

    Создай чистую рабочую директорию проекта ~/docker-practice и подготовим исходные файлы приложения:

    mkdir -p ~/docker-practice/src && cd ~/docker-practice

# 1. Фиксируем точные версии библиотек (воспроизводимость сборки!)
cat << 'EOF' > requirements.txt
flask==3.0.3
redis==5.0.8
gunicorn==23.0.0
EOF

# 2. Создаем код микросервиса (src/app.py):
# Сервис читает конфигурацию и секреты исключительно из переменных окружения,
# имеет эндпоинт самодиагностики /health и защищенный эндпоинт /hit
cat << 'EOF' > src/app.py
import os
import socket
from flask import Flask, jsonify, request
import redis

app = Flask(__name__)

REDIS_HOST = os.getenv("REDIS_HOST", "localhost")
REDIS_PORT = int(os.getenv("REDIS_PORT", 6379))
API_SECRET_KEY = os.getenv("API_SECRET_KEY", "not-set")

cache = redis.Redis(host=REDIS_HOST, port=REDIS_PORT, decode_responses=True)

@app.route("/health")
def health():
    return jsonify({"status": "healthy", "hostname": socket.gethostname()}), 200

@app.route("/hit")
def hit():
    client_key = request.headers.get("X-API-Key")
    if client_key != API_SECRET_KEY:
        return jsonify({"error": "Unauthorized: invalid X-API-Key"}), 403
    try:
        count = cache.incr("hits")
        return jsonify({
            "message": "Success",
            "hits": count,
            "container_id": socket.gethostname(),
            "version": os.getenv("APP_VERSION", "unknown")
        }), 200
    except redis.ConnectionError:
        return jsonify({"error": "Redis connection failed"}), 500

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)
EOF

    Этап 2. Настройка .dockerignore и создание защищенного Multi-Stage Dockerfile

    1. Первым делом ставим барьер безопасности .dockerignore, чтобы локальные файлы .env, кэши и история Git ни при каких обстоятельствах не попали в контекст сборки образа:
    cat << 'EOF' > .dockerignore
.git
.env
*.env
*.log
__pycache__
README.md
EOF
    1. Теперь создадим промышленный Dockerfile. Обрати внимание на детали инженерной культуры внутри него:
    2. Сборка разделена на два этапа (builder и финальный образ).
    3. Во втором этапе первым делом выполняются apt-get upgrade -y (чтобы закрыть свежие уязвимости CVE в базовом образе) и очистка кэша apt в том же самом слое RUN.
    4. Создается системный пользователь appuser с UID 10001 без командной оболочки (/usr/sbin/nologin).
    5. Для проверки здоровья контейнера (HEALTHCHECK) мы не устанавливаем в образ лишнюю утилиту curl (которая увеличит размер образа и принесет с собой свои CVE!), а элегантно выполняем проверку средствами стандартной библиотеки самого Python (urllib.request)!
    cat << 'EOF' > Dockerfile
# ==========================================
# Stage 1: Builder (изолированная сборка зависимостей)
# ==========================================
FROM python:3.12-slim AS builder

WORKDIR /build
COPY requirements.txt .

# Устанавливаем пакеты в отдельную папку /install без сохранения кэша pip
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ==========================================
# Stage 2: Production Runtime (чистый боевой образ)
# ==========================================
FROM python:3.12-slim

# Параметризация версии при сборке (ARG) и проброс в переменные окружения контейнера (ENV)
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION} \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PORT=8000

WORKDIR /app

# Обновляем системные библиотеки безопасности, очищаем кэш apt в том же слое
# и создаем непривилегированного пользователя appuser (UID 10001)
RUN apt-get update && apt-get upgrade -y && \
    rm -rf /var/lib/apt/lists/* && \
    groupadd -r appgroup && \
    useradd -r -g appgroup -u 10001 -s /usr/sbin/nologin appuser

# Копируем готовые установленные библиотеки из первого этапа
COPY --from=builder /install /usr/local

# Копируем исходный код и сразу назначаем владельцем нашего пользователя
COPY --chown=appuser:appgroup src/ ./src/

# Переключаемся с root на непривилегированного пользователя
USER 10001:10001

EXPOSE 8000

# Встроенная самодиагностика контейнера каждые 15 секунд штатными средствами Python
HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=3 \
  CMD ["python3", "-c", "import urllib.request; urllib.request.urlopen('[http://127.0.0.1:8000/health](http://127.0.0.1:8000/health)')"]

# Запускаем приложение через многопоточный сервер gunicorn строго в exec-форме (как PID 1)
ENTRYPOINT ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "src.app:app"]
EOF

    Этап 3. Сборка и сканирование образа на уязвимости через Trivy

    1. Соберем образ, передав ему на этапе сборки конкретную версию релиза APP_VERSION=1.0.5, и присвоим иммутабельный тег hit-counter:1.0.5:
    docker build --build-arg APP_VERSION=1.0.5 -t hit-counter:1.0.5 .
    1. Оценим компактный размер получившегося образа и посмотрим на его послойную структуру (обрати внимание: внутри истории слоев нет ни одного секрета):
    docker images hit-counter:1.0.5
docker history hit-counter:1.0.5
    1. Проведем аудит безопасности нашего свежесобранного образа с помощью сканера Trivy на предмет критических уязвимостей и забытых ключей:
    docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image --severity HIGH,CRITICAL hit-counter:1.0.5

    Этап 4. Изолированная сеть, том данных и безопасный запуск с секретами

    Теперь развернем инфраструктуру по канонам микросервисной безопасности:

    1. Создадим пользовательскую изолированную сеть backend-net (со встроенным DNS) и постоянный именованный том redis-data для сохранения состояния базы данных:
    docker network create backend-net
docker volume create redis-data
    1. Запустим СУБД Redis внутри сети backend-net с включенным журналом сохранения данных на диск (--appendonly yes), примонтированным к нашему тому redis-data. (Важная деталь архитектуры: мы не указываем флаг -p 6379:6379! База данных полностью изолирована от внешнего мира и хоста — подключиться к ней может только наш бэкенд внутри сети backend-net по DNS-имени redis-db):
    docker run -d \
  --name redis-db \
  --network backend-net \
  -v redis-data:/data \
  --restart unless-stopped \
  redis:7-alpine redis-server --appendonly yes
    1. Создадим на хосте защищенный файл .env с боевым секретным ключом API и закроем права чтения на него (chmod 600). Благодаря нашему .dockerignore этот файл никогда не попадет внутрь образа при пересборках:
    cat << 'EOF' > .env
REDIS_HOST=redis-db
REDIS_PORT=6379
API_SECRET_KEY=ProdSuperSecretToken999
EOF
chmod 600 .env
    1. Запустим контейнер нашего микросервиса hit-app в режиме максимальной защиты (Hardened Runtime):
    2. Передаем секреты снаружи через --env-file .env.
    3. Блокируем корневую файловую систему контейнера от любых изменений флагом --read-only (выделив под временные сокеты воркеров Gunicorn папку /tmp в оперативной памяти --tmpfs /tmp).
    4. Отбираем у процесса абсолютно все привилегии ядра Linux (--cap-drop=ALL и --security-opt=no-new-privileges).
    5. Ограничиваем аппетиты контейнера квотой 128 МБ RAM и половиной ядра CPU (--cpus="0.5"):
    docker run -d \
  --name hit-app \
  --network backend-net \
  --env-file .env \
  -p 8080:8000 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --memory="128m" \
  --cpus="0.5" \
  --restart unless-stopped \
  hit-counter:1.0.5

    ✅ Чек-лист самопроверки по Модулю 2

    Выполни пять проверочных тестов, чтобы лично убедиться, что каждый уровень нашей защиты и архитектуры работает безупречно:

    1. Проверка встроенной самодиагностики (HEALTHCHECK): Подожди 15 секунд после старта и выполни: 

      docker ps
      Ожидаемый результат: В колонке STATUS у контейнера hit-app рядом со временем работы горит статус (healthy).

    2. Аудит непривилегированного пользователя внутри контейнера: 

      docker exec hit-app id
      Ожидаемый результат: uid=10001(appuser) gid=10001(appgroup) groups=10001(appgroup) — приложение работает без прав root.

    3. Симуляция взлома: проверка защиты Read-Only файловой системы: Представь, что злоумышленник проник внутрь контейнера и пытается записать вредоносный скрипт в рабочую папку приложения /app: 

      docker exec hit-app touch /app/hacked.txt
      Ожидаемый результат: Система мгновенно блокирует запись с ошибкой touch: cannot touch '/app/hacked.txt': Read-only file system!

    4. Проверка авторизации по секрету и связки с Redis по внутреннему DNS:

    5. Попробуй обратиться к сервису без секретного заголовка (должен вернуться отказ 403 Forbidden): 
      curl -i http://localhost:8080/hit

    6. А теперь отправь запрос с правильным ключом из .env 2–3 раза подряд: 

      curl -H "X-API-Key: ProdSuperSecretToken999" http://localhost:8080/hit
      Ожидаемый результат: Сервис возвращает 200 OK, версию "1.0.5" и увеличивающийся счетчик "hits" из базы Redis!

    7. Краш-тест сохранности данных в постоянном томе (redis-data): Уничтожим контейнер базы данных Redis и создадим совершенно новый контейнер с подключением того же тома redis-data: 

      docker rm -f redis-db
docker run -d --name redis-db --network backend-net -v redis-data:/data redis:7-alpine redis-server --appendonly yes
curl -H "X-API-Key: ProdSuperSecretToken999" http://localhost:8080/hit
      Ожидаемый результат: Счетчик "hits" не сбросился в 1, а продолжил отсчет с предыдущего значения — данные надежно пережили полное пересоздание контейнера СУБД!
