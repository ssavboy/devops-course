    Автоматизация сборки и CI

    До этого момента мы собирали Docker-образы, проверяли код и запускали сканер уязвимостей Trivy вручную в терминале. В реальной командной разработке ручная сборка запрещена: человек может забыть прогнать тесты, собрать образ из несохраненного локального файла или случайно запушить сломанный код.

    Continuous Integration (Непрерывная интеграция) — это инженерная практика, при которой каждое изменение кода в Git автоматически запускает конвейер (Pipeline): код проверяется линтерами, тестируется, сканируется на уязвимости и упаковывается в версионированный артефакт без участия человека.

    Блок 1. Архитектура CI-конвейеров и Lean-подход

    1.1. Что такое CI и принцип Fast Feedback (Быстрая обратная связь)

    Главная цель CI — обнаружить ошибку как можно раньше и дешевле. Если разработчик допустил синтаксическую ошибку или сломал API, он должен узнать об этом через 2–3 минуты после git push, а не через неделю на продакшене.

    Lean-подход к проектированию конвейеров (Fail Fast):

    В соответствии с принципами бережливого производства (Lean), этапы конвейера всегда выстраиваются от самых быстрых и дешевых к самым долгим и ресурсоемким:

    1. Линтинг и проверка форматирования (lint — 10–20 сек): Мгновенно отсекает синтаксические ошибки в Python/Go/JS, Dockerfile и YAML-файлах. Нет смысла запускать тяжелую сборку Docker, если в коде пропущена скобка.
    2. Модульные тесты и SAST (test — 30–60 сек): Проверка бизнес-логики изолированными unit-тестами и статический анализ безопасности исходного кода.
    3. Сборка образа (build — 1–3 мин): Упаковка приложения в Docker-образ.
    4. Сканирование образа и интеграционные тесты (security / integration — 1–2 мин): Проверка готового образа через Trivy и тестовый запуск связки с БД.
    5. Публикация артефакта (publish — 20 сек): Отправка проверенного образа в Container Registry.
    [git push] ──► (Stage 1: Lint) ──► (Stage 2: Unit Tests & SAST) ──► (Stage 3: Docker Build) ──► (Stage 4: Trivy Scan) ──► (Stage 5: Push Registry)
                  ~15 sec                   ~45 sec                       ~90 sec                    ~40 sec                   ~15 sec

    1.2. Архитектура GitLab CI: Сервер против Раннеров (Runners)

    Многие начинающие инженеры думают, что сборка кода происходит прямо внутри самого сервера GitLab. Это критическое заблуждение. Если бы тяжелые сборки шли на основном сервере GitLab, веб-интерфейс и Git-репозитории всей компании зависали бы при каждом коммите.

    Архитектура разделена на два независимых компонента:

    1. GitLab Server (Coordinator): Хранит Git-репозитории, читает файл .gitlab-ci.yml, управляет очередью задач и отображает статус пайплайнов в веб-интерфейсе.
    2. GitLab Runner (Агент-исполнитель): Легковесный демон на языке Go, который устанавливается на отдельные виртуальные машины или в Kubernetes-кластер. Раннер сам опрашивает сервер GitLab по HTTP/HTTPS (Pull-модель), забирает задачи (Jobs), выполняет их и отправляет обратно логи и статус выполнения.

    Типы исполнителей (Executors) у GitLab Runner:

    При регистрации раннера мы выбираем, в какой среде он будет выполнять команды из .gitlab-ci.yml:

    Тип Executor Как работает Плюсы и минусы
    shell Выполняет команды напрямую в bash хостовой ОС, где стоит раннер. Быстро, но опасно и грязно: задачи разных проектов влияют друг на друга, остаются временные файлы, нет изоляции.
    docker (Стандарт) На каждую джобу (job) раннер поднимает чистый одноразовый Docker-контейнер с нужным образом (например, python:3.12), выполняет команды и удаляет контейнер. Идеальная изоляция, воспроизводимость, на одном сервере можно одновременно собирать Python, Go, Node.js и Terraform.
    kubernetes На каждую джобу создает отдельный Pod в кластере Kubernetes. Автоматическое масштабирование от 0 до сотен сборок параллельно в облаке.

    Блок 2. Анатомия файла .gitlab-ci.yml

    Конвейер описывается декларативно в файле .gitlab-ci.yml в корне Git-репозитория.

    2.1. Базовые сущности: stages, jobs, image, services

    • stages (Стадии): Определяют глобальный порядок этапов. Все джобы внутри одной стадии выполняются параллельно, а следующая стадия начинается только тогда, когда все джобы предыдущей завершились успешно (код возврата 0).
    • jobs (Задачи): Сами блоки команд (script:), привязанные к конкретной стадии.
    • image: В каком Docker-образе должна запуститься данная джоба (например, python:3.12-slim для тестов или hadolint/hadolint для проверки Dockerfile).
    • services (Вспомогательные контейнеры): Позволяют поднять рядом с джобой временную базу данных (например, postgres:16-alpine или redis:7-alpine) специально на время прогона интеграционных тестов!

    2.2. Кэширование (cache) против Артефактов (artifacts)

    На собеседованиях постоянно спрашивают разницу между cache и artifacts. Оба механизма передают файлы между джобами, но у них совершенно разное назначение:

    Характеристика Кэш (cache:) Артефакты (artifacts:)
    Назначение Ускорение скачивания зависимостей из интернета (папки .cache/pip, node_modules/, .m2/). Передача результата работы одной стадии в следующую (скомпилированный бинарник, отчет о тестах, HTML-отчет Trivy).
    Область действия Сохраняется между разными пайплайнами (коммитами) по ключу key: (например, хэшу файла requirements.txt). Передается строго внутри одного текущего пайплайна от ранних стадий к поздним и доступен для скачивания в UI GitLab.
    Гарантия доставки Best-effort (если кэш пуст или сброшен, джоба всё равно должна успешно скачать пакеты сама). Гарантированная доставка (хранится на сервере GitLab или в S3 до истечения срока expire_in). 
    # Пример правильного кэширования pip-пакетов по хэшу файла requirements.txt:
# Кэш обновится только тогда, когда разработчик изменит список библиотек!
cache:
  key:
    files:
      - app/requirements.txt
  paths:
    - .cache/pip

    2.3. Ускорение пайплайна с помощью DAG (needs:) и правил (rules:)

    • Директива needs: (Directed Acyclic Graph): Позволяет джобе не ждать завершения всей предыдущей стадии целиком, а стартовать мгновенно, как только завершилась конкретная нужная ей джоба.
    • Директива rules: (Замена устаревших only / except): Управляет тем, когда запускать джобу. Например: тесты гонять на каждый коммит в любой ветке, а сборку и пуш релизного образа в Registry — только при слиянии в ветку main или создании git-тега!
    rules:
  # Запускать только в ветке main и только если изменились файлы внутри папки app/
  - if: $CI_COMMIT_BRANCH == "main"
    changes:
      - app/**/*

    Блок 3. Контроль качества кода (Quality Gates) и сборка контейнеров в CI

    3.1. Эшелонированная проверка качества (Shift-Left Security)

    Вместо того чтобы искать баги после релиза, мы сдвигаем проверки безопасности максимально влево (Shift-Left) — на этап коммита:

    1. Линтинг кода (ruff / flake8 для Python): Проверяет стиль кода (PEP8), неиспользуемые импорты и синтаксические ошибки за 2 секунды.
    2. Линтинг Dockerfile (hadolint): Проверяет Dockerfile на соблюдение лучших практик безопасности и кэширования слоев.
    3. SAST (Static Application Security Testing — bandit / semgrep): Анализирует исходный код на наличие потенциальных дыр в безопасности (SQL-инъекции, захардкоженные пароли, небезопасная десериализация).
    4. Unit и Интеграционные тесты (pytest): Проверяют работу функций и реальное подключение к тестовым контейнерам PostgreSQL и Redis, поднятым через секцию services:.

    3.2. Как собирать Docker-образы внутри Docker-раннера: DinD vs Kaniko

    Когда сама джоба уже бежит внутри Docker-контейнера, возникает вопрос: как собрать новый Docker-образ внутри контейнера? Есть 3 подхода:

    1. Проброс сокета хоста (/var/run/docker.sock binding): Быстро (использует общий кэш хоста), но несет риски безопасности на общих серверах (контейнер получает полный доступ к демону Docker на хосте).
    2. Docker-in-Docker (docker:dind service): Поднимает изолированный демон Docker как service рядом с джобой. Требует флага privileged: true в настройках раннера.
    3. Kaniko (gcr.io/kaniko-project/executor) — стандарт DevSecOps: Инструмент от Google, который собирает образы из Dockerfile прямо в пространстве пользователя вообще без демона Docker и без привилегированного режима (privileged: false)!

    Блок 4. Типичные антипаттерны в CI-конвейерах

    Антипаттерн в CI К чему приводит Как сделать правильно
    1. Отсутствие кэширования зависимостей При каждом коммите pip install или npm install заново качает сотни мегабайт из сети. Пайплайн идет 15 минут вместо 1 минуты. Настроить секцию cache: с ключом по файлу requirements.txt / package-lock.json.
    2. Игнорирование упавших тестов (allow_failure: true на тестах) Разработчики перестают чинить упавшие тесты, в main вливается нерабочий код. Любое падение линтера, unit-теста или критической CVE в Trivy должно жестко валить пайплайн (exit 1).
    3. Хранение паролей и токенов в .gitlab-ci.yml Любой разработчик с доступом к репозиторию видит продакшен-секреты. Хранить секреты строго в Settings $\rightarrow$ CI/CD $\rightarrow$ Variables с флагами Masked (скрывать в логах звездочками [MASKED]) и Protected (доступны только в защищенной ветке main).
    4. Сборка образа заново на каждой стадии На стадии test собрали один образ, а на стадии publish собрали его еще раз с нуля (нарушение принципа Build Once). Собрать образ один раз с тегом по SHA коммита (:$CI_COMMIT_SHORT_SHA), протестировать именно его, и при успехе просто присвоить ему релизный тег (docker tag + docker push).

    🛠 Практический проект Модуля 6: Создание сборочного CI-конвейера с автоматическим контролем качества

    Мы создадим промышленный многоэтапный конвейер .gitlab-ci.yml для нашего микросервиса из предыдущих модулей и протестируем его работу локально прямо на твоем компьютере (с помощью Docker и GitLab Runner), даже не поднимая тяжелый сервер GitLab!

    Этап 1. Подготовка репозитория с тестами и проверками качества

    Перейдем в папку нашего кластера ~/compose-cluster (или создадим её) и добавим автоматические тесты pytest для нашего API:

    mkdir -p ~/compose-cluster/app/tests && cd ~/compose-cluster

# 1. Добавим в зависимости для разработки быстрый линтер ruff, SAST-сканер bandit и pytest
cat << 'EOF' > app/requirements-dev.txt
-r requirements.txt
pytest==8.3.2
ruff==0.6.2
bandit==1.7.9
EOF

# 2. Напишем автоматические тесты (Unit + интеграционная проверка БД и Redis)
cat << 'EOF' > app/tests/test_app.py
import os
import sys
sys.path.insert(0, os.path.abspath(os.path.join(os.path.dirname(__file__), '..')))

from main import app

def test_health_endpoint():
    """Проверяем, что сервис отвечает 200 OK на /health при живых БД и Redis"""
    client = app.test_client()
    response = client.get("/health")
    assert response.status_code == 200
    data = response.get_json()
    assert data["status"] == "healthy"

def test_visit_increments_counter():
    """Проверяем, что /api/visit корректно пишет в PostgreSQL и увеличивает счетчик в Redis"""
    client = app.test_client()
    resp1 = client.get("/api/visit").get_json()
    resp2 = client.get("/api/visit").get_json()
    assert resp2["redis_hits"] == resp1["redis_hits"] + 1
    assert resp2["postgres_saved_rows"] == resp1["postgres_saved_rows"] + 1
EOF

    Этап 2. Проектирование эталонного .gitlab-ci.yml

    Создай в корне проекта файл .gitlab-ci.yml, реализующий 5 стадий конвейера по принципу Fail Fast: 1. lint: Проверка Python-кода линтером ruff и проверка Dockerfile линтером hadolint (запускаются параллельно!). 2. test: Запуск SAST-анализатора безопасности кода bandit и прогон тестов pytest с автоматическим поднятием временных контейнеров postgres:16-alpine и redis:7-alpine через секцию services:. 3. build: Сборка Docker-образа с версионированием по короткому хэшу коммита ($CI_COMMIT_SHORT_SHA). 4. security: Автоматическое сканирование собранного образа через Trivy с сохранением отчета в artifacts:. 5. publish: Публикация проверенного образа в GitLab Container Registry (только для ветки main).

    cat << 'EOF' > .gitlab-ci.yml
stages:
  - lint
  - test
  - build
  - security
  - publish

# Глобальные переменные конвейера
variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
  IMAGE_TAG: "$CI_REGISTRY_IMAGE/backend:$CI_COMMIT_SHORT_SHA"
  IMAGE_LATEST: "$CI_REGISTRY_IMAGE/backend:latest"

# Кэширование скачанных Python-пакетов между запусками по хэшу файла зависимостей
cache:
  key:
    files:
      - app/requirements-dev.txt
  paths:
    - .cache/pip

# ==========================================================
# STAGE 1: LINT (Быстрая проверка синтаксиса и стиля < 15 сек)
# ==========================================================
lint:python:
  stage: lint
  image: python:3.12-slim
  script:
    - pip install --quiet ruff==0.6.2
    - ruff check app/

lint:dockerfile:
  stage: lint
  image: hadolint/hadolint:latest-debian
  script:
    # Игнорируем DL3008 (версии системных пакетов apt), проверяем остальное строго
    - hadolint --ignore DL3008 app/Dockerfile

# ==========================================================
# STAGE 2: TEST & SAST (Проверка безопасности кода и тесты с БД)
# ==========================================================
sast:bandit:
  stage: test
  image: python:3.12-slim
  needs: ["lint:python"]
  script:
    - pip install --quiet bandit==1.7.9
    # Проверяем код на уязвимости высокой и средней критичности (-ll)
    - bandit -r app/main.py -ll

unit-and-integration:pytest:
  stage: test
  image: python:3.12-slim
  needs: ["lint:python"]
  # GitLab Runner автоматически поднимет эти контейнеры рядом с джобой!
  services:
    - name: postgres:16-alpine
      alias: db
    - name: redis:7-alpine
      alias: redis
  variables:
    POSTGRES_USER: test_admin
    POSTGRES_PASSWORD: test_secret_password
    POSTGRES_DB: test_cluster_db
    DB_HOST: db
    REDIS_HOST: redis
  script:
    - pip install --quiet -r app/requirements-dev.txt
    - pytest app/tests/ -v --junitxml=report.xml
  artifacts:
    when: always
    reports:
      junit: report.xml
    expire_in: 7 days

# ==========================================================
# STAGE 3: BUILD (Сборка Docker-образа)
# ==========================================================
build:image:
  stage: build
  image: docker:27-cli
  services:
    - docker:27-dind
  needs: ["unit-and-integration:pytest", "lint:dockerfile", "sast:bandit"]
  script:
    - docker build -t "$IMAGE_TAG" ./app
    - docker save "$IMAGE_TAG" -o image.tar
  artifacts:
    paths:
      - image.tar
    expire_in: 1 hour

# ==========================================================
# STAGE 4: SECURITY SCAN (Проверка образа через Trivy)
# ==========================================================
security:trivy:
  stage: security
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  needs: ["build:image"]
  script:
    # Сканируем собранный tar-архив образа; если есть CRITICAL уязвимости в коде — валим сборку (--exit-code 1)
    - trivy image --input image.tar --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 --format table -o trivy-report.txt
    - cat trivy-report.txt
  artifacts:
    when: always
    paths:
      - trivy-report.txt
    expire_in: 30 days

# ==========================================================
# STAGE 5: PUBLISH (Публикация в Registry только из ветки main)
# ==========================================================
publish:registry:
  stage: publish
  image: docker:27-cli
  services:
    - docker:27-dind
  needs: ["security:trivy"]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  script:
    - docker load -i image.tar
    - echo "$CI_REGISTRY_PASSWORD" | docker login "$CI_REGISTRY" -u "$CI_REGISTRY_USER" --password-stdin
    - docker tag "$IMAGE_TAG" "$IMAGE_LATEST"
    - docker push "$IMAGE_TAG"
    - docker push "$IMAGE_LATEST"
EOF

    Этап 3. Локальный прогон всех стадий CI-конвейера в Docker

    Чтобы убедиться, что каждый шаг нашего конвейера работает безупречно (точно так же, как его выполнит Docker Executor в GitLab Runner), выполни локальный прогон всех стадий одной командой:

    cd ~/compose-cluster

echo "=== [STAGE 1.1] Запуск линтера Python (Ruff) ==="
docker run --rm -v "$(pwd):/work" -w /work python:3.12-slim \
  sh -c "pip install -q ruff==0.6.2 && ruff check app/"

echo "=== [STAGE 1.2] Запуск линтера Dockerfile (Hadolint) ==="
docker run --rm -i hadolint/hadolint:latest-debian hadolint --ignore DL3008 - < app/Dockerfile

echo "=== [STAGE 2.1] Статический анализ безопасности кода (Bandit SAST) ==="
docker run --rm -v "$(pwd):/work" -w /work python:3.12-slim \
  sh -c "pip install -q bandit==1.7.9 && bandit -r app/main.py -ll"

echo "=== [STAGE 2.2] Запуск интеграционных тестов Pytest со связкой PostgreSQL + Redis ==="
docker compose up -d db redis
docker run --rm \
  --network compose-cluster_backend-net \
  -v "$(pwd):/work" -w /work \
  -e DB_HOST=db \
  -e POSTGRES_USER=app_admin \
  -e POSTGRES_DB=cluster_db \
  -e POSTGRES_PASSWORD=SuperStrongPgSecret2026 \
  -e REDIS_HOST=redis \
  python:3.12-slim \
  sh -c "pip install -q -r app/requirements-dev.txt && pytest app/tests/ -v"

echo "=== [STAGE 3 & 4] Сборка образа и проверка безопасности через Trivy ==="
docker build -t compose-cluster-backend:ci-test ./app
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 compose-cluster-backend:ci-test
