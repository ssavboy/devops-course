    Введение в DevOps и системы контроля версий Git

    В современном DevOps всё является кодом: исходный код приложений, конфигурация серверов (Ansible), описание облачной инфраструктуры (Terraform), манифесты кластера (Kubernetes) и сами пайплайны сборки (CI/CD). Поэтому Git — это единый источник истины (Single Source of Truth), с которого начинается любое изменение в инфраструктуре.

    Блок 1. Философия и культура DevOps

    1.1. Историческая проблема: «Стена отчуждения» (Wall of Confusion)

    До появления DevOps разработка (Development) и эксплуатация (Operations) имели прямо противоположные KPI:

    • Цель разработчиков (Dev): Как можно быстрее выпускать новые фичи для бизнеса (Изменения = хорошо).
    • Цель администраторов (Ops): Чтобы серверы работали стабильно и ничего не падало (Изменения = риск падения).

    Разработчики перекидывали код «через забор» со словами «У меня на ноутбуке всё работало!», а админы вручную деплоили его по ночам и блокировали частые релизы. DevOps убирает эту стену, объединяя процессы, людей и инструменты вокруг общей цели — быстрой и безопасной доставки ценности конечному пользователю.

    1.2. Модель CALMS и её влияние на скорость разработки

    Акроним CALMS (предложенный Джезом Хамблом) описывает 5 столпов зрелого DevOps-процесса:

    Буква Расшифровка Суть и влияние на Time-to-Market
    C Culture (Культура) Отказ от поиска виноватых (Blameless Postmortems). Если упал прод — виноват не человек, который нажал кнопку, а процесс, который позволил ошибке дойти до прода без проверок. Общая ответственность: «You build it, you run it».
    A Automation (Автоматизация) Устранение ручного труда (toil). Ручная настройка серверов по SSH запрещена — всё делается через CI/CD, Terraform и Ansible. Это ускоряет релизы с недель до минут.

    | | L | Lean (Бережливое производство) | Фокус на маленьких партиях изменений (Small Batch Sizes) и устранении потерь времени (ожиданий ревью, ручного тестирования). Проще выкатить и протестировать 10 строчек кода, чем релиз за полгода на 50 000 строк.

    | | M | Measurement (Измерения) | Если вы что-то не измеряете, вы не можете это улучшить. Измеряется всё: от загрузки CPU до бизнес-метрик и скорости доставки кода (DORA-метрики).

    | | S | Sharing (Обмен знаниями) | Отсутствие «незаменимых шаманов» (низкого Bus Factor). Единая документация, открытые репозитории, совместные разборы инцидентов и взаимное обучение между Dev, QA и Ops. |

    1.3. Четыре ключевые DORA-метрики эффективности

    Исследовательская группа DORA выделила 4 метрики, которые объективно показывают качество инженерных процессов в компании:

    1. Deployment Frequency (Частота релизов): Как часто команда успешно выкатывает код в продакшен (у лидеров индустрии — по запросу, десятки раз в день).
    2. Lead Time for Changes (Время вывода изменений): Время от момента создания коммита до того, как этот код начал работать в продакшене (цель — менее часа).
    3. Change Failure Rate (Доля неуспешных изменений): Какой процент деплоев приводит к деградации сервиса, хотфиксам или откату (цель — $0\text{–}15\%$).
    4. MTTR (Mean Time to Restore / Recovery): Среднее время восстановления сервиса после аварии (цель — менее часа, достигается за счет мониторинга и автоматического отката).

    Блок 2. Внутреннее устройство Git: репозитории, коммиты и история

    2.1. Как Git хранит данные под капотом

    В отличие от старых систем (SVN), которые хранили разницу между файлами (дельты), Git хранит полные слепки состояния (snapshots) в виде направленного ациклического графа (DAG) в папке .git/objects/.

    Внутри Git есть 4 основных типа объектов, идентифицируемых по SHA-1 хэшу (40 шестнадцатеричных символов):

    • blob: Содержимое конкретного файла (без имени файла и прав).
    • tree: Аналог директории — содержит список имен файлов, их права и ссылки на blob-объекты и другие tree.
    • commit: Слепок проекта. Содержит ссылку на корневой объект tree, метаданные автора, сообщение коммита и ссылку на родительский коммит (parent).
    • tag: Постоянная именная метка, привязанная к конкретному коммиту (например, v1.2.0).

    Что такое ветка (Branch)? Ветка в Git — это не копия файлов! Это просто крошечный текстовый файл (весом 41 байт) в .git/refs/heads/, внутри которого записан SHA-1 хэш последнего коммита. Поэтому создание и переключение веток в Git происходит мгновенно. Указатель HEAD показывает, на какой ветке или коммите вы находитесь прямо сейчас.

    2.2. Четыре зоны состояния файлов в Git

    1. Working Directory (Рабочая директория): Файлы, которые вы прямо сейчас редактируете на диске.
    2. Staging Area / Index (Индекс): Промежуточная зона подготовки. Сюда вы складываете (git add) только те изменения, которые должны войти в следующий осмысленный коммит.

    3. Local Repository (.git): Ваша локальная база данных коммитов (git commit).

    4. Remote Repository (origin): Удаленный сервер (GitLab, GitHub), куда пушатся изменения (git push).

    [Working Dir]  --(git add)-->  [Staging / Index]  --(git commit)-->  [Local Repo]  --(git push)-->  [Remote Repo]

    Базовая настройка и навигация по истории:

    # Обязательная первичная настройка имени и почты
git config --global user.name "Ivan Petrov"
git config --global user.email "i.petrov@example.com"
git config --global init.defaultBranch main

# Красивый граф истории коммитов со всеми ветками в терминале
git log --oneline --graph --decorate --all

# Посмотреть, какие именно строки изменились в каждом коммите
git log -p -n 2

# Узнать, кто и каким коммитом изменил каждую строчку в конфиге (незаменимо при разборе полетов!)
git blame nginx.conf

    Блок 3. Стратегии ветвления (Branching Strategies)

    Выбор стратегии ветвления напрямую влияет на то, как вы будете строить CI/CD пайплайны в следующих модулях.

    | Характеристика | GitFlow

    | GitHub Flow

    | Trunk-Based Development (TBD) | | --- | --- | --- | --- | | Основные ветки | main, develop, feature/*, release/*, hotfix/* | main + короткоживущие feature/* | main (trunk) + микро-ветки на пару часов | | Жизненный цикл фичи | Длинный: feature $\rightarrow$ develop $\rightarrow$ release $\rightarrow$ main | Простой: feature $\rightarrow$ Pull Request $\rightarrow$ main $\rightarrow$ Деплой | Сверхбыстрый: слияние в main минимум раз в день (использование Feature Flags)

    | | Плюсы | Строгий контроль версий, удобно поддерживать несколько старых релизов параллельно | Простота, прозрачность, быстрый вывод фич в прод | Нет болезненных merge-конфликтов, максимальная скорость CI/CD | | Минусы | Огромная бюрократия, долгоживущие ветки, тяжелые конфликты слияния | Требует надежных автотестов в CI перед слиянием в main | Требует высокой зрелости команды и умения работать с Feature Flags | | Где применяется | Коробочный софт, мобильные приложения, легаси-банкинг | 80% современных веб-сервисов и инфраструктурных репозиториев (IaC) | Зрелые продуктовые компании с непрерывным деплоем (CD) |

    Блок 4. Сравнение версий, разрешение конфликтов и чистота истории

    4.1. Сравнение версий (git diff)

    Перед тем как делать коммит или вливать чужую ветку, инженер всегда проверяет дельту изменений:

    # Что изменилось в рабочей папке, но еще НЕ добавлено в индекс (git add)
git diff

# Что уже лежит в индексе (staged) и прямо сейчас войдет в коммит
git diff --staged

# Сравнить две ветки между собой (например, main и feature/nginx-tuning)
git diff main..feature/nginx-tuning

# Показать только список измененных файлов между двумя коммитами
git diff --name-status a1b2c3d f4e5d6c

    4.2. git merge vs git rebase и поддержание чистоты истории

    Когда вы работаете в своей ветке feature, основная ветка main успевает уйти вперед. Объединить изменения можно двумя способами:

    1. git merge (Слияние)

    • Создает специальный merge-коммит, имеющий сразу двух родителей.
    • Плюс: Сохраняет точную хронологическую правду.
    • Минус: Если разработчики постоянно подтягивают main в свои ветки через merge, история превращается в нечитаемую «гитару» из переплетенных линий.

    2. git rebase (Перебазирование)

    • Берет ваши коммиты из ветки feature, временно откладывает их, перематывает ветку на самый свежий коммит main и по очереди применяет ваши коммиты поверх (переписывая их хэши).

    • Плюс: Идеально прямая, линейная история коммитов без лишнего шума.

    • Золотое правило безопасности Rebase: Никогда не делайте rebase публичных общих веток (main, develop), в которых уже работают другие люди! Делать rebase можно только для своей локальной фича-ветки перед отправкой в Pull Request.

    Интерактивный ребейз (git rebase -i) и Squashing

    В процессе работы над задачей вы могли сделать 5 черновых коммитов: WIP, fix typo, try again, almost working. Вливать такой мусор в main — дурной тон.

    Перед открытием Pull Request их склеивают (squash) в один чистый коммит:

    # Открыть интерактивный ребейз для последних 4 коммитов
git rebase -i HEAD~4

    В открывшемся редакторе у первого коммита оставляем слово pick, а у остальных меняем pick на squash (или s) — они сольются в один аккуратный коммит.

    4.3. Анатомия и разрешение Merge-конфликтов

    Конфликт возникает, когда в двух сливаемых ветках была изменена одна и та же строка одного и того же файла (или в одной ветке файл удалили, а в другой отредактировали).

    При возникновении конфликта Git помечает проблемный участок специальными маркерами:

    <<<<<<< HEAD
worker_processes 4;
=======
worker_processes auto;
>>>>>>> feature/optimize-nginx
    • Между <<<<<<< HEAD и ======= — то, что находится в вашей текущей ветке.
    • Между ======= и >>>>>>> feature/... — то, что пришло из вливаемой ветки.

    Алгоритм разрешения конфликта:

    1. Посмотреть список конфликтующих файлов: git status.
    2. Открыть файл в редакторе, выбрать правильный вариант кода и **полностью удалить строки с маркерами <<<<<<<, =======, >>>>>>>**.
    3. Отметить, что конфликт решен: git add <имя_файла>.
    4. Завершить слияние: git commit (для merge) или git rebase --continue (для rebase). (Если всё пошло не так и хочется вернуть как было до начала слияния: git merge --abort или git rebase --abort).

    Блок 5. Командная работа через Pull / Merge Requests и антипаттерны

    5.1. Стандарты оформления коммитов (Conventional Commits)

    Чтобы по истории репозитория можно было автоматически генерировать Changelog и понимать суть правок за секунду, используют стандарт Conventional Commits:

    • feat: add prometheus exporter config — новая функциональность.
    • fix: resolve port conflict in nginx.conf — исправление ошибки.
    • refactor: simplify backup bash script — рефакторинг без изменения логики.
    • docs: update README deployment guide — обновление документации.
    • ci: add linter stage to gitlab-ci — правки конвейера сборки.

    5.2. Культура Pull Requests (GitHub) / Merge Requests (GitLab)

    Ветка main в реальных проектах всегда закрыта от прямого git push (Protected Branch). Любое изменение попадает туда только через PR/MR:

    1. Инженер пушит ветку feat/add-firewall на сервер и открывает PR/MR.

    2. Автоматически запускается CI-пайплайн (линтеры, тесты, проверка безопасности).

    3. Коллеги проводят Code Review (оставляют комментарии к строкам кода, проверяют архитектуру).

    4. После получения аппрувов (например, минимум 1–2 Approve) и зеленого статуса пайплайна ветка вливается в main (часто с галочкой Squash commits и Delete source branch).

    Спасательный круг инженера: git reflog

    Если вы случайно сделали git reset --hard, удалили не ту ветку или неудачно сделали rebase, «потеряв» коммиты — не паникуйте. Git хранит локальный журнал всех перемещений указателя HEAD минимум 30–90 дней:

    # Посмотреть историю всех ваших действий в репозитории
git reflog

# Восстановить состояние на момент любого шага из reflog
git reset --hard HEAD@{2}

    🛠 Практический проект Модуля 1: Рефакторинг проблемного репозитория

    Представь реальную рабочую ситуацию: тебе достался инфраструктурный репозиторий от уволившегося джуна. В нём полный хаос:

    • В историю попал файл с паролями от базы secrets.env и мусорные логи *.log.
    • Нет файла .gitignore.
    • В рабочей ветке куча кривых мелких коммитов (test, oops, fix2).
    • Между ветками висит неразрешенный конфликт в конфигурационном файле.

    Твоя задача — провести полный рефакторинг репозитория прямо в терминале.

    Этап 1. Генерация «проблемного» репозитория (стенд задачи)

    Скопируй и выполни этот блок команд целиком — он автоматически создаст на твоей машине учебный репозиторий messy-infra-repo со всеми типичными ошибками:

    mkdir -p ~/messy-infra-repo && cd ~/messy-infra-repo
git init -b main

# 1. Первый коммит с конфигом и случайно добавленными секретами и логами
cat << 'EOF' > app.conf
PORT=8080
WORKERS=2
LOG_LEVEL=debug
EOF

echo "DB_PASSWORD=SuperSecretProdPass123!" > secrets.env
echo "2026-10-18 ERROR connection timeout" > debug.log

git add .
git commit -m "initial commit"

# 2. Создаем ветку фичи с "грязной" историей коммитов и конфликтующим изменением
git checkout -b feature/prod-tuning
sed -i 's/WORKERS=2/WORKERS=8/' app.conf
git commit -am "update workers"

echo "# temp note" >> app.conf
git commit -am "wip"

sed -i 's/LOG_LEVEL=debug/LOG_LEVEL=warn/' app.conf
git commit -am "oops forgot log level"

# 3. Возвращаемся в main и создаем встречное изменение в той же строке (провоцируем конфликт!)
git checkout main
sed -i 's/WORKERS=2/WORKERS=4/' app.conf
git commit -am "hotfix workers count in main"

    Посмотри на текущее состояние с помощью git log --oneline --graph --all. Теперь начинаем наводить порядок по шагам!

    Этап 2. Удаление секретов и мусора из индекса и настройка .gitignore

    1. Создай правильный файл .gitignore, чтобы логи, секреты и временные файлы больше никогда не попадали в Git:
    cat << 'EOF' > .gitignore
# Secrets and environments
*.env
*.key
*.pem

# Logs and temp files
*.log
*.tmp
.DS_Store
EOF
    1. Удали secrets.env и debug.log из отслеживания Git, но оставь сам файл secrets.env лежать локально на диске (флаг --cached удаляет файл только из индекса Git, не стирая его с диска!):
    git rm --cached secrets.env
git rm -f debug.log

git add .gitignore
git commit -m "chore: add .gitignore and untrack sensitive files"

    Этап 3. Очистка истории ветки (Interactive Rebase & Squash)

    Переключись в ветку feature/prod-tuning и посмотри на её неряшливую историю:

    git checkout feature/prod-tuning
git log --oneline -n 4

    Мы видим три мелких коммита (oops forgot log level, wip, update workers). Склеим их в один атомарный коммит с правильным сообщением по стандарту Conventional Commits:

    # Сбрасываем мягко (soft) 3 последних коммита, оставляя все их изменения в индексе (staged)
git reset --soft HEAD~3

# Убираем мусорную строчку "# temp note" из файла app.conf
sed -i '/# temp note/d' app.conf

# Делаем один чистый и понятный коммит
git add app.conf
git commit -m "feat(config): optimize workers count and set warn log level"

    Проверь git log --oneline — вместо трёх мусорных коммитов остался один образцовый!

    Этап 4. Перебазирование на main и разрешение конфликта

    Теперь подтянем актуальные изменения из ветки main, используя rebase, чтобы история осталась идеально линейной:

    git rebase main

    Git остановится и сообщит о конфликте: CONFLICT (content): Merge conflict in app.conf.

    1. Посмотри на конфликт внутри файла cat app.conf:
    PORT=8080
<<<<<<< HEAD
WORKERS=4
LOG_LEVEL=debug
=======
WORKERS=8
LOG_LEVEL=warn
>>>>>>> feat(config): optimize workers count...
    1. Разреши конфликт вручную (оставляем финальные продакшен-настройки WORKERS=8 и LOG_LEVEL=warn без маркеров конфликта):
    cat << 'EOF' > app.conf
PORT=8080
WORKERS=8
LOG_LEVEL=warn
EOF
    1. Добавь исправленный файл в индекс и заверши ребейз:
    git add app.conf
git rebase --continue

    (Если откроется текстовый редактор для подтверждения сообщения коммита — в nano нажми Ctrl+O, Enter, Ctrl+X, а в vim введи :wq и Enter).

    1. Влей чистую ветку в main и удали отработанную фича-ветку:
    git checkout main
git merge feature/prod-tuning
git branch -d feature/prod-tuning

    Этап 5 (Продвинутый DevSecOps). Полная зачистка пароля из глубокой истории Git

    Мы удалили secrets.env во втором этапе, но если выполнить git log -p, пароль SuperSecretProdPass123! всё еще виден в самом первом коммите (initial commit)!

    Вычистим файл secrets.env из всех исторических коммитов репозитория:

    git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch secrets.env" \
  --prune-empty --tag-name-filter cat -- --all

    ✅ Чек-лист самопроверки по Модулю 1

    Выполни эти 3 проверочные команды в папке ~/messy-infra-repo:

    1. Проверка линейности и чистоты истории:
    git log --oneline --graph --all

    Ожидаемый результат: Прямая линия из 4 аккуратных коммитов без лишних веток и коммитов wip/oops. 2. Проверка работы .gitignore: 

    git status

    Ожидаемый результат: nothing to commit, working tree clean (при том, что файл secrets.env продолжает лежать в папке ls -la, но Git его полностью игнорирует). 3. Проверка отсутствия утечки пароля во всей истории коммитов:

    git log -S "SuperSecretProdPass123!" --oneline

    Ожидаемый результат: Пустой вывод! Пароль бесследно стерт из истории репозитория.
