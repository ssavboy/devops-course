    Управление конфигурацией (SCM) — Ansible

    В предыдущем модуле мы изучили Terraform, который отвечает за создание облачного «железа» (сетей, виртуальных машин, дисков и бакетов). Но когда виртуальная машина только что создана в облаке — внутри неё абсолютно пустая операционная система. Кто установит на 50 новых серверов Docker, настроит права пользователей, пропишет правила фаервола, разложит SSL-сертификаты и сгенерирует конфигурационные файлы nginx.conf под каждое окружение?

    Эту задачу решает класс инструментов SCM (Software Configuration Management — Управление конфигурацией), и безусловный стандарт индустрии здесь — Ansible.

    [ Terraform / OpenTofu ]                 [ Ansible ]
Создает инфраструктуру в облаке   ───►   Настраивает ОС и софт внутри ВМ
(VPC, Subnets, VMs, Disks, S3)           (Users, SSH, Firewall, Docker, Configs)

    Блок 1. Архитектура Ansible, Инвентарь и Идемпотентность

    1.1. Безагентная архитектура (Agentless)

    Главное преимущество Ansible перед старыми системами (Puppet, Chef, SaltStack) — безагентная архитектура (Agentless): * На целевые серверы (Managed Nodes) не нужно устанавливать никаких специальных демонов-агентов, которые висят в памяти и требуют обновлений. * Всё, что нужно от целевого сервера — работающий SSH-сервер и установленный Python (который уже есть из коробки в Ubuntu/Debian/RHEL). * С вашего ноутбука или раннера GitLab CI (Control Node) Ansible подключается к серверам по SSH, передает маленькие Python-скрипты (модули), выполняет их и удаляет за собой временные файлы.

    1.2. Главный принцип: Идемпотентность (Idempotency)

    Идемпотентность — это свойство операции, при котором повторный запуск плейбука 1, 10 или 100 раз подряд приводит сервер в одно и то же желаемое состояние, не совершая лишних действий и не ломая систему.

    • Неидемпотентный подход (плохой Bash): Команда echo "Port 2222" >> /etc/ssh/sshd_config при каждом запуске будет дописывать новую строчку в конец файла, пока конфиг не сломается.
    • Идемпотентный подход (модуль Ansible lineinfile): Ansible сначала прочитает файл /etc/ssh/sshd_config. Если строчка Port 2222 там уже есть — он ничего не тронет и вернет зеленый статус ok. Если строчки нет — он аккуратно добавит её и вернет желтый статус changed.

    Три главных цвета в выводе Ansible: * 🟢 ok: Сервер уже находится в нужном состоянии, никаких изменений не потребовалось. * 🟡 changed: Ansible внес изменения на сервере (установил пакет, изменил конфиг, перезапустил сервис). * 🔴 failed / unreachable: Произошла ошибка выполнения или сервер недоступен по SSH.

    1.3. Инвентаризация (Inventory): Статическая и Динамическая

    Inventory (Инвентарь) — это список ваших серверов, разбитый по логическим группам (webservers, databases, k8s_nodes) и окружениям (staging, production). Современный стандарт оформления инвентаря — формат YAML (inventory.yml):

    all:
  vars:
    ansible_user: deployer
    ansible_ssh_private_key_file: ~/.ssh/id_ed25519_devops
    ansible_python_interpreter: /usr/bin/python3

  children:
    webservers:
      hosts:
        web-01:
          ansible_host: 10.10.1.11
          http_port: 8080
        web-02:
          ansible_host: 10.10.1.12
          http_port: 8080

    databases:
      hosts:
        db-master:
          ansible_host: 10.10.1.50
          pg_max_connections: 200

    Динамический инвентарь (Dynamic Inventory): В облаках (Yandex Cloud, AWS) IP-адреса серверов меняются динамически при масштабировании. Вместо ручного редактирования inventory.yml используют плагины динамического инвентаря (или генерацию inventory.yml напрямую через terraform output!), которые сами опрашивают API облака по тегам и собирают актуальный список хостов на лету.

    Блок 2. Переменные, Факты (Facts), Условия и Шаблоны Jinja2

    2.1. Переменные (group_vars и host_vars) и Факты (ansible_facts)

    Чтобы не смешивать список IP-адресов с настройками в одном файле, Ansible автоматически подхватывает переменные из двух специальных папок рядом с инвентарем: * group_vars/webservers.yml — переменные для всей группы webservers. * host_vars/web-01.yml — индивидуальные переменные для конкретного хоста web-01 (переопределяют групповые).

    Сбор фактов о сервере (Gathering Facts — модуль setup):

    Перед выполнением первой задачи каждого плейбука Ansible автоматически опрашивает сервер и собирает сотни системных параметров в словарь ansible_facts: * ansible_facts['os_family'] — семейство ОС (Debian, RedHat). * ansible_facts['distribution_version'] — версия дистрибутива (24.04). * ansible_facts['processor_vcpus'] — количество ядер CPU. * ansible_facts['memtotal_mb'] — объем оперативной памяти в МБ. * ansible_facts['default_ipv4']['address'] — основной IP-адрес сервера.

    2.2. Условные конструкции (when) и Циклы (loop)

    Зная факты о сервере, мы можем адаптировать поведение плейбука под разные ОС и окружения:

    - name: Установка веб-сервера и создание пользователей
  hosts: webservers
  become: true # Выполнять задачи с привилегиями root (через sudo)

  tasks:
    # Условие when: выполнится только на системах семейства Debian/Ubuntu
    - name: Установить Nginx на Debian/Ubuntu
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
      when: ansible_facts['os_family'] == "Debian"

    # Цикл loop: создание сразу нескольких системных директорий за один шаг
    - name: Создать рабочие директории проекта
      ansible.builtin.file:
        path: "{{ item }}"
        state: directory
        owner: www-data
        group: www-data
        mode: "0755"
      loop:
        - /opt/app
        - /opt/app/config
        - /var/log/app

    Золотое правило безопасности Ansible: Никогда не используйте модули shell: или command: для установки пакетов или создания файлов! Команды в shell: неидемпотентны и всегда возвращают changed. Всегда используйте специализированные модули (ansible.builtin.apt, file, copy, template, user, systemd). Если всё же пришлось вызвать command:, указывайте параметр creates: /path/to/file или changed_when: false.

    2.3. Динамическая шаблонизация конфигов через Jinja2 (.j2)

    Представь, что у тебя 10 серверов: на одном 2 ядра CPU и 2 ГБ RAM, а на другом — 16 ядер и 64 ГБ RAM. Как сгенерировать для каждого из них идеальный nginx.conf или postgresql.conf автоматически?

    Для этого используется шаблонизатор Jinja2 (модуль ansible.builtin.template). Внутри шаблона nginx.conf.j2 доступны: * {{ переменная }} — подстановка переменных и системных фактов (включая математику, например выделение 25% RAM под БД: {{ (ansible_facts['memtotal_mb'] * 0.25) | int }}MB). * {% if ... %} ... {% endif %} — ветвления внутри конфига (например, включить access_log только на staging, а на prod писать только ошибки). * {% for item in list %} ... {% endfor %} — автоматическая генерация списка серверов в блоке upstream!

    Пример умного шаблона templates/nginx.conf.j2: 

    # Файл сгенерирован автоматически через Ansible. Ручные правки запрещены!
# Сервер: {{ inventory_hostname }} (ОС: {{ ansible_facts['distribution'] }})
worker_processes {{ ansible_facts['processor_vcpus'] }};

events {
    worker_connections {{ max_connections | default(1024) }};
}

http {
{% if env_name == 'production' %}
    access_log off;
    error_log /var/log/nginx/error.log crit;
{% else %}
    access_log /var/log/nginx/access.log;
    error_log /var/log/nginx/error.log debug;
{% endif %}

    server {
        listen {{ http_port }};
        location /status {
            return 200 '{"node": "{{ inventory_hostname }}", "cpus": {{ ansible_facts["processor_vcpus"] }}, "env": "{{ env_name }}"}\n';
        }
    }
}

    Блок 3. Отказоустойчивые плейбуки: Обработчики (Handlers), Блоки ошибок и Стратегии

    3.1. Обработчики событий (Handlers и notify)

    Мы изменили файл nginx.conf из шаблона Jinja2. Чтобы настройки вступили в силу, нужно выполнить systemctl reload nginx. * Если просто поставить задачу рестарта Nginx обычным шагом внизу плейбука — Nginx будет перезапускаться при каждом запуске Ansible, даже если конфиг вообще не менялся! * Решение — Handlers (Обработчики): Задачи в секции handlers: спят и запускаются только тогда, когда задача выше реально изменила файл (вернула статус changed) и послала сигнал notify:! При этом, даже если 5 разных задач за время плейбука вызвали notify: Reload Nginx, сам обработчик выполнится ровно один раз в самом конце плейбука.

    3.2. Блоки перехвата ошибок (block / rescue / always)

    Как в Python есть конструкция try / except / finally, так и в Ansible для создания отказоустойчивых плейбуков с автооткатом используется конструкция block / rescue / always: * block: — основные задачи (например, выкатить новый конфиг и проверить его валидность). * rescue: — выполняется только если любая задача внутри block упала с ошибкой (например: вернуть старый бэкап конфига и отправить алерт в Telegram). * always: — выполняется всегда, независимо от успеха или ошибки (например: очистить временные установочные архивы в /tmp).

    - name: Безопасное обновление конфигурации с автооткатом при ошибке
  block:
    - name: Выкатить новый конфиг приложения
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/myapp/app.conf
        backup: true # Создать резервную копию перед перезаписью
      register: config_result

    - name: Проверить валидность нового конфига
      ansible.builtin.command: /usr/bin/myapp --check-config
      changed_when: false

  rescue:
    - name: АВАРИЙНЫЙ ОТКАТ — вернуть старый конфиг из бэкапа при ошибке валидации
      ansible.builtin.copy:
        src: "{{ config_result.backup_file }}"
        dest: /etc/myapp/app.conf
        remote_src: true
      when: config_result.backup_file is defined

  always:
    - name: Убедиться, что сервис запущен
      ansible.builtin.service:
        name: myapp
        state: started

    3.3. Стратегии выполнения и Rolling Updates (serial, max_fail_percentage)

    По умолчанию Ansible применяет каждую задачу ко всем серверам группы одновременно (стратегия linear, по 5 хостов за раз — параметр forks). Если вы обновляете боевой кластер из 10 веб-серверов и перезапустите их все одновременно — сайт упадет!

    Для бесперебойного обновления (Rolling Update) в плейбуке задают: * serial: 2 (или serial: "25%") — Ansible будет полностью проходить весь плейбук сначала только на первых 2 серверах, и лишь убедившись, что они живы, перейдет к следующим двум! * max_fail_percentage: 20 — если более 20% серверов первой пачки упали с ошибкой, немедленно остановить обновление всего остального кластера!

    Блок 4. Модульные Роли (Roles), Ansible Galaxy и защита секретов (Ansible Vault)

    4.1. Структура Ролей (Roles) для переиспользования кода

    Хранить все задачи, шаблоны и переменные в одном гигантском файле playbook.yml — антипаттерн. В промышленной разработке код разбивается на независимые Роли (roles/) по компонентам: роль security_baseline, роль docker, роль postgresql, роль nginx_proxy.

    Стандартная структура роли (создается автоматически командой ansible-galaxy role init <имя_роли>):

    roles/
└── webapp_node/
    ├── defaults/
    │   └── main.yml      # Переменные по умолчанию (самый низкий приоритет, легко переопределить)
    ├── tasks/
    │   └── main.yml      # Главный список задач роли
    ├── handlers/
    │   └── main.yml      # Обработчики перезапуска сервисов (notify)
    ├── templates/
    │   └── app.conf.j2   # Шаблоны Jinja2
    ├── files/
    │   └── ca.crt        # Статические файлы для копирования без изменений
    └── meta/
        └── main.yml      # Зависимости роли и авторство

    4.2. Интеграция готовых решений из Ansible Galaxy

    Ansible Galaxy — это официальный публичный реестр готовых ролей и коллекций от сообщества и вендоров (например, эталонная роль установки Docker geerlingguy.docker или коллекция community.postgresql).

    Список внешних зависимостей фиксируется в файле requirements.yml: 

    ---
roles:
  - name: geerlingguy.security
    version: 2.3.0

collections:
  - name: community.general
    version: ">=9.0.0"
    Установка зависимостей одной командой перед запуском пайплайна: 
    ansible-galaxy install -r requirements.yml

    4.3. Шифрование секретов с помощью Ansible Vault

    Как хранить пароли от БД, токены API и приватные ключи прямо внутри Git-репозитория вместе с кодом Ansible, не нарушая безопасность? Для этого в Ansible встроен криптографический инструмент ansible-vault (алгоритм шифрования AES-256):

    # 1. Зашифровать файл с секретами паролем (файл превратится в нечитаемый шифротекст $ANSIBLE_VAULT;1.1;AES256)
ansible-vault encrypt group_vars/production/vault.yml

# 2. Посмотреть содержимое зашифрованного файла без расшифровки на диске
ansible-vault view group_vars/production/vault.yml

# 3. Отредактировать зашифрованный файл на лету
ansible-vault edit group_vars/production/vault.yml

# 4. Запустить плейбук с передачей мастер-пароля из файла (или из переменной GitLab CI)
ansible-playbook site.yml --vault-password-file .vault_pass
    Безопасно коммитить в Git: Зашифрованный через ansible-vault файл абсолютно безопасно хранить в Git! Главное — добавить сам файл мастер-пароля .vault_pass в .gitignore.

    🛠 Практический проект Модуля 9: Разработка Ansible-проекта с ролями, шаблонами Jinja2, блоками отказоустойчивости и Ansible Vault

    Мы соберем полноценный инфраструктурный проект Ansible, который: 1. Подключает внешнюю коллекцию из Ansible Galaxy. 2. Хранит секретные API-ключи в зашифрованном виде через Ansible Vault (AES-256). 3. Разделяет переменные для окружений staging и production через group_vars. 4. Использует собственную модульную роль microservice_config, которая: * Собирает системные факты о хосте (CPU, RAM, OS). * Генерирует индивидуальные конфигурационные файлы сервисов и Nginx из шаблонов Jinja2 под конкретное окружение. * Проверяет валидность конфига внутри отказоустойчивого блока block / rescue с автооткатом. * Вызывает handler только при реальном изменении файлов.

    Этап 1. Установка Ansible и создание каркаса проекта

    1. Проверим наличие ansible (если не установлен — установим за 15 секунд): 

      if ! command -v ansible-playbook &> /dev/null; then
    echo "Устанавливаем Ansible..."
    sudo apt-get update && sudo apt-get install -y ansible
fi
ansible --version

    2. Создадим промышленную структуру каталогов и инициализируем роль microservice_config с помощью ansible-galaxy: 

      mkdir -p ~/ansible-practice/{inventories/staging,inventories/production,roles}
cd ~/ansible-practice

# Создаем стандартный каркас роли через встроенный генератор ansible-galaxy
ansible-galaxy role init roles/microservice_config

    3. Создадим главный конфигурационный файл ansible.cfg и файл внешних зависимостей requirements.yml для Ansible Galaxy: 

      cat << 'EOF' > ~/ansible-practice/ansible.cfg
[defaults]
inventory = inventories/staging/hosts.yml
roles_path = ./roles
host_key_checking = False
retry_files_enabled = False
stdout_callback = yaml
interpreter_python = auto_silent
EOF

cat << 'EOF' > ~/ansible-practice/requirements.yml
---
collections:
  - name: community.general
EOF

# Устанавливаем коллекцию из Ansible Galaxy
ansible-galaxy collection install -r requirements.yml

    Этап 2. Настройка Инвентаря, Переменных окружений (group_vars) и шифрования Ansible Vault

    Мы настроим два окружения (staging и production), которые будут раскатывать конфигурации в изолированные директории /tmp/ansible-env-staging и /tmp/ansible-env-production на нашем хосте — это позволит мгновенно увидеть разницу генерации шаблонов для разных сред!

    # 1. Инвентарь и переменные для STAGING
mkdir -p ~/ansible-practice/inventories/staging/group_vars/app_cluster

cat << 'EOF' > ~/ansible-practice/inventories/staging/hosts.yml
all:
  children:
    app_cluster:
      hosts:
        stage-node-01:
          ansible_connection: local
          http_port: 8081
EOF

cat << 'EOF' > ~/ansible-practice/inventories/staging/group_vars/app_cluster/vars.yml
env_name: staging
deploy_root: /tmp/ansible-env-staging
app_workers: 2
enable_debug_logs: true
db_secret_password: "{{ vault_db_password }}"
EOF

# 2. Инвентарь и переменные для PRODUCTION
mkdir -p ~/ansible-practice/inventories/production/group_vars/app_cluster

cat << 'EOF' > ~/ansible-practice/inventories/production/hosts.yml
all:
  children:
    app_cluster:
      hosts:
        prod-node-01:
          ansible_connection: local
          http_port: 9091
EOF

cat << 'EOF' > ~/ansible-practice/inventories/production/group_vars/app_cluster/vars.yml
env_name: production
deploy_root: /tmp/ansible-env-production
app_workers: 8
enable_debug_logs: false
db_secret_password: "{{ vault_db_password }}"
EOF

    Создадим и зашифруем секретный файл vault.yml с помощью ansible-vault:

    cd ~/ansible-practice

# Создаем мастер-ключ шифрования (и сразу прячем его в .gitignore!)
echo "MyVaultMasterKey2026!" > .vault_pass
chmod 600 .vault_pass
echo ".vault_pass" > .gitignore

# Создаем файл с секретами для обоих окружений
cat << 'EOF' > inventories/staging/group_vars/app_cluster/vault.yml
vault_db_password: "Stage_Encrypted_DB_Password_123"
EOF

cat << 'EOF' > inventories/production/group_vars/app_cluster/vault.yml
vault_db_password: "PROD_Ultra_Secret_Vault_Password_999!"
EOF

# Шифруем оба файла алгоритмом AES-256 через ansible-vault!
ansible-vault encrypt inventories/staging/group_vars/app_cluster/vault.yml --vault-password-file .vault_pass
ansible-vault encrypt inventories/production/group_vars/app_cluster/vault.yml --vault-password-file .vault_pass

    Посмотри, во что превратился файл секретов на диске: 

    head -n 5 inventories/production/group_vars/app_cluster/vault.yml
    Ты увидишь заголовок $ANSIBLE_VAULT;1.1;AES256 и криптографический шифр вместо пароля!

    Этап 3. Наполнение роли microservice_config (Defaults, Jinja2 Templates, Tasks, Block/Rescue, Handlers)

    1. Зададим значения по умолчанию в roles/microservice_config/defaults/main.yml: 

      cat << 'EOF' > ~/ansible-practice/roles/microservice_config/defaults/main.yml
---
env_name: development
deploy_root: /tmp/ansible-env-dev
http_port: 8000
app_workers: 1
enable_debug_logs: true
simulate_broken_config: false
EOF

    2. Создадим динамический шаблон Jinja2 roles/microservice_config/templates/service.conf.j2, использующий системные факты (ansible_facts), математику памяти, условия {% if %} и расшифрованный секрет из Vault: 

      cat << 'EOF' > ~/ansible-practice/roles/microservice_config/templates/service.conf.j2
# =====================================================================
# MANAGED BY ANSIBLE ROLE: microservice_config
# Target Host: {{ inventory_hostname }} | OS: {{ ansible_facts['distribution'] }} {{ ansible_facts['distribution_version'] }}
# Hardware Facts: {{ ansible_facts['processor_vcpus'] }} vCPUs / {{ ansible_facts['memtotal_mb'] }} MB RAM
# =====================================================================

[server]
environment = {{ env_name }}
listen_port = {{ http_port }}
workers = {{ app_workers }}
# Автоматический расчет буфера памяти (10% от всей RAM сервера):
memory_limit_mb = {{ (ansible_facts['memtotal_mb'] * 0.10) | int }}

[logging]
{% if enable_debug_logs %}
log_level = DEBUG
verbose_sql_trace = true
{% else %}
log_level = ERROR
verbose_sql_trace = false
{% endif %}

[database]
db_password = {{ db_secret_password }}

{% if simulate_broken_config %}
INVALID_DIRECTIVE = CRASH_NOW
{% endif %}
EOF

    3. Напишем обработчик событий (Handler) в roles/microservice_config/handlers/main.yml: 

      cat << 'EOF' > ~/ansible-practice/roles/microservice_config/handlers/main.yml
---
- name: Reload Microservice Daemon
  ansible.builtin.debug:
    msg: "🔄 [HANDLER TRIGGERED] Конфигурация изменилась! Перезагружаем сервис на узле {{ inventory_hostname }} (Окружение: {{ env_name }})"
EOF

    4. Напишем отказоустойчивые задачи роли (block / rescue / always) в roles/microservice_config/tasks/main.yml: 

      cat << 'EOF' > ~/ansible-practice/roles/microservice_config/tasks/main.yml
---
- name: Создать структуру каталогов для окружения {{ env_name }}
  ansible.builtin.file:
    path: "{{ item }}"
    state: directory
    mode: "0750"
  loop:
    - "{{ deploy_root }}"
    - "{{ deploy_root }}/etc"
    - "{{ deploy_root }}/logs"

- name: Отказоустойчивое обновление конфигурации с проверкой и автооткатом
  block:
    - name: Сгенерировать конфигурационный файл service.conf из шаблона Jinja2
      ansible.builtin.template:
        src: service.conf.j2
        dest: "{{ deploy_root }}/etc/service.conf"
        mode: "0600"
        backup: true
      register: template_result
      notify: Reload Microservice Daemon

    - name: Проверить сгенерированный конфиг на наличие запрещенных директив (Валидация)
      ansible.builtin.command: >
        grep -v "INVALID_DIRECTIVE" {{ deploy_root }}/etc/service.conf
      changed_when: false

  rescue:
    - name: "🚨 [RESCUE] Ошибка валидации конфига! Выполняем откат из резервной копии"
      ansible.builtin.copy:
        src: "{{ template_result.backup_file }}"
        dest: "{{ deploy_root }}/etc/service.conf"
        remote_src: true
        mode: "0600"
      when: template_result.backup_file is defined

    - name: Завершить выполнение с ошибкой после успешного отката
      ansible.builtin.fail:
        msg: "Выкатка прервана: обнаружена ошибка в конфиге! Старая рабочая конфигурация успешно восстановлена блоком rescue."

  always:
    - name: Записать метку времени последнего аудита Ansible
      ansible.builtin.copy:
        content: "Last checked on {{ ansible_facts['date_time']['iso8601'] }} for env {{ env_name }}\n"
        dest: "{{ deploy_root }}/logs/audit.log"
        mode: "0644"
      changed_when: false
EOF

    Этап 4. Создание главного плейбука site.yml и запуск на разных окружениях!

    Создадим корневой плейбук site.yml, который настраивает кластер с ограничением пачки обновления serial: 1: 

    cat << 'EOF' > ~/ansible-practice/site.yml
---
- name: Настройка серверов кластера приложений
  hosts: app_cluster
  serial: 1
  gather_facts: true

  roles:
    - role: microservice_config
EOF

    Теперь протестируем работу на обоих окружениях (staging и production) с автоматической расшифровкой секретов из Ansible Vault!

    cd ~/ansible-practice

echo "=== 1. Раскатка конфигурации на STAGING ==="
ansible-playbook -i inventories/staging/hosts.yml site.yml --vault-password-file .vault_pass

echo "=== 2. Раскатка конфигурации на PRODUCTION ==="
ansible-playbook -i inventories/production/hosts.yml site.yml --vault-password-file .vault_pass
