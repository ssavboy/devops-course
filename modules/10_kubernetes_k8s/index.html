    Kubernetes и оркестрация контейнеров в продакшене

    В Модуле 4 мы научились запускать несколько контейнеров через Docker Compose. Но у Docker Compose есть фундаментальное ограничение: он работает только в пределах одного физического или виртуального сервера. Что произойдет, если этот единственный сервер выйдет из строя, у него сгорит диск или закончится оперативная память? Весь ваш проект мгновенно упадет.

    Kubernetes (K8s) решает задачу управления контейнерами в масштабе кластера из десятков и сотен серверов. Вы больше не думаете о том, на каком конкретно сервере запустить контейнер — вы просто передаете кластеру YAML-манифест: «Мне нужно 5 копий бэкенда, по 512 МБ RAM на каждую, и база данных с диском на 20 ГБ». Kubernetes сам найдет свободные серверы, запустит контейнеры, свяжет их единой сетью, а если один из серверов ночью физически отключится — автоматически за секунды переселит упавшие контейнеры на живые узлы!

    Блок 1. Архитектура Kubernetes и развёртывание кластера

    Кластер Kubernetes состоит из двух типов узлов (серверов): управляющего слоя (Control Plane) и рабочих лошадок (Worker Nodes).

    +-----------------------------------------------------------------------+
|                        CONTROL PLANE (Мозг кластера)                  |
|                                                                       |
|  [ kube-apiserver ] <---> [ etcd (База состояния кластера) ]          |
|         ^                                                             |
|         +---> [ kube-scheduler ]      [ kube-controller-manager ]     |
+---------|-------------------------------------------------------------+
          | (HTTPS REST API)
          v
+-----------------------------------------------------------------------+
|                        WORKER NODES (Рабочие узлы)                    |
|                                                                       |
|  +-------------------------------+   +-----------------------------+  |
|  | Worker Node 1                 |   | Worker Node 2               |  |
|  | [kubelet]    [kube-proxy]     |   | [kubelet]    [kube-proxy]   |  |
|  | [containerd (CRI)]            |   | [containerd (CRI)]          |  |
|  | +-----------+  +-----------+  |   | +-----------+ +-----------+ |  |
|  | |   Pod A   |  |   Pod B   |  |   | |   Pod A   | |   Pod C   | |  |
|  | +-----------+  +-----------+  |   | +-----------+ +-----------+ |  |
|  +-------------------------------+   +-----------------------------+  |
+-----------------------------------------------------------------------+

    1.1. Компоненты Control Plane (Управляющий контур)

    1. kube-apiserver (API-сервер): Главные и единственные входные ворота кластера. Все компоненты внутри кластера и администраторы (через утилиту kubectl) общаются только с API-сервером по HTTPS (REST API). Он отвечает за аутентификацию, авторизацию (RBAC) и валидацию манифестов.
    2. etcd: Распределенное, строго согласованное (алгоритм Raft) хранилище типа «ключ-значение». Здесь хранится всё состояние кластера (какие поды созданы, какие секреты загружены). Потеря etcd = потеря всего кластера, поэтому его регулярно бэкапят.
    3. kube-scheduler (Планировщик): Следит за появлением новых подов, которым еще не назначен сервер, оценивает свободные ресурсы (CPU/RAM), правила привязки (Affinity/Taints) и решает: «Этот Pod поедет на Worker Node №2».
    4. kube-controller-manager: Набор бесконечных циклов контроля (Reconciliation Loops). Он непрерывно сравнивает желаемое состояние (в etcd написано replicas: 3) с фактическим (живы только 2 пода) и дает команду создать недостающий под.

    1.2. Компоненты Worker Node (Рабочий узел)

    1. kubelet: Главный агент на каждом рабочем сервере. Он получает команды от kube-apiserver, дает поручение контейнерному рантайму запустить контейнеры, проверяет их здоровье (Probes) и отчитывается обратно.
    2. Container Runtime (containerd / CRI-O): Низкоуровневый движок, который непосредственно скачивает образы и запускает контейнеры в ядре Linux. (Сам монолитный Docker в качестве рантайма K8s больше не используется — используется его быстрая сердцевина containerd).
    3. kube-proxy: Сетевой агент на каждом узле. Управляет правилами iptables или IPVS, обеспечивая маршрутизацию виртуальных IP-адресов сервисов (Service) до конкретных подов.

    1.3. Варианты развёртывания кластера

    • Для локальной разработки и тестирования (на ноутбуке или в CI):
    • kind (Kubernetes IN Docker): Запускает полноценный многоузловой кластер K8s, где роль серверов (нод) выполняют обычные Docker-контейнеры. Стартует за 20 секунд, идеален для практики!
    • minikube: Классический локальный кластер в ВМ или контейнере.
    • k3s (от Rancher): Облегченный сертифицированный дистрибутив K8s в одном бинарнике (потребляет всего 512 МБ RAM, идеален для Edge, IoT, Raspberry Pi / Argon и небольших продакшен-серверов).
    • Для боевого продакшена:
    • Managed Kubernetes (Yandex Managed Service for Kubernetes, AWS EKS, Google GKE): Облачный провайдер сам держит и обновляет Control Plane, а вы управляете только Worker Nodes.
    • Self-Hosted (на своих серверах): Развертывание с помощью kubeadm или готового набора Ansible-ролей Kubespray.

    Блок 2. Базовые ресурсы, YAML-манифесты и диагностика с kubectl

    Любой манифест в Kubernetes обязательно содержит 4 корневых поля: * apiVersion: — версия API группы ресурса (v1, apps/v1, networking.k8s.io/v1). * kind: — тип объекта (Pod, Deployment, Service, Ingress). * metadata: — имя (name), пространство имен (namespace) и метки (labels). * spec: — желаемая спецификация (характеристики) объекта.

    2.1. Иерархия рабочих нагрузок: Namespace, Pod, ReplicaSet, Deployment

    1. Namespace (Пространство имен): Виртуальный «отдел» внутри кластера для логической изоляции сред или команд (kube-system — системные поды K8s, monitoring, staging, production).
    2. Pod (Под): Минимальная неделимая единица в Kubernetes. K8s управляет не отдельными контейнерами, а Подами!
    3. Внутри одного Пода находится один (в 95% случаев) или несколько тесно связанных контейнеров (например, основной контейнер приложения + вспомогательный Sidecar-контейнер сборщика логов или прокси).
    4. Все контейнеры внутри одного Пода делят один общий IP-адрес (localhost) и общие тома (Volumes).
    5. Важно: Поды смертны (эфемерны). При перезапуске или переезде на другую ноду Под всегда получает новый IP-адрес. Поэтому в продакшене никто не создает голые Поды напрямую — ими управляют через Deployment!
    6. Deployment (Развертывание): Управляет ReplicaSet, который поддерживает нужное число копий Подов (replicas: 3) и отвечает за их плавное обновление (RollingUpdate) и откат (kubectl rollout undo).

    2.2. Профессиональная диагностика с помощью kubectl

    Когда приложение в Kubernetes не работает, инженер идет по четкому алгоритму диагностики из 5 команд:

    Ситуация / Статус Пода Что означает ошибка Команда диагностики
    Pending Под застрял в очереди планировщика: в кластере не хватает свободных CPU/RAM или не может примонтироваться диск (PVC). kubectl describe pod <имя_пода> (смотреть в самый низ в секцию Events!)
    ImagePullBackOff / ErrImagePull K8s не может скачать Docker-образ: опечатка в имени/теге образа или нет секрета авторизации (imagePullSecrets) к приватному реестру. kubectl describe pod <имя_пода>
    CrashLoopBackOff Контейнер скачался, запустился, но приложение внутри тут же упало с ненулевым кодом ошибки (например, нет связи с БД или синтаксическая ошибка). kubectl logs <имя_пода> и посмотреть логи предыдущего упавшего экземпляра: kubectl logs <имя_пода> --previous
    OOMKilled (Exit Code 137) Процесс внутри контейнера превысил жесткий лимит памяти (limits.memory), и ядро Linux убило его через SIGKILL. Увеличить resources.limits.memory в манифесте или искать утечку памяти в коде.
    Завис внутри, но не падает Нужно зайти внутрь контейнера или проверить сеть. kubectl exec -it <имя_пода> -- /bin/sh

    Блок 3. Бесперебойные обновления, Probes и Stateful-сервисы

    3.1. Три типа проверок здоровья (Probes) для Zero-Downtime

    Чтобы при выкатке новой версии (RollingUpdate) пользователи не получали ошибок 502 Bad Gateway, Kubernetes должен точно знать состояние каждого контейнера с помощью трех проб:

    1. startupProbe (Проба запуска): Проверяет, закончилась ли долгая первичная инициализация тяжелого приложения. Пока она не пройдет, остальные пробы не начинают работу.
    2. readinessProbe (Проба готовности принимать трафик) — ГЛАВНАЯ ДЛЯ ZERO-DOWNTIME:
    3. Если readinessProbe возвращает ошибку, Kubernetes НЕ убивает под, но временно убирает его IP-адрес из балансировщика (Service)!
    4. При обновлении новый под сначала обязан пройти readinessProbe, только после этого на него пойдет трафик и только тогда старый под начнет гаситься.
    5. livenessProbe (Проба живучести): Проверяет, не зависло ли приложение в мертвом цикле (Deadlock). Если проба падает — kubelet убивает и перезапускает контейнер.

    Важное правило: При выключении пода Kubernetes параллельно посылает ему SIGTERM и удаляет его IP из балансировщика. Чтобы за эти 1–2 секунды синхронизации сетевых правил на выключающийся под не прилетел новый запрос, добавляют хук lifecycle.preStop: exec: command: ["sleep", "5"].

    3.2. Ресурсы (requests и limits) и автоскейлинг (HPA)

    В каждом контейнере обязательно задаются два параметра ресурсов: * requests (Гарантированный минимум): Сколько CPU и RAM нужно контейнеру для старта. Именно по цифре requests планировщик kube-scheduler ищет свободную ноду! * limits (Жесткий потолок): Больше этого значения контейнер потребить не может. При превышении CPU процесс начнет притормаживаться (CPU Throttling), а при превышении Memory — будет убит (OOMKilled).

    Horizontal Pod Autoscaler (HPA):

    Когда нагрузка на CPU или память превышает заданный процент (например, 70% от requests.cpu), контроллер HPA автоматически увеличивает количество реплик в Deployment (например, с 2 до 10 подов), а ночью при спаде трафика — уменьшает обратно до 2!

    3.3. Stateful-сервисы: StatefulSet, PV, PVC и StorageClass

    Обычный Deployment идеален для Stateless-бэкендов, где все поды одинаковы как близнецы и имеют случайные имена (backend-7b9f8-x9z2k). Но для баз данных (PostgreSQL, Redis, Kafka, Elasticsearch) нужен StatefulSet:

    • Предсказуемые постоянные имена: Поды получают строгие порядковые номера: postgres-0, postgres-1, postgres-2, которые не меняются при перезапуске!
    • Строгий порядок запуска и остановки: postgres-1 не запустится, пока postgres-0 (мастер) полностью не перейдет в статус Ready.
    • Персональное хранилище данных (VolumeClaimTemplates): За каждым подом StatefulSet навсегда закрепляется его собственный изолированный сетевой диск.

    Как работает дисковая подсистема в K8s: 1. StorageClass: Описывает «тип» облачного диска (например, быстрый ssd или дешевый hdd) и провиженер (CSI-драйвер), который умеет автоматически нарезать диски в облаке. 2. PersistentVolumeClaim (PVC): Заявка от разработчика: «Выделите моему поду 10 ГБ диска класса standard». 3. PersistentVolume (PV): Сам реальный кусок хранилища, автоматически созданный и привязанный к заявке PVC.

    Блок 4. Конфигурации, Секреты, Сеть и Безопасность (NetworkPolicy)

    4.1. Управление конфигурациями (ConfigMap) и секретами (Secret)

    Чтобы не зашивать конфиги и пароли внутрь Docker-образа: * ConfigMap: Хранит несекретные настройки (переменные окружения LOG_LEVEL=info или целые конфигурационные файлы nginx.conf, которые можно примонтировать в папку контейнера как том). * Secret: Хранит пароли, TLS-сертификаты и токены (в манифесте значения кодируются в base64, или создаются на лету через kubectl create secret generic).

    Внимание по DevSecOps: Обычный base64 — это кодировка, а не шифрование (echo "cGFzcw==" | base64 -d мгновенно вернет текст). Поэтому в боевом кластере включают шифрование etcd на диске (EncryptionConfiguration), а в Git хранят секреты через SealedSecrets или подтягивают их из HashiCorp Vault / External Secrets Operator.

    4.2. Сетевое взаимодействие: Service, Ingress и NetworkPolicy

    Поскольку IP-адреса Подов постоянно меняются, обращаться к Поду напрямую по IP нельзя. Для этого существует абстракция Service, которая дает группе Подов (по их меткам selector: app: backend) постоянный виртуальный IP и постоянное DNS-имя (например, http://backend-svc.prod.svc.cluster.local:8000).

    Четыре типа Service:

    1. ClusterIP (По умолчанию): Внутренний IP, доступный только внутри кластера. Идеально для связи между микросервисами и БД (Nginx $\rightarrow$ Backend $\rightarrow$ Postgres).
    2. NodePort: Открывает статический порт (в диапазоне 30000–32767) на IP-адресе каждого сервера кластера.
    3. LoadBalancer: Дает команду облачному провайдеру (Yandex Cloud / AWS) создать внешний облачный балансировщик с белым IP.
    4. Headless Service (clusterIP: None): Не балансирует сам, а возвращает DNS-записи каждого конкретного пода напрямую (обязателен для StatefulSet баз данных: postgres-0.db-svc...).

    Внешний доступ через Ingress:

    Создавать платный облачный LoadBalancer на каждый из 20 микросервисов — разорительно. Вместо этого в кластер ставится один Ingress Controller (обычно на базе Nginx, Traefik или Cilium), который получает один белый IP, терминирует HTTPS/TLS-сертификаты и по правилам объекта Ingress маршрутизирует трафик по доменам и путям (api.example.com/v1 $\rightarrow$ backend-svc:8000).

    Сетевые политики безопасности (NetworkPolicy — Брандмауэр внутри кластера):

    По умолчанию в Kubernetes действует правило «Все поды во всех неймспейсах могут общаться со всеми подами». Если злоумышленник взломает уязвимый фронтенд-под, он сможет напрямую подключиться к поду базы данных! Объект NetworkPolicy работает как L3/L4 фаервол для подов: мы запрещаем весь входящий трафик по умолчанию (Default Deny) и разрешаем доступ к поду postgres строго от подов с меткой app: backend и только по порту 5432!

    Блок 5. Пакетное управление приложениями с помощью Helm

    Для деплоя одного микросервиса нужно написать 5–6 разных YAML-манифестов (Deployment, Service, ConfigMap, Secret, Ingress, HPA, NetworkPolicy). А если нужно выкатить этот же сервис на dev, staging и production, где отличаются только домен, число реплик и лимиты памяти? Копировать 6 файлов в 3 папки — это путь к хаосу.

    Helm — это пакетный менеджер и шаблонизатор для Kubernetes (как apt для Ubuntu). Он упаковывает все манифесты приложения в единый версионированный пакет — Helm Chart:

    my-service-chart/
├── Chart.yaml            # Паспорт чарта: имя, версия чарта (version) и версия приложения (appVersion)
├── values.yaml           # Значения по умолчанию для шаблонов
├── values-staging.yaml   # Переопределения для Staging (replicas: 1, debug: true)
├── values-prod.yaml      # Переопределения для Production (replicas: 3, limits: 512Mi)
└── templates/            # Шаблоны манифестов на языке Go-templates
    ├── deployment.yaml   # Подставляет {{ .Values.replicaCount }} и {{ .Values.image.tag }}
    ├── service.yaml
    ├── ingress.yaml
    └── hpa.yaml

    Главные команды Helm для работы с релизами: 

    # Проверить синтаксис чарта и срендерить итоговый YAML в консоль (без отправки в кластер!)
helm lint ./my-chart
helm template my-release ./my-chart -f values-prod.yaml

# Установить или обновить релиз (флаг --atomic автоматически откатит релиз, если поды не пройдут readinessProbe!)
helm upgrade --install my-release ./my-chart -n production --create-namespace -f values-prod.yaml --atomic

# Посмотреть историю ревизий релиза и откатиться на любую предыдущую версию за 1 секунду!
helm history my-release -n production
helm rollback my-release 1 -n production

    🛠 Практический проект Модуля 10: Деплой отказоустойчивого многокомпонентного приложения в Kubernetes через Helm

    Мы развернем настоящий локальный кластер Kubernetes (kind), упакуем наш микросервис и базу данных в полноценный Helm-чарт, включающий: * StatefulSet + Headless Service + PVC для персистентного хранения базы данных Redis/Postgres. * Deployment бэкенда с настроенными readinessProbe / livenessProbe, preStop хуком и не-root контекстом безопасности (securityContext). * ConfigMap и Secret для разделения настроек и паролей. * NetworkPolicy для жесткой сетевой защиты слоя данных. * HorizontalPodAutoscaler (HPA) для автоматического масштабирования. * Ingress для внешнего доступа.

    Этап 2. Сборка образа микросервиса и загрузка в кластер

    Соберем наш легкий образ бэкенда hit-counter:2.0.0 (из Модуля 2) и загрузим его напрямую внутрь узлов кластера kind командой kind load:

    mkdir -p ~/k8s-practice/app && cd ~/k8s-practice/app

cat << 'EOF' > app.py
import os
import socket
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

APP_VERSION = os.getenv("APP_VERSION", "2.0.0")
ENV_NAME = os.getenv("ENV_NAME", "production")
SECRET_TOKEN = os.getenv("API_SECRET_KEY", "not-set")

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health":
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(json.dumps({"status": "healthy", "pod": socket.gethostname()}).encode())
        elif self.path == "/api/info":
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            resp = {
                "pod_name": socket.gethostname(),
                "version": APP_VERSION,
                "environment": ENV_NAME,
                "secret_loaded": len(SECRET_TOKEN) > 5
            }
            self.wfile.write(json.dumps(resp).encode())
        else:
            self.send_response(404)
            self.end_headers()

if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
EOF

cat << 'EOF' > Dockerfile
FROM python:3.12-slim
WORKDIR /app
RUN groupadd -r appgroup && useradd -r -g appgroup -u 10001 appuser
COPY --chown=appuser:appgroup app.py .
USER 10001:10001
EXPOSE 8000
ENTRYPOINT ["python3", "app.py"]
EOF

# Собираем версии 2.0.0 и 2.1.0 и загружаем их в ноды кластера Kubernetes
docker build -t hit-counter:2.0.0 .
docker tag hit-counter:2.0.0 hit-counter:2.1.0
kind load docker-image hit-counter:2.0.0 --name devops-k8s
kind load docker-image hit-counter:2.1.0 --name devops-k8s

    Теперь создадим шаблоны манифестов в папке templates/:

    1. ConfigMap, Secret и StatefulSet (с PersistentVolumeClaim) для Stateful-слоя (templates/stateful-and-config.yaml):

    cat << 'EOF' > ~/k8s-practice/charts/webapp/templates/stateful-and-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  ENV_NAME: {{ .Values.envName | quote }}
---
apiVersion: v1
kind: Secret
metadata:
  name: {{ .Release.Name }}-secret
type: Opaque
stringData:
  API_SECRET_KEY: {{ .Values.secret.apiSecretKey | quote }}
---
# Headless Service для StatefulSet
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-redis
spec:
  clusterIP: None
  selector:
    app: {{ .Release.Name }}-redis
  ports:
    - port: 6379
      name: redis
---
# StatefulSet с автоматическим заказом постоянного диска (volumeClaimTemplates)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: {{ .Release.Name }}-redis
spec:
  serviceName: "{{ .Release.Name }}-redis"
  replicas: 1
  selector:
    matchLabels:
      app: {{ .Release.Name }}-redis
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - containerPort: 6379
          volumeMounts:
            - name: redis-data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: [ "ReadWriteOnce" ]
        resources:
          requests:
            storage: {{ .Values.redisStorageSize }}
EOF

    2. Deployment, Service, HPA, Ingress и NetworkPolicy (templates/backend-stack.yaml):

    cat << 'EOF' > ~/k8s-practice/charts/webapp/templates/backend-stack.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-backend
  labels:
    app: {{ .Release.Name }}-backend
spec:
  replicas: {{ .Values.replicaCount }}
  # Стратегия бесперебойного обновления (Zero-Downtime RollingUpdate)
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: {{ .Release.Name }}-backend
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-backend
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
      containers:
        - name: backend
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: 8000
          env:
            - name: APP_VERSION
              value: {{ .Values.image.tag | quote }}
          envFrom:
            - configMapRef:
                name: {{ .Release.Name }}-config
            - secretRef:
                name: {{ .Release.Name }}-secret
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
          # Readiness Probe гарантирует, что трафик пойдет только на готовый под!
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 2
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 10
          # Плавный вывод пода из балансировки перед остановкой
          lifecycle:
            preStop:
              exec:
                command: ["sleep", "2"]
---
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-backend-svc
spec:
  type: ClusterIP
  selector:
    app: {{ .Release.Name }}-backend
  ports:
    - port: {{ .Values.service.port }}
      targetPort: 8000
---
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ .Release.Name }}-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ .Release.Name }}-backend
  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}
{{- end }}
---
# Сетевая политика безопасности: разрешаем доступ к Redis ТОЛЬКО от подов бэкенда!
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: {{ .Release.Name }}-redis-netpol
spec:
  podSelector:
    matchLabels:
      app: {{ .Release.Name }}-redis
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: {{ .Release.Name }}-backend
      ports:
        - protocol: TCP
          port: 6379
---
# Ingress для внешней маршрутизации HTTP-трафика
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Release.Name }}-ingress
spec:
  rules:
    - host: "app.local"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: {{ .Release.Name }}-backend-svc
                port:
                  number: {{ .Values.service.port }}
EOF
