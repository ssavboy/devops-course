    Kubernetes и оркестрация контейнеров в продакшене

    В четвертом модуле мы научились объединять несколько контейнеров в единую систему с помощью Docker Compose. Однако у Docker Compose есть фундаментальный архитектурный предел: он управляет контейнерами строго в рамках одной физической или виртуальной машины. Что произойдет с вашим бизнесом, если на этом единственном сервере выйдет из строя блок питания, деградирует SSD-диск или закончится оперативная память? Весь проект мгновенно остановится.

    Kubernetes (K8s) выводит оркестрацию на уровень распределенного кластера из десятков и сотен серверов. С переходом на Kubernetes инженер перестает мыслить отдельными виртуальными машинами и вручную распределять контейнеры по хостам. Вместо этого вы передаете в API кластера декларативный YAML-манифест: «Мне нужно 5 копий бэкенда с гарантией по 512 МБ RAM на каждую и реляционная база данных с постоянным диском на 20 ГБ». Kubernetes самостоятельно анализирует загруженность серверов, размещает контейнеры, связывает их виртуальной сетью, а если один из физических серверов в три часа ночи внезапно отключится — автоматически за считанные секунды перезапустит упавшие контейнеры на оставшихся в живых узлах кластера!

    Блок 1. Архитектура Kubernetes и развёртывание кластера

    Любой промышленный кластер Kubernetes разделен на два функциональных эшелона серверов: управляющий контур (Control Plane — «мозг» кластера, принимающий решения) и рабочие узлы (Worker Nodes — «мышцы» кластера, на которых непосредственно крутятся пользовательские приложения).

    +-----------------------------------------------------------------------+
|                        CONTROL PLANE (Мозг кластера)                  |
|                                                                       |
|  [ kube-apiserver ] <---> [ etcd (База состояния кластера) ]          |
|         ^                                                             |
|         +---> [ kube-scheduler ]      [ kube-controller-manager ]     |
+---------|-------------------------------------------------------------+
          | (HTTPS REST API)
          v
+-----------------------------------------------------------------------+
|                        WORKER NODES (Рабочие узлы)                    |
|                                                                       |
|  +-------------------------------+   +-----------------------------+  |
|  | Worker Node 1                 |   | Worker Node 2               |  |
|  | [kubelet]    [kube-proxy]     |   | [kubelet]    [kube-proxy]   |  |
|  | [containerd (CRI)]            |   | [containerd (CRI)]          |  |
|  | +-----------+  +-----------+  |   | +-----------+ +-----------+ |  |
|  | |   Pod A   |  |   Pod B   |  |   | |   Pod A   | |   Pod C   | |  |
|  | +-----------+  +-----------+  |   | +-----------+ +-----------+ |  |
|  +-------------------------------+   +-----------------------------+  |
+-----------------------------------------------------------------------+

    1.1. Компоненты Control Plane (Управляющий контур)

    На мастер-узлах управления работают четыре ключевые системные службы:

    1. kube-apiserver (API-сервер): Центральный шлюз и единственная точка входа в кластер. Ни один внутренний компонент и ни один инженер (работающий через консольную утилиту kubectl) никогда не обращаются к базе данных или узлам напрямую — абсолютно все взаимодействия идут исключительно через kube-apiserver по защищенному протоколу HTTPS (REST API). Именно этот сервис проверяет права доступа (аутентификацию и ролевую модель RBAC) и валидирует синтаксис ваших YAML-манифестов перед сохранением.
    2. etcd: Распределенное, строго согласованное (работающее на базе алгоритма консенсуса Raft) хранилище типа «ключ-значение». Внутри etcd записана вся правда о текущем и желаемом состоянии кластера: какие сервисы развернуты, какие конфигурации и секреты загружены, на каких узлах запущены поды. Именно поэтому в продакшене потеря базы etcd без регулярного бэкапа равносильна полной потере всего кластера Kubernetes.
    3. kube-scheduler (Планировщик): Отвечает за расселение контейнеров по серверам. Как только в базе появляется запись о новом Поде, которому еще не назначен конкретный узел (nodeName пуст), планировщик за миллисекунды оценивает остатки свободных ресурсов CPU и RAM на всех рабочих нодах, проверяет правила притяжения и отталкивания (Affinity / Taints) и выносит вердикт: «Этот Pod отправится работать на сервер Worker Node №2».
    4. kube-controller-manager (Менеджер контроллеров): Служба, внутри которой в бесконечном цикле крутятся десятки контроллеров согласования состояния (Reconciliation Loops). Их задача — непрерывно сверять желаемое состояние (например, в etcd записано replicas: 3) с фактическим состоянием в кластере (в живых осталось только 2 пода) и немедленно отдавать команду API-серверу на создание недостающего экземпляра.

    1.2. Компоненты Worker Node (Рабочий узел)

    На каждом линейном сервере кластера, где запускаются ваши контейнеры, обязательно работают три инфраструктурных агента:

    1. kubelet: Главный представитель Kubernetes на рабочем сервере (обычный системный демон systemd). Он поддерживает постоянную связь с kube-apiserver, получает от него список Подов, назначенных на данную ноду, приказывает контейнерному движку скачать образы и запустить их, регулярно опрашивает контейнеры проверками здоровья (Probes) и отправляет отчеты о состоянии узла обратно в центр.
    2. Container Runtime (containerd или CRI-O): Низкоуровневый движок, совместимый со стандартом CRI (Container Runtime Interface), который по команде от kubelet непосредственно настраивает namespaces и cgroups в ядре Linux и запускает процессы контейнеров. (Важная деталь: сам тяжеловесный демон Docker в качестве рантайма внутри Kubernetes давно не используется — вместо него работает его быстрая и легкая сердцевина containerd).
    3. kube-proxy: Сетевой демон, живущий на каждом узле кластера. Он непрерывно синхронизирует правила сетевой фильтрации в ядре Linux (iptables или высокопроизводительные таблицы балансировки IPVS), обеспечивая прозрачную пересылку трафика от виртуальных IP-адресов сервисов (Service) к реальным IP-адресам живых подов на любых серверах кластера.

    1.3. Инструменты развёртывания кластера: от ноутбука до облака

    В зависимости от стоящей перед инженером задачи, Kubernetes разворачивается разными инструментами:

    • Для локальной разработки, обучения и прогона автотестов в CI/CD:
    • kind (Kubernetes IN Docker): Элегантный инструмент от самих разработчиков Kubernetes, который поднимает полноценный кластер за 20 секунд, используя в качестве «серверов» (нод) обычные локальные Docker-контейнеры. Не требует тяжелых виртуальных машин и идеально подходит для отработки боевых сценариев.
    • minikube: Классический инструмент запуска одноузлового локального кластера внутри виртуальной машины или контейнера.
    • k3s (от компании Rancher / CNCF): Облегченный, полностью сертифицированный дистрибутив Kubernetes, упакованный в один бинарный файл весом менее 100 МБ. Потребляет всего около 512 МБ оперативной памяти, благодаря чему стал стандартом для Edge-вычислений, IoT, домашних лабораторий (Raspberry Pi) и небольших продакшен-проектов.
    • Для промышленного продакшена (Production):
    • Managed Kubernetes (Yandex Managed Service for Kubernetes, AWS EKS, Google GKE): Самый популярный подход в бизнесе — облачный провайдер берет на себя всю головную боль по поддержке, резервному копированию и обновлению управляющего слоя Control Plane, а инженеры компании управляют только пулами рабочих узлов (Worker Nodes).
    • Self-Hosted (На собственном «железе» / Bare-Metal): Когда компания строит кластер в собственном дата-центре, его разворачивают с помощью штатного бутстраппера kubeadm или промышленного набора готовых Ansible-ролей Kubespray.

    Блок 2. Базовые ресурсы, YAML-манифесты и диагностика с kubectl

    Вся работа с Kubernetes строится на отправке декларативных YAML-манифестов в API-сервер. Абсолютно любой манифест в мире K8s обязан содержать четыре корневых поля верхнего уровня: * apiVersion: — версия схемы API, к которой принадлежит данный объект (например, v1 для базовых сущностей, apps/v1 для контроллеров приложений или networking.k8s.io/v1 для сетевых правил). * kind: — тип создаваемого ресурса (Pod, Deployment, Service, StatefulSet, Ingress). * metadata: — паспорт объекта: его уникальное имя (name), принадлежность к пространству имен (namespace) и произвольные текстовые метки (labels), по которым объекты находят друг друга. * spec: — желаемая техническая спецификация объекта (какой образ запустить, сколько реплик поддерживать, какие порты открыть).

    2.1. Иерархия рабочих нагрузок: Namespace → Deployment → ReplicaSet → Pod

    Новички часто удивляются, почему в Kubernetes нельзя просто сказать «запусти контейнер». Вместо этого выстроена гибкая матрешка абстракций:

    1. Namespace (Пространство имен): Виртуальный изолированный сегмент внутри единого физического кластера. Позволяет разделить на одном оборудовании системные службы самого кластера (kube-system), стек мониторинга (monitoring), тестовый стенд (staging) и боевой контур (production), выставив на каждый неймспейс свои квоты ресурсов и права доступа.
    2. Pod (Под — «капсула»): Минимальная неделимая единица развертывания в Kubernetes. Важно запомнить: Kubernetes оперирует не отдельными контейнерами, а Подами!
    3. В 95% случаев внутри одного Пода живет ровно один контейнер вашего приложения. Однако при необходимости в ту же капсулу Пода можно подселить вспомогательный контейнер (Sidecar — например, агент чтения логов, сетевой прокси Envoy или экспортер метрик).
    4. Все контейнеры внутри одного Пода разделяют одно сетевое пространство имен: у них один общий IP-адрес, они общаются друг с другом через localhost и могут монтировать общие дисковые папки (Volumes).
    5. Эфемерность Подов: Поды в Kubernetes считаются «смертными» расходными единицами. Если Под упал или переехал на другой сервер, старый Под уничтожается и создается совершенно новый — с новым случайным IP-адресом! Именно поэтому в продакшене никто никогда не создает одиночные «голые» Поды напрямую — их жизнью всегда управляет контроллер верхнего уровня Deployment.
    6. Deployment (Развертывание) и ReplicaSet: Вы создаете объект Deployment, указывая в нем шаблон Пода и желаемое число копий (replicas: 3). Под капотом Deployment автоматически порождает контроллер ReplicaSet (который следит, чтобы в любую секунду в кластере было ровно 3 живых Пода), а сам Deployment управляет бесшовной сменой версий (RollingUpdate), хранит историю ревизий и позволяет откатить релиз одной командой (kubectl rollout undo).

    2.2. Профессиональный алгоритм диагностики сбоев с помощью kubectl

    Когда вы выкатили манифест, но приложение не отвечает, опытный DevOps-инженер никогда не гадает на кофейной гуще. Любая неисправность в Kubernetes локализуется за 30 секунд по статусу Пода в выводе kubectl get pods и пяти диагностическим командам:

    Статус Пода / Симптом Что реально происходит под капотом кластера Точная команда диагностики для инженера
    Pending Под создан в базе etcd, но застрял в очереди планировщика kube-scheduler: ни на одном сервере кластера не хватает свободной памяти/CPU под запрошенные requests, либо не может примонтироваться сетевой диск (PVC). kubectl describe pod <имя_пода> — прокрутить вывод в самый низ до таблицы Events (там открытым текстом написана причина, например 0/3 nodes are available: Insufficient memory)!
    ImagePullBackOff / ErrImagePull Агент kubelet на ноде пытается скачать Docker-образ, но получает отказ от Registry: вы допустили опечатку в имени/теге образа, такого тега не существует, либо для приватного реестра не подключен секрет авторизации (imagePullSecrets). kubectl describe pod <имя_пода> — в секции Events будет точный ответ реестра (manifest unknown или 401 Unauthorized).
    CrashLoopBackOff Образ успешно скачался и контейнер стартовал, но главный процесс (PID 1) внутри него тут же завершился с ошибкой (например, синтаксическая ошибка в Python или нет связи с БД), после чего K8s в цикле пытается перезапустить его с растущей паузой. Читаем логи приложения: kubectl logs <имя_пода>, а если контейнер уже успел перезапуститься — смотрим предсмертный лог предыдущего упавшего экземпляра: kubectl logs <имя_пода> --previous!
    OOMKilled (Exit Code 137) Процесс внутри контейнера попытался потребить больше оперативной памяти, чем разрешено в его жестком потолке resources.limits.memory, и OOM Killer ядра Linux мгновенно уничтожил его сигналом SIGKILL ($128 + 9 = 137$). Проверить секцию Last State в kubectl describe pod <имя_пода>; увеличить лимит memory в манифесте или профилировать утечку памяти в коде.
    Статус Running, но сервис завис Контейнер жив, но нужно проверить сетевую связность или файлы изнутри самой капсулы Пода. Открыть интерактивный терминал внутри работающего контейнера: kubectl exec -it <имя_пода> -- /bin/sh.

    Блок 3. Бесперебойные обновления, Probes и Stateful-сервисы

    3.1. Три типа проверок здоровья (Probes) — фундамент Zero-Downtime

    По умолчанию Kubernetes считает контейнер «готовым» в ту же миллисекунду, как только в ядре Linux стартовал процесс контейнера. Но, как мы помним, веб-приложению на Python, Go или Java требуется еще несколько секунд на загрузку библиотек и подключение к базе данных. Если пустить пользовательский трафик на такой контейнер мгновенно — клиенты получат каскад ошибок 502 Bad Gateway!

    Чтобы сделать обновление абсолютно незаметным для пользователей, в манифест контейнера встраиваются три независимых сенсора здоровья (Probes), которые регулярно выполняет агент kubelet:

    1. startupProbe (Проба первичного запуска): Предназначена для тяжелых или легаси-приложений, которые могут долго прогревать кэши при старте. Пока startupProbe не вернет успех один раз, две остальные пробы поставлены на паузу и не мешают приложению загружаться.
    2. readinessProbe (Проба готовности принимать трафик) — ГЛАВНЫЙ МЕХАНИЗМ ZERO-DOWNTIME: Проверяет, готов ли контейнер прямо сейчас обслуживать реальные запросы (например, стучится по HTTP на /health, где проверяется коннект к БД).
    3. Критическая особенность: если readinessProbe возвращает ошибку, Kubernetes НЕ убивает и не перезапускает под — он просто временно вычеркивает IP-адрес этого пода из балансировщика нагрузки (Service), прекращая подачу на него клиентского трафика до тех пор, пока под снова не отрапортует о готовности!
    4. Именно на readinessProbe держится плавное обновление RollingUpdate: Kubernetes поднимает рядом новый под v2.0, ждет, пока его readinessProbe загорится зеленым, включает его в балансировку и лишь после этого начинает гасить старый под v1.0.
    5. livenessProbe (Проба живучести): Проверяет, не завис ли процесс приложения намертво во взаимной блокировке (Deadlock). Если livenessProbe проваливается несколько раз подряд — kubelet принимает радикальное решение: принудительно убивает зависший контейнер и запускает его заново с чистого листа.

    Тонкость идеального Graceful Shutdown (хук preStop): Когда Kubernetes решает остановить старый Под, он выполняет два действия одновременно (асинхронно): kubelet посылает процессу в контейнере сигнал остановки SIGTERM, а сетевой демон kube-proxy начинает удалять IP-адрес этого Пода из таблиц маршрутизации iptables на всех узлах кластера. Поскольку обновление таблиц на десятках серверов занимает 1–2 секунды, может возникнуть гонка: ваше приложение уже закрылось по SIGTERM, а балансировщик по старой памяти еще секунду шлет на него пакеты! Чтобы исключить эту потерю пакетов на 100%, в промышленных манифестах добавляют короткую задержку перед выключением — хук lifecycle.preStop: exec: command: ["sleep", "5"], дающий сети кластера время спокойно отвести весь трафик от уходящего пода до остановки процесса.

    3.2. Управление ресурсами (requests и limits) и автоскейлинг (HPA)

    Запускать контейнеры в боевом кластере без указания квот ресурсов категорически запрещено — один «прожорливый» сервис сожрет всю память рабочего узла и положит соседние поды. Для каждого контейнера задаются две границы по процессору (измеряется в тысячных долях ядра — милликорах m, где 1000m = 1 полное ядро CPU) и оперативной памяти (в мебибайтах Mi / гибибайтах Gi):

    • requests (Гарантированный минимум): Объем CPU и RAM, который приложение гарантированно получает со старта. Важно: планировщик kube-scheduler принимает решение о размещении Пода на сервере, опираясь исключительно на сумму цифр requests (он бронирует этот объем на ноде за вашим подом)!
    • limits (Жесткий потолок потребления): Максимальная планка, выше которой ядро Linux (cgroups) не позволит подняться контейнеру. При этом физика ограничения CPU и памяти принципиально различается:
    • CPU — ресурс сжимаемый: если процесс упрется в limits.cpu, он не упадет — ядро просто начнет искусственно притормаживать его выполнение, пропуская такты процессора (CPU Throttling).
    • Память RAM — ресурс несжимаемый: отобрать уже выделенную страницу памяти у процесса нельзя, поэтому в ту же секунду, когда контейнер превысит планку limits.memory, ядро уничтожит его со статусом OOMKilled.

    Горизонтальное автомасштабирование (HorizontalPodAutoscaler — HPA)

    Когда вы задали requests.cpu, в кластере открывается возможность автоматического эластичного масштабирования. Вы создаете ресурс HorizontalPodAutoscaler, указывая целевой порог (например, средняя загрузка CPU 70% при диапазоне от 2 до 10 реплик). Как только в час пик нагрузка на поды превышает 70%, контроллер HPA автоматически увеличивает количество реплик в Deployment, поднимая новые копии сервиса, а ночью, когда трафик падает, сам гасит лишние поды обратно до минимума!

    3.3. Stateful-приложения в Kubernetes: StatefulSet, PV, PVC и StorageClass

    Контроллер Deployment идеален для Stateless-приложений: все поды в нем обезличены, получают случайные хэши в именах (backend-7b9f8-x9z2k), запускаются и удаляются в произвольном порядке.

    Но что, если нам нужно развернуть внутри Kubernetes базу данных с состоянием (PostgreSQL, Redis, Kafka, RabbitMQ, Elasticsearch)? Для них обезличенный подход смертелен, поэтому в Kubernetes используется специализированный контроллер StatefulSet, дающий три железобетонные гарантии:

    1. Предсказуемые, неизменные имена и сетевые паспорта: Поды внутри StatefulSet никогда не получают случайных хэшей — они именуются строго по порядковым индексам: postgres-0, postgres-1, postgres-2. Даже если под postgres-0 умрет и пересоздастся на другом сервере, он вернется в строй под тем же самым именем postgres-0!
    2. Строгая последовательность старта и обновления: Реплика postgres-1 физически не начнет создаваться до тех пор, пока главный мастер-под postgres-0 полностью не запустится и не пройдет проверку readinessProbe.
    3. Персональное постоянное хранилище за каждой репликой (volumeClaimTemplates): У каждого пода в StatefulSet есть свой собственный изолированный сетевой диск, который следует за ним при переезде с сервера на сервер.

    Архитектура дисковой подсистемы Kubernetes (StorageClass → PVC → PV)

    Чтобы контейнеры не зависели от локальных дисков конкретной ноды, работа с хранилищем разделена на три слоя абстракции: * StorageClass (Класс хранилища): Настраивается администратором кластера и описывает профиль облачного хранилища (например, fast-nvme, network-ssd или cold-hdd) и драйвер CSI (Container Storage Interface), который умеет автоматически по API нарезать блочные диски в облаке Yandex Cloud или AWS. * PersistentVolumeClaim (PVC — Заявка на том): Декларативный ордер-запрос от разработчика или StatefulSet: «Прошу выделить моему поду 10 гигабайт постоянного диска из класса network-ssd в режиме чтения-записи (ReadWriteOnce)». * PersistentVolume (PV — Физический том): Сам реальный выделенный сетевой диск в инфраструктуре, который автоматически создается провиженером при появлении заявки PVC и намертво связывается с ней (статус Bound). Когда Под удаляется, его PVC и PV со всеми таблицами базы данных остаются в полной сохранности и тут же подключаются обратно к новому Поду!

    Блок 4. Конфигурации, Секреты, Сетевая маршрутизация и NetworkPolicy

    4.1. Внешняя конфигурация (ConfigMap) и управление секретами (Secret)

    Следуя канонам 12-Factor App, мы никогда не зашиваем настройки окружения и пароли внутрь Docker-образа — для их инжекции в поды Kubernetes предоставляет две нативные сущности:

    • ConfigMap: Объект для хранения несекретных параметров конфигурации. В него можно положить как отдельные пары «ключ-значение» (чтобы пробросить их в контейнер как переменные окружения ENV), так и целиком многострочные файлы конфигураций (nginx.conf, prometheus.yml), которые Kubernetes примонтирует внутрь контейнера как обычные файлы на диске!
    • Secret: Специализированный объект для передачи паролей БД, приватных ключей и TLS-сертификатов. Внутри YAML-манифеста поля секрета хранятся в кодировке base64 (либо удобно записываются обычным текстом через секцию stringData:, которую API-сервер сам переведет в base64 при сохранении).

    Критическое правило DevSecOps по работе с Secret в Kubernetes: Никогда не путайте кодировку base64 с криптографическим шифрованием! Любой человек, увидевший строку cGFzcw== в вашем Git-репозитории, раскодирует её за долю секунды стандартной командой echo "cGFzcw==" | base64 -d. Поэтому хранить сырые манифесты kind: Secret в открытом Git запрещено. В боевом продакшене применяются два стандарта защиты: на уровне самого кластера включают аппаратное шифрование базы etcd на диске (EncryptionConfiguration), а для доставки секретов из Git используют контроллер Bitnami SealedSecrets (асимметричное шифрование) или оператор External Secrets Operator (ESO), который на лету вытягивает пароли в поды напрямую из защищенного хранилища HashiCorp Vault или облачного KMS!

    4.2. Сетевая архитектура: Service, Ingress и микросегментация NetworkPolicy

    Поскольку Поды постоянно пересоздаются и меняют свои внутренние IP-адреса при каждом обновлении, обращаться к Поду напрямую по его IP-адресу бессмысленно. Чтобы дать микросервису постоянную точку входа, перед группой Подов ставится абстракция Service (Сервис).

    Объект Service находит нужные Поды по совпадению их меток (selector: app: backend), выделяет им единый неизменный виртуальный IP-адрес и регистрирует во внутреннем DNS-сервере кластера (CoreDNS) постоянное доменное имя в формате <имя-сервиса>.<неймспейс>.svc.cluster.local. При этом Service автоматически балансирует трафик только между теми Подами, которые прямо сейчас проходят проверку readinessProbe!

    Четыре архитектурных типа Service в Kubernetes:

    1. ClusterIP (используется по умолчанию): Выделяет внутренний виртуальный IP, доступный исключительно внутри периметра самого кластера. Это стандарт для общения микросервисов между собой и с базами данных.
    2. NodePort: Помимо внутреннего ClusterIP, открывает статический порт (из зарезервированного диапазона 30000–32767) напрямую на внешних сетевых картах абсолютно всех рабочих серверов (Worker Nodes) кластера.
    3. LoadBalancer: При создании такого сервиса в облачном Kubernetes (Yandex Cloud, AWS, GCP) кластер сам обращается по API к облачному провайдеру, автоматически заказывает внешний облачный балансировщик нагрузки с выделенным публичным («белым») IP-адресом и направляет его трафик в ваши поды.
    4. Headless Service (Безголовый сервис — задается параметром clusterIP: None): Специальный режим, обязательный для работы со StatefulSet баз данных. Вместо одного общего виртуального IP такой сервис при DNS-запросе возвращает прямые A-записи каждого конкретного пода по его имени (postgres-0.db-svc..., postgres-1.db-svc...), позволяя репликам БД находить мастера напрямую.

    Маршрутизация внешнего HTTP/HTTPS-трафика через Ingress

    Заказывать отдельный платный облачный Service: LoadBalancer с белым IP на каждый из 30 микросервисов компании дорого и неудобно в управлении SSL-сертификатами. Вместо этого в кластер устанавливается всего один входной шлюз — Ingress Controller (на базе Nginx, Traefik, HAProxy или Cilium), который получает единственный белый IP на весь кластер. А правила того, какой домен и какой URL-путь в какой внутренний Service направить (api.example.com/v1 → backend-svc:8000), описываются легкими декларативными объектами kind: Ingress.

    Сетевая безопасность внутри кластера (NetworkPolicy — Zero-Trust Networking)

    Мало кто из новичков знает опасную особенность Kubernetes «из коробки»: по умолчанию сеть внутри кластера абсолютно плоская и открытая — любой Под в любом неймспейсе может без ограничений подключиться по сети к любому другому Поду! Это значит, что если злоумышленник найдет уязвимость в незначительном публичном контейнере лендинга, он сможет напрямую из него подключиться к поду вашей боевой базы данных PostgreSQL на порту 5432!

    Чтобы выстроить эшелонированную защиту по принципу нулевого доверия (Zero-Trust), применяются объекты kind: NetworkPolicy — встроенный в сетевой плагин (CNI) межсетевой экран уровня L3/L4 для подов. С помощью NetworkPolicy мы закрываем под базы данных от всего мира и явно прописываем правило: «Разрешить входящие соединения на порт TCP 5432 или 6379 исключительно от подов, имеющих метку app: backend»!

    Блок 5. Пакетное управление и шаблонизация в Kubernetes с помощью Helm

    Для полноценного запуска всего одного микросервиса в Kubernetes требуется написать 5–6 связанных YAML-манифестов: Deployment, Service, ConfigMap, Secret, HorizontalPodAutoscaler, Ingress и NetworkPolicy. А теперь представьте, что этот сервис нужно выкатить в три разных контура — dev, staging и production, где манифесты на 95% идентичны, но отличаются лишь тегом образа, числом реплик и лимитами памяти. Копировать и синхронизировать десятки статических YAML-файлов вручную по разным папкам невозможно — вы неизбежно допустите опечатку.

    Эту задачу решает Helm — де-факто стандартный пакетный менеджер и шаблонизатор для Kubernetes (выполняющий для кластера ту же роль, что apt для Ubuntu). Helm позволяет превратить набор статических манифестов в единый параметризованный пакет — Helm Chart (Чарт) со строгой структурой каталогов:

    my-service-chart/
├── Chart.yaml            # Паспорт пакета: название, версия самого чарта (version) и версия приложения (appVersion)
├── values.yaml           # Базовые значения всех переменных по умолчанию
├── values-staging.yaml   # Переопределения только для контура Staging (replicaCount: 1, debug: true)
├── values-prod.yaml      # Переопределения для боевого контура Production (replicaCount: 3, autoscaling: true)
└── templates/            # Динамические шаблоны манифестов на языке Go-templates
    ├── deployment.yaml   # Подставляет переменные вида {{ .Values.replicaCount }} и {{ .Values.image.tag }}
    ├── service.yaml
    ├── ingress.yaml
    └── hpa.yaml

    Helm не просто рендерит шаблоны — он ведет прямо внутри кластера (в специальных секретах ревизий) полную версионированную историю всех ваших релизов, позволяя обновлять стек с автоматической проверкой здоровья и откатывать сломанный релиз целиком со всеми его конфигами за одну секунду:

    # 1. Проверить синтаксис чарта встроенным линтером и вывести в терминал итоговый сгенерированный YAML
# для визуальной проверки (Dry-Run без отправки в кластер!)
helm lint ./my-chart
helm template my-release ./my-chart -f values-prod.yaml

# 2. Установить релиз (если его еще нет) или обновить существующий:
# Флаг --atomic — лучший друг DevOps-инженера: если во время обновления новые поды упадут
# и не пройдут readinessProbe в течение таймаута, Helm АВТОМАТИЧЕСКИ откатит весь релиз на прошлую рабочую версию!
helm upgrade --install my-release ./my-chart -n production --create-namespace -f values-prod.yaml --atomic

# 3. Просмотреть таблицу всех исторических ревизий релиза в кластере и мгновенно откатиться на ревизию №1
helm history my-release -n production
helm rollback my-release 1 -n production

    🛠 Практический проект Модуля 10: Развёртывание отказоустойчивого микросервисного стека в кластере Kubernetes через Helm

    Переходим к практике промышленной оркестрации. Сейчас мы развернем на твоей машине настоящий кластер Kubernetes с помощью kind, соберем образ микросервиса, разработаем с нуля собственный Production-grade Helm-чарт и выкатим его в изолированный неймспейс production.

    Этап 2. Сборка Docker-образа микросервиса и загрузка внутрь нод кластера

    Создадим легкий микросервис на Python (app.py), который отдает статус здоровья для проб Kubernetes на /health и возвращает паспорт пода (имя пода, версию релиза, окружение и статус загрузки секрета из Secret) на /api/info.

    Чтобы не пушить учебный образ во внешний интернет в Docker Hub, мы соберем сразу два релиза (2.0.0 и 2.1.0) и загрузим их напрямую в локальное хранилище containerd внутри ноды нашего кластера командой kind load docker-image:

    mkdir -p ~/k8s-practice/app && cd ~/k8s-practice/app

cat << 'EOF' > app.py
import os
import socket
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

APP_VERSION = os.getenv("APP_VERSION", "2.0.0")
ENV_NAME = os.getenv("ENV_NAME", "production")
SECRET_TOKEN = os.getenv("API_SECRET_KEY", "not-set")

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health":
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(json.dumps({"status": "healthy", "pod": socket.gethostname()}).encode())
        elif self.path == "/api/info":
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            resp = {
                "pod_name": socket.gethostname(),
                "version": APP_VERSION,
                "environment": ENV_NAME,
                "secret_loaded": len(SECRET_TOKEN) > 5
            }
            self.wfile.write(json.dumps(resp).encode())
        else:
            self.send_response(404)
            self.end_headers()

if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
EOF

cat << 'EOF' > Dockerfile
FROM python:3.12-slim
WORKDIR /app
RUN groupadd -r appgroup && useradd -r -g appgroup -u 10001 appuser
COPY --chown=appuser:appgroup app.py .
USER 10001:10001
EXPOSE 8000
ENTRYPOINT ["python3", "app.py"]
EOF

# Собираем две версии артефакта и импортируем их напрямую внутрь узлов кластера kind
docker build -t hit-counter:2.0.0 .
docker tag hit-counter:2.0.0 hit-counter:2.1.0
kind load docker-image hit-counter:2.0.0 --name devops-k8s

    1. Шаблон конфигурации и Stateful-слоя БД (templates/stateful-and-config.yaml):

    Обрати внимание на связку Service (clusterIP: None) + StatefulSet + секцию volumeClaimTemplates: при создании пода redis-0 Kubernetes сам автоматически закажет для него постоянный диск PVC размером 1Gi!

    cat << 'EOF' > ~/k8s-practice/charts/webapp/templates/stateful-and-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  ENV_NAME: {{ .Values.envName | quote }}
---
apiVersion: v1
kind: Secret
metadata:
  name: {{ .Release.Name }}-secret
type: Opaque
stringData:
  API_SECRET_KEY: {{ .Values.secret.apiSecretKey | quote }}
---
# Headless Service (обязателен для прямой DNS-адресации подов внутри StatefulSet)
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-redis
spec:
  clusterIP: None
  selector:
    app: {{ .Release.Name }}-redis
  ports:
    - port: 6379
      name: redis
---
# Контроллер StatefulSet с автоматическим созданием постоянного диска через volumeClaimTemplates
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: {{ .Release.Name }}-redis
spec:
  serviceName: "{{ .Release.Name }}-redis"
  replicas: 1
  selector:
    matchLabels:
      app: {{ .Release.Name }}-redis
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - containerPort: 6379
          volumeMounts:
            - name: redis-data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: [ "ReadWriteOnce" ]
        resources:
          requests:
            storage: {{ .Values.redisStorageSize }}
EOF

    2. Шаблон Stateless-бэкенда, автоскейлера и сетевой защиты (templates/backend-stack.yaml):

    cat << 'EOF' > ~/k8s-practice/charts/webapp/templates/backend-stack.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-backend
  labels:
    app: {{ .Release.Name }}-backend
spec:
  replicas: {{ .Values.replicaCount }}
  # Стратегия бесперебойного обновления без простоя (Zero-Downtime RollingUpdate)
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: {{ .Release.Name }}-backend
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-backend
    spec:
      # Hardening на уровне пода: запрещаем запуск от root, жестко задаем UID 10001
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
      containers:
        - name: backend
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: 8000
          env:
            - name: APP_VERSION
              value: {{ .Values.image.tag | quote }}
          # Инжекция всех переменных из ConfigMap и Secret одной строчкой!
          envFrom:
            - configMapRef:
                name: {{ .Release.Name }}-config
            - secretRef:
                name: {{ .Release.Name }}-secret
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
          # Сенсор готовности: трафик от Service пойдет на под только после ответа 200 OK на /health
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 2
            periodSeconds: 5
          # Сенсор живучести: перезапустит контейнер при зависании процесса
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 10
          # Пауза перед остановкой для плавного вывода пода из таблиц балансировки iptables
          lifecycle:
            preStop:
              exec:
                command: ["sleep", "2"]
---
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-backend-svc
spec:
  type: ClusterIP
  selector:
    app: {{ .Release.Name }}-backend
  ports:
    - port: {{ .Values.service.port }}
      targetPort: 8000
---
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ .Release.Name }}-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ .Release.Name }}-backend
  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}
{{- end }}
---
# Микросегментация сети (NetworkPolicy): разрешаем подключение к порту Redis 6379 ТОЛЬКО подам нашего бэкенда!
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: {{ .Release.Name }}-redis-netpol
spec:
  podSelector:
    matchLabels:
      app: {{ .Release.Name }}-redis
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: {{ .Release.Name }}-backend
      ports:
        - protocol: TCP
          port: 6379
---
# Правило внешней HTTP-маршрутизации (Ingress)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Release.Name }}-ingress
spec:
  rules:
    - host: "app.local"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: {{ .Release.Name }}-backend-svc
                port:
                  number: {{ .Values.service.port }}
EOF

    Этап 4. Валидация Helm-чарта, выкатка релиза в кластер и инспекция ресурсов

    1. Проверим наш свежесозданный чарт встроенным синтаксическим анализатором helm lint:
    cd ~/k8s-practice

    1. Установим релиз под именем prod-app в выделенный неймспейс production (флаг --wait прикажет Helm дождаться момента, когда все поды и диски реально перейдут в статус Ready!):

  --namespace production \
  --create-namespace \

    1. Выведем полную картину созданных в неймспейсе production объектов одной командой kubectl:
    kubectl get all,pvc,ingress,networkpolicy,hpa -n production

    Обрати внимание на красоту инженерной оркестрации в выводе терминала: * Контроллер StatefulSet поднял под базы со строгим предсказуемым именем pod/prod-app-redis-0 и автоматически создал и привязал к нему постоянный диск persistentvolumeclaim/redis-data-prod-app-redis-0 в статусе Bound! * Контроллер Deployment запустил 2 реплики бэкенда prod-app-backend-... в статусе 1/1 Running, которые успешно прошли проверки readinessProbe и встали за виртуальный балансировщик service/prod-app-backend-svc.

    ✅ Чек-лист самопроверки и испытания RollingUpdate / Rollback по Модулю 10

    Выполни три финальных испытания в терминале:

    1. Проверка работы сервиса, чтения ConfigMap/Secret и балансировки трафика через Service: Откроем защищенный туннель (port-forward) от локального порта 8085 напрямую в виртуальный сервис кластера svc/prod-app-backend-svc и сделаем запрос: 

      kubectl port-forward -n production svc/prod-app-backend-svc 8085:8000 &
PF_PID=$!
sleep 2

curl -s http://localhost:8085/api/info | python3 -m json.tool
kill $PF_PID
      Ожидаемый результат: Чистый JSON-ответ от одного из подов кластера с версией "2.0.0", окружением "production" из ConfigMap и подтверждением "secret_loaded": true из Secret!

    2. Испытание бесперебойного обновления (Zero-Downtime RollingUpdate) до версии 2.1.0 через Helm: Переопределим версию образа на лету флагом --set image.tag="2.1.0". Благодаря нашим настройкам maxUnavailable: 0 и readinessProbe, Kubernetes сначала поднимет новые поды 2.1.0, убедится в их здоровье и только потом погасит старые: 

      helm upgrade prod-app ./charts/webapp \
  -n production \
  --set image.tag="2.1.0" \
  --wait

kubectl rollout status deployment/prod-app-backend -n production

    3. Испытание машины времени helm rollback (мгновенный откат релиза по истории ревизий): Выведем журнал ревизий нашего релиза в кластере, а затем одной командой откатим весь стек назад на ревизию 1 (версию 2.0.0): 

      helm history prod-app -n production
helm rollback prod-app 1 -n production --wait
helm history prod-app -n production
      Ожидаемый результат: В таблице истории появилась новая запись ревизии 3 со статусом deployed и комментарием Rollback to 1 — кластер за 3 секунды без единого разрыва соединения вернул все поды на стабильную версию 2.0.0!
